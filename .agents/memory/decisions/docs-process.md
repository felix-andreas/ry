# Decisions: Docs, process and positioning

The docs site, licensing, positioning, and how agents record and organize knowledge.

## Licensing

**Status:** built, except reading base R's code from the user's GNU R installation, which "ry ships its own base R, and GNU R through `R_HOME` is the opt-in" supersedes.

- **Rule.** GPL-2.0-or-later where code translated from GNU R is contained or linked, UPL-1.0 elsewhere, LGPL-2.1-or-later C headers (`crates/libr/include`), MIT editor extensions. Each `Cargo.toml` `license` field is the source of truth; `docs/src/content/docs/reference/licensing.md` is the user-facing contract and lists every part.
- **Why GPL at all.** Many runtime components (TOMS 708, `pnorm`/`qnorm`, `ptukey`, the random variate generators, plotmath, `persp`, `swilk`, UNCMIN, QUADPACK, the X-spline and others) are translations of GNU R's C sources, so an earlier clean-room/UPL claim was false. Each such file keeps R's copyright lines in a header naming the R source file.
- **Why GPL-2.0-or-later, not -only.** It equals R's own "GPL (>= 2)", so code flows both ways with R and CRAN. GPL-2.0-only is impossible: 17 shipped crates carry mandatory Apache-2.0 terms (`ab_glyph`, `miette`, the polars crates, `ring`), so the binary as a whole is conveyed under GPL-3, which `LICENSE` says once.
- **Why the split.** UPL is GPL-compatible, so the tooling crates stay reusable as permissive libraries at no legal cost. The test is the dependency graph, not the binary: `repl` embeds the built `libR` as bytes and links none of its code, so it and the crates that reach the runtime only through it stay UPL.
- **Why LGPL headers.** R's public headers are LGPL, so a package compiled against them keeps its own licence. ry's headers must not copy R's GPL-only `Rinterface.h` or `Rembedded.h`.
- **Why MIT editors.** No R-derived code, and Zed's registry needs an accepted licence. The VS Code vsix bundles the GPL binary, so `just build-extension` writes a `LICENSE` with the MIT text, ry's `LICENSE` and `THIRD_PARTY_NOTICES`.
- **Notices.** `just notices` (`tools/third-party-notices.py`) generates `THIRD_PARTY_NOTICES` from `cargo metadata`, the crates' licence files, the R provenance headers and a fixed list of notices outside Cargo (Adobe AFM metrics, L-BFGS-B, MT19937, Xfig, IJG, bundled C libraries); `just package` puts it beside `LICENSE` in every archive, and `just notices --check` fails when it is stale or a crate's `license` breaks the rule.
- **Invariant.** New code may translate GNU R when that is the fastest route to bit-identical results, but only in a GPL crate with an R provenance header. A UPL crate must never gain a dependency on a GPL crate.

## Positioning

**Status:** built, except the Tutorial and why-ry pages, which "Docs information architecture: Introduction, Learn, Reference, Development" supersedes, and the Speed tab's linear chart, which the landing page does not have.

- **Audience.** Teams with large, old R code bases that want agents to write and change that code. Agent-written code needs verification that does not depend on a human reading every line, and a type checker gives it on every edit. The pitch leads with this, because "a language server for R" undersells why the project exists.
- **Shape: one toolchain, R plus types, then R++ and R--.** ry's types sit on top of R and check existing code; ry's runtime features (records, tags and `match`, frames, the standard library, inline annotations) plus plain R are R++; strict mode, typed code only, is R--. A two-circle Venn diagram shows it (R left, ry's types and features right, typed R with `#:` comments in the overlap; the union is R++, the right circle strict mode), with one source, `docs/src/components/Venn.astro`, used by the landing page and `getting-started.mdx`.
- **One tagline: "A type checker and a fast runtime for R, written in Rust."** The README, landing subhead and meta description, Starlight site description, `getting-started.mdx`, `ry.mdx`, the Zed extension and the `ry-lang` crate repeat it word for word (user direction). It names the two things a reader cannot get elsewhere; linter, formatter and language server follow in the body. The hero heading "A toolchain for R." is drawn by the user-owned animation and keeps its own wording.
- **The migration is sold as moving your code into the future, not as switching to ry.** Avoid "migrate to ry"; step 4 is "Go fully typed". Step 3 is "Switch to the ry runtime" (user direction), because it is the one step that changes what runs the code.
- **The landing page sells features first, migration last**: one toolchain (what works today), then the runtime's features, then the four migration steps beside the Venn. A reader has to want the destination before a path to it matters. On wide screens the steps and the selected step's code fill the left column and the diagram sits right, so code stays under the step that chose it; on phones the diagram comes first. Rejected: opening with the Venn and migration, and leading with "a reimplementation of R" (true, but the incomplete runtime is the destination, not the pitch).
- **Almost no prose on the landing page.** A headline, at most one sentence, and tabs of real code beside real output; no eyebrow labels, notes or hints. Detail lives in `getting-started.mdx`.
- **Motion shows the story, never decorates.** Each step moves a "your code" marker in the Venn (`data-step` on `Venn.astro`; without it the diagram is static). Every switch shares one symmetric ease-in-out curve and duration (`--switch-ease`, `--switch-duration`), because ease-out read as abrupt. Snippets reveal code first, then output, on first view and on each tab switch; one neutral pill slides between tabs (no colored outline or glow). Every snippet function uses a `{}` body. All motion is off under `prefers-reduced-motion`.
- **Each landing snippet teaches exactly its tab's concept.** An R user who has never seen ry understands it in five seconds, and nothing else makes a newcomer stop: `type`, never `alias`; no `@new`, one-field records, generics, open unions or `eval(parse())` tricks; one union variant per line with a leading `|`; the fewest annotations that make the point. If a snippet needs a sentence, simplify the snippet.
- **The checker tab opens untyped**: plain R with a real `ry check` finding, then an Untyped/Typed toggle showing the fix plus one `#:` line that finds the next bug, one diagnostic per mode so both outputs have the same height, and a one-line caption says R reads the `#:` line as a comment. Each toolchain view ends with one quiet docs link. Leading with annotations assumed the reader knew what they were.
- **Tabs in one frame share the tallest tab's height** (panels share one grid cell so a switch does not move the page on wide screens), so snippets are sized to similar heights (toolchain tabs about 320px at 1440px wide, typing steps within about 100px of each other), and the language server's feature tabs sit in the frame's header row like the checker toggle. At 900px and below, code and output stack and each frame fits its own panel.
- **The landing Venn has a step indicator and a caption**: four clickable bars repeat the step tabs for pointer users, one plain caption per step says what the highlighted region means (defining R++ and R-- in context), and the Venn is centred against the steps column. The static copy on `getting-started.mdx` has neither.
- **A tab appears only once its feature has a real snippet**; no placeholder tabs. A speed chart keeps every program, slowdowns included, because hiding a loss costs more trust than it buys. The DataFrame tab shows the Polars-style API, never data.table's `x[i, j, by]` (kept for compatibility only), with one line for the `tools/bench/internal/table` result.
- **Four migration steps, each optional and reversible**: check the code you have, add `#:` types, switch to the ry runtime (inline types, which it also enforces at run time, and ry's own features), go fully typed under strict mode. The user proposed this structure; it is kept because each step maps to a shipped feature with real output. `docs/src/content/docs/guide.mdx` tells it in full.
- **GNU R stays a first-class target.** `#:` comments keep a file plain R; the pitch says so in one sentence.
- **The benchmark is honest about typing**: it never implies that types buy speed beyond what the measured results show.

## Data-oriented design and explicit allocators

**Status:** built.

Performance comes first (user directive, `AGENTS.md` "Goals"). The open audit list is `backlog.md`, "Open: data-oriented layouts and explicit allocators".

- **The rule.** Hot data is dense arrays indexed by small `Copy` ids (`u32`), not a graph of boxed nodes. Split a record into parallel arrays when a hot loop reads only some fields, keep variable-length children in one flat side array addressed by ranges, and use bitsets for per-element flags. Memory that lives exactly one phase (one item check, one parse, one JIT compilation, one query plan) comes from an arena or bump allocator dropped as a whole. Long-lived objects of one shape come from pools of that shape. A new hot structure holding `Box`, `Vec` or `String` per node needs a reason.
- **Where it applies first.** The checker's per-item inference, HIR lowering, the JIT's analysis plan, the heap's mark and sweep. The table engine already keeps Arrow columns and struct-of-arrays accumulators.
- **Toolchain: a pinned nightly (user directive), with std's allocator API as the interface.** `rust-toolchain.toml` pins a dated nightly that has the `allocator_api` subset Rust 1.100.0 stabilizes (rust-lang/rust#156882: `Allocator`, `Global`, `System`, `Box<T, A>`, `Vec<T, A>` with `new_in` and `with_capacity_in`) with no feature gate; `#![feature(allocator_api)]` only warns, and the unstable remainder is `allocator_ext`. Verified: `Vec::new_in(&bump)` and `Box::new_in(x, &bump)` build against `bumpalo` 3.20, and `hashbrown::HashMap::new_in(&bump)` with hashbrown 0.16's `nightly` feature. Arenas are `bumpalo` through std's `Vec` and `Box`; maps stay on `hashbrown` with its `nightly` feature (std's `HashMap`, `String`, `Rc`, `Arc` take no allocator). The `allocator-api2` polyfill route is rejected.
- **Trap: `bumpalo`'s `allocator_api` feature must stay off in any build that links Cranelift.** Cargo unifies it with the `allocator-api2` feature `regalloc2` uses, and with both on `bumpalo` drops its `allocator-api2` impl and `regalloc2` fails to compile. The JIT wraps `&Bump` in its own std `Allocator` (`Arena` in `crates/jit/src/analysis.rs`).
- **The pin moves deliberately**: bump the date in one commit that also fixes what the new nightly breaks, never float `nightly`. `flake.nix` reads the channel from `rust-toolchain.toml`, so a bump may need `nix flake update rust-overlay`. `cargo install --git` ignores the file, so the installation page says to pass `+nightly`.
- **A nightly feature needs a clear payoff**, a `#![feature(...)]` at the crate root and a one-line reason. Likely candidates: `allocator_ext`, `portable_simd` (table kernels), `likely_unlikely` (interpreter and heap fast paths), `never_type`, `try_blocks`, `trait_alias`. Incomplete features (`specialization`, `generic_const_exprs`) stay out. Nightly rustfmt applies `group_imports` and `imports_granularity` from `rustfmt.toml`, so each file has one `use { ... }` tree.
- **The global allocator is mimalloc**, in the `ry` binary (`crates/ry/src/main.rs`, default feature `mimalloc`) and in `libR.so` (`crates/libr/src/libr.rs`), pinned to `features = ["local_dynamic_tls", "v2"]`: the default TLS model fails `dlopen`, and v3 crashes in `mi_thread_init` on the second thread that allocates after the first one exits (the libr test binaries do this; a package with short-lived threads could). Under `ry run`, data.table's OpenMP workers and Polars' thread pool run beside v2 without a crash (both keep their threads alive). Move to v3 only once a `libmimalloc-sys` release passes the libr test binaries. Cargo unifies features, so a build of both gives the binary v2 too; `mi_option_arena_eager_commit` is option 4 in both versions. Arenas sit on top of the global allocator.
- **Salsa.** Tracked-query results and interned data must own their memory and compare by value, because salsa stores them across revisions and backdates by equality. An arena never leaks into a memoized result: do the work in a scratch arena and copy out a compact owned form (boxed slices, dense tables indexed by `ExprId`). Types an item check builds and discards belong in a per-check store; only exported schemes and recorded expression types get interned, because interned ids (`Ty`, `Name`) are dense but every intern goes through salsa's shared table.
- **R's C API.** Every `SEXP` lives in `heap`'s collector, because native code holds it for an unknown time (`PROTECT`, preserved objects, external pointers). A phase arena must never back an R object that can escape to C. Inside the heap, data-oriented design applies (side mark bitmaps, size-class pages) as long as a `SEXP` is a stable, non-moving pointer to its header. `R_alloc` is the one arena R defines (`crates/heap/src/arena.rs`). Arenas suit analysis, the parser, and the JIT's compile-time data.
- **Trap: reserve arena lists whose final size is roughly known.** A bump arena cannot reuse a vector's old buffer, so a growing list copies itself on every doubling; the JIT analysis plan's first arena layout was 25% slower than the old one for this reason.
- **Measured: the JIT's analysis plan** (`crates/jit/src/analysis.rs`): operands borrowed from the bytecode words, abstract states as rows of one flat matrix, liveness as bitsets, `block_at` as a dense array, all in one `Bump` per compilation. Analysis time per program fell from about 6.0 ms to about 4.5 ms over seven benchmark programs, but analysis is only about 5% of compile time; Cranelift's code generation is the rest.
- **Impact.** Incremental analysis is unaffected as long as memoized results stay owned and value-compared. Each audit item is measured before and after, and a layout change that does not pay is reverted.

## Docs information architecture: Introduction, Learn, Reference, Development

**Status:** built.

- **Shape.** Introduction (`getting-started.mdx` with no code example, `installation.md`, `benchmarks.mdx`), Learn (`guide.mdx`, "Adopting ry", one H2 per step; `ry.mdx`, the language tour), Reference (`reference/`, the contracts) and Development (`development/`, design drafts in `development/design/`). Owner direction: one guide instead of per-step tutorial pages, the tour and guide in their own section, no example on getting started. One page per story means links are anchors and step names live in one file.
- **Redirects.** Old URLs redirect through the `redirects` map in `docs/astro.config.ts` (`/tutorial/<page>` to the matching `/guide#step-N-...` anchor, `/tour` to `/ry`).
- **Markdown copies** (`/<page>.md`, `/llms.txt`, `/llms-full.txt`) are built from the raw MDX by `docs/src/lib/markdown.ts`. `starlight-llms-txt` was rejected because it converts rendered HTML and writes no per-page files. Page order comes from the sidebar in `astro.config.ts` (via `virtual:starlight/user-config`), and `PageTitle.astro` derives breadcrumbs from it, so the sidebar is the one source of order.
- **Sidebar scroll.** starlight-theme-black scrolls `.sidebar-content`, while Starlight's persister saves the scroll of `#starlight__sidebar`, which never scrolls. `docs/src/components/Sidebar.astro` saves `.sidebar-content`'s `scrollTop` to sessionStorage on click and `pagehide` and restores it in an inline script right after the sidebar markup, before first paint.
- **Content rules.** Every rule is stated with its reason; a thing is explained once where it is introduced and tabulated once in Reference, and other pages link to it.

## Landing-page and README samples are captured from the running tools

**Status:** built.

- **Decision.** Every diagnostic or console sample on the landing page and in the README is tool output, cut to the headline and underlined line, never hand-edited, because a hand-edited sample drifts silently with the next wording change.
- **Shape.** Landing samples are tests in `crates/ry/tests/test_docs.rs`. The README shows diagnostics as SVG panels (`docs/public/diagnostic*.svg`) because GitHub strips ANSI colors; `scripts/render-diagnostic-svg.rs` (`PANELS` names each image's `ry.toml`) renders them from output captured with `CLICOLOR_FORCE=1` and embeds a `prefers-color-scheme` rule. `just readme --check` reports a stale panel.
- **Gap.** The VS Code extension's README holds two plain-text diagnostics that no check covers.

## The decision log is one file per area, with a generated index and byte budgets

**Status:** built.

- **Shape.** Twelve area files under `.agents/memory/decisions/`, each entry an H2 with its `**Status:**` line, and `decisions/index.md`, generated by `python3 tools/memory.py index`, with one heading per entry. `tools/memory.py check` (in `just gate`) fails on a reappearing `decisions.md`, a stale index, an unknown area file, a file over its byte budget or a line over its file's limit. Every area file is capped at 160,000 bytes (`AREA_CAP`; an area that reaches it is split in two), and the other budgets (`BUDGETS`) sit about 5% above the sizes when they were set, as a ratchet to tighten. `tools/memory.py split` moves a stray `decisions.md` into the area files and refuses to write if the multiset of entry bodies changes.
- **Why.** A single 1.5 MB log (433 entries under 70 H1 records that had drifted from their content, one holding 189 unrelated entries) could only be grepped, never read, and nothing bounded its growth. An agent reads the index, then one area file; budgets make growth a visible decision.
- **What every agent pays for.** `AGENTS.md` loads into every session, so each rule appears once; crate-scoped rules live in `crates/<crate>/AGENTS.md`, long examples and docs mechanics in `development/index.md`. `AGENTS.md` is capped at 28 KB, `MEMORY.md` at 32 KB and `.agents/orchestrator.md` at 30 KB with lines of at most 2 KB (its log keeps the last 20 one-line entries). `backlog.md` lists open work only: a shipped item is deleted, with its rationale here and its contract in the docs. `worklog.md` holds one line of at most 400 bytes per cycle.

## Source comments have length limits, enforced by a ratchet

**Status:** built.

- **Previous shape.** Comments were 17.8% of the Rust source bytes, and the comment rules in `AGENTS.md` had no check. Long blocks that restated code, narrated history or organized a file cost context on every whole-file read by an agent.
- **Target shape.** `tools/comments.py check` (`just comments`, in `just gate`) flags a `//` or `///` block over 12 lines, a `//!` doc over 25, banners, short section-heading lines, and process words (milestones, phases, pull request numbers, and hashes after "commit", "revert" or the like or in backticks, so hex constants and "Apple M1" pass). The regex leaves out "no longer" and "this session", which are domain terms for R sessions, and GNU R's `PR#` bug references. License headers, `patches/` and `target/` are exempt.
- **Ratchet.** `tools/comments-baseline.txt` holds per-file counts that may only shrink: `baseline` refuses to raise a count without `--force`, and `check` fails both above and below a count, so a fix is recorded. A block whose facts do not fit the limit stays over it and is carried by the baseline: a fact outranks the line limit, so shortening never drops a reason, an invariant or a measured cost.
- **Impact.** A new over-long or history comment fails the gate, while files under active edit by other work get time to be cleaned up.

## Each crate's `AGENTS.md` loads through a one-line `CLAUDE.md` beside it

**Status:** built.

- **Shape.** Every `crates/<crate>/AGENTS.md` has a sibling `CLAUDE.md` holding only `@AGENTS.md`, as the repository root does. Claude Code loads a nested `CLAUDE.md` when it reads or edits files in that directory, so a crate's traps reach the agent that works there and cost nothing elsewhere.
- **Why.** The crate rules moved out of the root `AGENTS.md` to cut what every session pays for, and nothing loaded them, so an agent had to know to open them.
- **Rule.** A new crate `AGENTS.md` gets its `CLAUDE.md` in the same change. The rules stay in `AGENTS.md`, which other tools read; `CLAUDE.md` never holds text of its own.
