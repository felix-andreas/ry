Two principles explain most of the rules on this page. First, the checker prefers skipping a check
to giving a wrong answer: a construct it cannot describe becomes `Unknown`, which is compatible with
everything, so a gap means a skipped check rather than a false error, and [strict mode](#strict-mode)
shows where the gaps are. Second, every rule must be cheap enough to check on every keystroke, which
is why inference is Hindley–Milner, why your own functions cannot be overloaded, and why there is no
subtyping between nominal types. The [overview](/type-checking/overview) introduces the same ideas
through examples.

`ry check` reports the type errors on this page only when typing is on, through `[check] typing = true`
in `ry.toml` or a `# typing: on` comment at the top of the file (see
[configuration](/reference/configuration)). Every output block here was produced that way. With
typing off, the checker still reports unresolved names, such as a misspelled column in a data.table
query's `i`, but no type errors.

## Typing comment syntax

Annotations are written in two ways that share one type grammar: in `#:` comments, described here,
and [inline](#inline-annotation-syntax), in the code itself. An example that has both spellings shows
them in tabs, and the tab you choose is remembered on every page of this site. A form that exists in
only one spelling shows a single block and says so. A `#:` comment sits directly above the
binding or expression it describes. Consecutive `#:` lines with no blank line between them form one
*annotation block*. Each annotation takes one of these forms:

- `#: TYPE` is a [checked annotation](#checked-annotations).
- `#: @trust TYPE` is a [trusted coercion](#trusted-coercions).
- `#: @if-unknown TYPE` is an [unknown-only coercion](#unknown-only-coercions).
- `#: @new NOMINAL_TYPE` is a [nominal introduction](#nominal-introduction).

A block is one of three kinds, which cannot be mixed: a single line in one of those forms, an
[expanded function annotation](#expanded-function-annotations) written as `@param` and `@return`
lines, or a definition block of `@type` and `@alias` lines.

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
value: integer <- 1L

double_count <- function(count: integer) -> integer count + count
```

</TabItem>
<TabItem label="Comments">

```r
#: integer
value <- 1L

#: fn(count: integer) -> integer
double_count <- function(count) count + count
```

</TabItem>
</Tabs>

A block can attach at any statement depth. Inside a function body it annotates the assignment or the
block-final expression that follows it, which is how a function that builds a value of a named type
is written:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
type Person = list{name: character}

make_person <- function(name: character) -> Person {
  @Person(list(name = name))
}
```

</TabItem>
<TabItem label="Comments">

```r
#: @type Person {list{name: character}}

#: fn(name: character) -> Person
make_person <- function(name) {
  #: @new Person
  list(name = name)
}
```

</TabItem>
</Tabs>

### Attachment

A block attaches to the expression that starts on the line directly after it. A braceless function
body, a braceless `if` branch, and a parenthesised expression are valid targets. When a block needs a
target and has none, it is an error and the annotation does not apply. That happens when:

- a blank line separates the block from the expression;
- a plain `#` comment separates them, or no expression follows at all;
- the block has no content beyond the `#:` marker;
- the block sits inside a call's argument list, for example beside a lambda passed to `lapply`,
  because an argument is not a statement. Give the value its own binding and annotate that instead.

A definition block, one that contains only `@type` and `@alias` lines, attaches to nothing, and
neither does a `@strict` toggle, so the adjacency rules do not apply to them.

### Refused blocks

A block is refused as a whole when it mixes forms, orders its directives wrongly, declares a
duplicate or unknown type parameter, or gives `@new` a payload that is not nominal. A refused block
reports its error and carries no typing payload, so a broken annotation does not cause follow-on
findings. Two known exceptions still do: a `[]` vector whose element type is not atomic or is not
declared (`Rec[]`), and a bare optional positional parameter (`fn(integer, [character])`). A block
the annotation grammar could not read at all is refused silently, because the parse error has
already said what was wrong.

## Inline annotation syntax

An inline annotation writes a type into the code instead of a comment above it:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
count: integer <- 0L

add <- function(x: integer, y: integer = 1L) -> integer {
  x + y
}

first <- function<T>(items: list[T]) -> T items[[1L]]
```

</TabItem>
<TabItem label="Comments">

```r
#: integer
count <- 0L

#: fn(x: integer, [y]: integer) -> integer
add <- function(x, y = 1L) {
  x + y
}

#: <T> fn(items: list[T]) -> T
first <- function(items) items[[1L]]
```

</TabItem>
</Tabs>

- `name: TYPE <- value` declares a binding's type. The `=` spelling, `name: TYPE = value`, works too.
- `name: TYPE` in a parameter list declares a parameter's type, before its default if it has one.
  `...: TYPE` declares the rest parameter.
- `-> TYPE` between the parameter list and the body declares a function's return type.
- `<T, U: numeric>` directly after `function` or `\` declares the function's type parameters, with
  the same names and constraints as the compact `<...>` binder.
- `type Name<T> = TYPE` and `alias Name<T> = TYPE` at the top level of a file define a
  [named type](#named-types-and-generic-application), like `#: @type Name<T> {TYPE}` and
  `#: @alias Name<T> {TYPE}`.
- `name: @trust TYPE <- value`, `name: @if-unknown TYPE <- value` and `name: @new Name <- value`
  write a binding's [coercion](#unknown-only-coercions) inline.
- `@Name(value)` and `@Name<ARGS>(value)` introduce a nominal type on a value, like `#: @new Name`
  on that value. The `(` must follow the type directly, and `value` may be any expression, including
  a record or tuple: `@Point((x = 1, y = 2))`.
- `name <- @pure function(...)` and `name <- @pure \(x) ...` declare the function pure, like a
  `#: @pure` line above the binding (see [purity](#purity)). Followed by `(`, `@pure(...)` is a
  nominal introduction instead.

Every `TYPE` is the type grammar of `#:` comments, so anything a `#:` type can say an inline type can
say, and a type reads the same written either way.

### Meaning

An inline annotation means exactly what the equivalent `#:` block means, because both lower to the
same annotation:

- A binding's type is a [checked annotation](#checked-annotations): `count: integer <- 0L` is
  `#: integer` above `count <- 0L`.
- A function's inline types form a [compact annotation](#compact-function-annotations) naming the
  annotated parameters, so `function(x: integer, y)` is `#: fn(x: integer)` over `function(x, y)`.
  [The formal list](#annotations-and-the-formal-list) rules apply unchanged, and an unannotated
  parameter keeps its inferred type.
- A parameter with a default is optional, so the inline form never needs `[name]`.
- `type` and `alias` definitions are the `@type` and `@alias` definitions of the same name, in the
  same project-global namespace.
- A binding's directive, as in `x: @trust integer <- v`, is the same directive in a `#:` block above
  the binding. `@Name(value)` is `(value)` with `#: @new Name` on it.
- A function without `-> TYPE` infers its return type from its body, as an
  [elided return](#elided-return-types) on a definition does. A function type inside an inline
  annotation, such as `f: fn(integer)` or `callback: fn(integer)`, follows the `#:` rule for that
  position: `NULL` when nested, and inferred from the body when it is a binding's whole type over a
  function literal.

Because the signature sits on the function itself, a function that is not a statement can be
annotated too. `lapply(ids, function(id: integer) -> character format(id))` checks the lambda's
body against its signature and the call against its parameter, where a `#:` comment could not reach
it. When a binding's type and its function's own signature are both written, as in
`step: fn(x: integer) -> integer <- function(x: integer) -> integer x + 1L`, the signature types the
function and the binding's type is then checked against it like any other value.

### Where inline annotations parse

A parameter's type and a function's return type and type parameters can be written on any function
literal. A binding's type is recognized only where a statement starts, at the top level of a file or
directly inside `{ }`. Elsewhere, such as in a braceless `if` branch, `y: integer <- 1L` is R's
reading of `y:integer` as an assignment target, which is reported as a syntax error. A binding's type
continues onto the next line inside an open bracket, after a `|`, and onto a line that starts with
`|`.

`type` and `alias` start a definition only at the start of a statement and only when a name follows
them on the same line, so `type <- "x"`, `alias(y)` and every other use of them as ordinary names
keep their R meaning. A definition inside a function body or any other block parses, but is an
`annotation` error: definitions belong at the top level of a file. A definition ends at the end of
its line, and nothing but a comment may follow it there, so `type Id = integer; x <- 1` is a syntax
error. Its type continues onto the next line after `=`, after a `|`, inside an open bracket, and
onto a line that starts with `|`. No R statement starts with `|`, so a union may line
up its members:

```r
alias Shape =
  | :Circle(radius: double)
  | :Rect(width: double, height: double)
```

A leading `|` is allowed in any union, in a `#:` comment too.

A return type is read as far as the type grammar reaches, and the body starts after it. A list or
function type must hug its bracket, as the formatter writes it: `-> list{name: character}` is a
record type, while in `-> list {` and `-> fn (` the bracket starts the body.

A mistake in an inline type's grammar is a `syntax-error`, because the statement cannot be read
until it is fixed. A type that parses but means nothing, such as an unknown type name or a record
that mixes named and positional items, is an `annotation` error, as it is in a comment.

### Erasure to plain R

R's own parser rejects every inline annotation except a binding's, which R reads as an assignment to
`name:TYPE` through a `` `:<-` `` replacement function that base R does not define. So no working R
program contains one, and existing R code parses and behaves exactly as before.

`type` and `alias` definitions and `@Name(value)` are not R either: a definition is two names in a
row, and `@` cannot start an R expression. At the start of a line, `@Name` reads as a constructor
only when `(` or `<` follows the name, so a slot access broken across lines, `obj` then `@slot`,
keeps R's own syntax error.

Removing each inline annotation turns an annotated program into the plain R program it means:
delete a binding's or parameter's `: TYPE` (with its directive), a function's `<...>`, its
`-> TYPE`, and the `@Name` of `@Name(value)`. A type definition becomes its `#:` comment, line for
line, so the erased program still declares the type, and a definition paired with a `#:` block
directly above it is removed, because that block already declares it. Comments and `#:` blocks
stay. `count: integer <- 0L`
erases to `count <- 0L`, `function<T>(x: T) -> T x` to `function(x) x`, `@UserId(5L)` to `(5L)`,
and `type UserId = integer` to `#: @type UserId {integer}`.

### Inline and comment annotations together

A statement can carry both a `#:` block and inline annotations. They combine one *slot* at a time,
where a slot is the binding's value, one parameter, the rest parameter, or the return:

- A slot only one of them types takes that type.
- A slot both type takes the inline type.
- A coercion (`@trust`, `@if-unknown`, `@new`) says how the value gets its type, so it governs the
  value wherever it is written, and the other side's type is only compared against it. When both
  sides are coercions, the inline one governs.

A slot typed both ways with different types is reported as `annotation-mismatch`, a warning at the
inline type that points at the comment's type, so the reader always learns which one ry uses.
Types are compared as types: an alias agrees with its expansion, and `integer | character` agrees
with `character | integer`. Type parameters pair by position, so `<T>` in the comment and `<U>` in
the code agree, and a binder whose constraint differs is reported the same way, with the inline
constraint winning. A positional parameter type in a compact `#:` annotation is compared with
the formal it pairs with.

A type definition pairs the same way. A `#:` definition directly above an inline definition of the
same name, with nothing but a line break between them, is one definition written twice. It counts
once, so it is not a duplicate, and the inline definition is the one that applies. When the two
differ in kind (`@type` against `alias`), in the number of type parameters, in a constraint, or in
the type itself, ry reports `annotation-mismatch` at the inline definition, pointing at the comment.
Type parameters pair by position, so `#: @alias Pair<T> {Tuple{T, T}}` and
`alias Pair<U> = Tuple{U, U}` agree. A `#:` definition anywhere else in the project with the same
name is a duplicate, as two `#:` definitions are.

This example deliberately uses both spellings on one function:

```r
#: fn(price: double, rate: double) -> double
apply_discount <- function(price: integer, rate) price * (1 - rate)
```

```text ry check typing
! the inline annotation gives parameter `price` the type `integer`, but the `#:` comment gives it
  `double`. ry uses the inline type; make the two agree, or delete one
```

### Turning inline annotations off

`[check] inline-annotations = false` in `ry.toml` turns inline annotations off, for code that must
also run under R. An annotation that is off types nothing, and each one is reported once as an
`inline-annotation` warning, because R cannot run that code. ry also warns once per run, and the
language server once per load, for as long as the setting stays off. A `#:` block on the same
statement then applies alone, and so does a paired `#:` definition. An inline type definition with
no `#:` partner still declares its name, so uses of it are not also reported as unknown types. A
`type` stays nominal, so a plain value is still not accepted where it is expected, but its
representation is `Unknown`. The setting also governs running code: `ry run` and `ry R` still
run annotated code, but ry's runtime registers no checks for the annotations.

### Inline annotations at run time

`ry run` runs annotated code on ry's runtime and `ry R` on GNU R, which reads the erasure. ry's runtime
reads the annotations themselves and checks a function's parameter and return types at its
boundary, so a function called with the wrong kind of value fails where it was called instead of
somewhere inside it. The checks come from the inline spelling, so this example has a single block:

```r
scale <- function(values: double, by: double) -> double values * by
scale("a", 1)
```

```text ry run runtime=ry
Error in scale("a", 1) :
  argument `values` must be `double`, not `character`
```

A check never changes what code that satisfies its annotations does, which the oracle pins by
comparing annotated cases on ry's runtime against GNU R running their erasure. The checks follow
these rules:

- **Parameters are checked when their value is computed.** An argument stays a promise and is
  checked when it is forced, so laziness, `missing()`, and `substitute()` behave as in R, and an
  argument that is never used is never checked. An argument that is already a value, such as a
  constant, is checked when the function is entered.
- **Every `...` argument is checked against the rest parameter's type**, under the same rule. An
  argument forwarded through `...` to another typed function is checked against both functions'
  types when it is forced.
- **The return value is checked when the function returns**, including through `return()`, and
  before `on.exit` code runs.
- **Bindings are not checked.** `x: integer <- value` types `x` for the checker and is erased at
  run time.
- **Type definitions and `@Name(value)` do nothing at run time.** A definition is skipped, and
  `@Name(value)` runs as `(value)`.
- **A check tests the value's storage type only.** `logical`, `integer`, `double`, `complex`,
  `character`, `raw`, and `NULL` admit values of that type, and each numeric type also admits the
  types below it in the promotion order, as the checker does. A list type admits any list, a
  function type any function, and a union any of its members. Vector shape, element types, and
  attributes are not checked, and a type the storage type cannot decide (an alias, a class, a type
  parameter, `Any`, `data.frame`) is not checked at all. A check therefore fails only on a value that really does not
  have the annotated type.
- **A function with no parameters whose body is a constant or a bare name is not checked**, because
  it has no language object to carry its signature.

A failed check is an ordinary R error, so `tryCatch()` and `try()` handle it. A parameter whose
check failed stays unevaluated, as it would after an error while computing it, so code that catches
the error and uses the parameter again computes it again and checks it again.

The checks belong to the function definition that carried the annotations. A closure built from
another function's `formals()` with a body of its own, as `rlang::new_function()` builds one, is a
new definition and is not checked.

Before running anything, `ry run` and `ry R` check the script and their console checks each command, with the
project's `ry.toml`. They print every `annotation-mismatch` and `inline-annotation` warning. In
[strict mode](/type-checking/strict-mode) they also print every error and refuse to run code that
has one: a script exits with status 1, and the console drops the command. Other findings are left
to `ry check`, so they never change whether R code runs.

## Types

### Atomic names

Types use R's own names: `logical`, `integer`, `double`, `complex`, `character`, `raw`, and `NULL`.
The names from other languages, such as `bool`, `int`, `float`, and `string`, are not accepted.

### Reserved constants

- `TRUE` and `FALSE` are `logical`.
- `NA` is `logical`, while `NA_integer_`, `NA_real_`, `NA_complex_`, and `NA_character_` are
  `integer`, `double`, `complex`, and `character`.
- `Inf` and `NaN` are `double`.
- An imaginary literal such as `1i` is `complex`.
- `NULL` is `NULL`.

### Vector shapes

Every atomic vector type comes in three shapes, written with a suffix on the atomic name:

```r
1L                  # integer: scalar-like, a vector of length one
c(1L, 2L)           # integer[]: array-like, a vector of unknown length
c(a = 1L, b = 2L)   # integer[named]: map-like, keyed by names
```

#### Vector coercions

- A scalar-like `T` coerces to an array-like `T[]`.
- A map-like `T[named]` coerces to an array-like `T[]`.
- An atomic type coerces up R's promotion order, `logical` < `integer` < `double` < `complex`, in
  every shape. That covers `logical` to `integer`, `integer[]` to `double[]`, `double[named]` to
  `complex[named]`, and compositions such as a scalar `integer` to `double[]`. The reverse never
  holds. `character` and `raw` are not part of the order, because R reaches `character` only through
  an explicit conversion.
- No other coercion between vector types is allowed unless a rule elsewhere on this page states it
  explicitly.

### List shapes

R has one list type, but programs use it in four roles, and the type system gives each role its own
type, because each role allows different checks:

- **tuple-like**, `list{T1, T2, ...}`: no names, a fixed number of positions, each with its own type.
- **list-like**, `list[T]`: no names, any length, one element type.
- **record-like**, `list{name: T, ...}`: named fields, a fixed set of them, each with its own type.
- **dict-like**, `list[named: T]`: names, any length, one element type.

The tuple-like and record-like shapes have a *fixed shape*: their positions or field names are part
of the type. The list-like and dict-like shapes are homogeneous collections, so no particular
position or name is part of the type. They mostly come from annotations and from coercing a
fixed-shape list.

A `list(...)` expression infers a fixed shape whenever its elements allow one:

- When all elements are unnamed, it is tuple-like, even when they share a type: `list()` is
  `list{}`, `list(1L, 2L, 3L)` is `list{integer, integer, integer}`, and `list(1L, "foo")` is
  `list{integer, character}`.
- When all elements are named and the names are known statically, it is record-like:
  `list(foo = 1L, bar = "foo")` is `list{foo: integer, bar: character}`.
- When named and unnamed elements are mixed, the names are dropped and it is list-like, so
  `list(1L, bar = "foo")` is `list[integer | character]`.
- When an argument is the enclosing function's `...`, the number and names of the elements are not
  known, so `list(...)` is `list[named: Unknown]`. Any field may be present, so reading or writing
  `dots$environment` is not reported. A list whose elements are not known at all, such as
  `as.list(environment())`, likewise says nothing about its names: `$` on a `list[Any]` or
  `list[Unknown]` reads `Any` or `Unknown` without an error.

R lets a list name be any string. A field name that is not a syntactic R name is written, and
rendered, in backticks, so `list(\`max size\` = 10L)` has the type `` list{`max size`: integer} ``.

#### List coercions

- Any list coerces to a list-like `list[T]` when every element is compatible with `T`.
- A record-like or dict-like list coerces to a dict-like `list[named: T]` when every value is
  compatible with `T`.
- When `T` is still open, it becomes the union of the element types, so `lapply(list(1L, "a"), f)`
  passes `integer | character`.
- The reverse is never allowed: a `list[T]` does not coerce back into a tuple-like, record-like, or
  dict-like list, and a `list[named: T]` does not coerce back into a record-like one.

Two records are compatible when they declare the same field names and each field's type is
compatible with the field of the same name on the other side. Fields pair by name, so their order
does not matter: `list(label = "a", id = 1L)` satisfies `list{id: integer, label: character}`.

When a record is rejected, the finding names the one field that failed rather than printing both
whole types: a field both sides declare whose types do not fit, a field the expected type declares
that the value lacks, or a field the value has that the expected type does not declare. For a nested
record, the finding names the path, outermost field first, as in `retry.count`.

#### The empty list

`list()` is the empty tuple `list{}`. It has no element whose type or name could conflict, so it is
compatible with `list[T]` and `list[named: T]` alike, which makes `function(options = list())` a
usable default for a `list[named: T]` parameter. A record type with required fields still rejects
it, because those fields really are missing.

Code starts from `list()` and fills it later far more often than it reads from a list it knows is
empty, so any element read from `list{}` is `Unknown`: `out <- list(); out[[1]]` and
`opts <- list(); opts$force` are not reported. Inside a union, an empty-list member contributes
`NULL` to a field read instead, as [`$` on a union](#indexing) describes.

### `NULL`

The literal `NULL` has the type `NULL`, which is the unit type of this type system and is
incompatible with every other type. An empty block is also `NULL`.

### `Any` and `Unknown`

`Any` and `Unknown` are both compatible with every type, in both directions. They differ in where
they come from, and therefore in what they mean.

`Any` is an explicit opt-out from type checking. It comes from an annotation you wrote or from a
standard-library declaration. The shipped declarations use it where any precise type would reject
calls R accepts, so seeing `Any` in a hover is not by itself a sign of a problem.

`Unknown` means the checker could not work out a more specific type, because of an unsupported or
partly supported construct, an unresolved name, or too little information. It is not an opt-out: it
records a gap in the checker's knowledge, and a value of that type flows into a `double` parameter
without complaint.

The difference in intent shows in two places. [`@if-unknown`](#unknown-only-coercions) supplies a
type where one is missing, so it applies to an `Unknown` and is refused on an `Any`, which already
says not to check the value. [Strict mode](#strict-mode) reports where an `Unknown` arose, and treats
an `Any` as an intentional opt-out.

### Type parameters, aliases, and nominal types

A type expression can bind type parameters with a leading binder, written `<T> TYPE` or
`<T, U> TYPE`:

- `<T> list[T]`
- `<T> list{ value: T }`
- `<T, U> fn(T) -> U`
- `<T> fn(T) -> T | NULL`

A type parameter may appear inside a structural type, a function type, and the vector suffix forms:
`list[T]`, `list{ value: T }`, `fn(T) -> T`, `T | NULL`, `T[]`, and `T[named]`.

Binders are rank-1: a binder is allowed only at the outermost level of a type expression, never
nested inside another type, and never inside parentheses. A directive's `{...}` payload does not
count as the outermost level, so the expanded form declares its type parameters with `@forall`, and
a named type declares them on its name, as in `@type Pair<T>`. All three of these are refused:

- `fn(f: <T> fn(T) -> T) -> integer`
- `list{ value: <T> list[T] }`
- `@param f {<T> fn(T) -> T}`

A refused binder is reported once. The type is then read as though the binder had not been written,
and the block carries no typing payload.

#### Constraints

A binder name may carry a constraint, written `NAME: CONSTRAINT`, as in
`<T: numeric> fn(values: T) -> T`. These are the constraints:

- `numeric` admits `integer` and `double`, scalar or vector, and any class that declares an
  arithmetic [operator method](#operator-methods-on-a-class).
- `atomic` admits one of the six atomic scalar types: `logical`, `integer`, `double`, `complex`,
  `character`, and `raw`.
- `key` admits a scalar `logical`, `integer`, `double` or `character`, the types a dictionary key
  or set element may have. `complex` and `raw` are left out.
- `scalar numeric` admits a scalar `integer` or `double`, which is both bounds at once. It is what an
  endpoint of `:` infers, so `function(n) 1:n` is `<T: scalar numeric> fn(n: T) -> double[]`.
- `item` admits what an [Array](#arrays) can hold: a scalar `logical`, `integer`, `double` or
  `character`, or a ry value. `as.Array : <T: item> fn(x: list[T]) -> Array<T>` uses it.

Any other constraint name is an annotation error, and the error lists the ones that exist. An
argument whose type violates a constraint is a type error at the call.

A constraint limits what a caller may instantiate `T` with, and the annotated body may rely on it.
Under `<T: numeric> fn(x: T) -> T` the body may use `x` as a number. A body under a plain `<T>` that
does arithmetic is a type error, and `atomic` does not imply `numeric`.

Using a type parameter as a vector element, `T[]`, imposes the `atomic` bound, because a vector holds
only atomic elements. This is what makes element-preserving signatures possible. With
`keep : <T> fn(x: T[]) -> T[]`, `keep(c("b", "a"))` is `character[]` and `keep(c(1L))` is
`integer[]`, while a list argument cannot bind `T` at all. Several rules follow from the bound:

- A scalar argument coerces into a generic vector parameter and binds the element, so
  `<T> fn(x: T[])` called with `2.5` binds `T := double`.
- `[[` on a generic vector `T[]` extracts `T`.
- An arithmetic operator on a `T[]` operand also requires the element to be numeric, so the variable
  then holds both bounds. The result keeps the element, so `keep(x) + 1L` is still `T[]`, unless a
  `double` operand promotes the result to `double[]`.
- A comparison on a `T[]` operand yields `logical[]` and constrains nothing beyond the bound.

A bound that can no longer be satisfied is a type error at the expression that imposed it, whether
that means binding an element variable to a type that is not atomic or requiring a `character`
element to be numeric.

Writing `X[]` is an error when `X` is neither an atomic type nor a type parameter. Records,
functions, and nominal types are all such an `X`, and `list[X]` is how to write a list of them. An
alias expands first, so `Id[]` with `@alias Id {integer}` is fine, while an alias of a record is
refused.

#### Named types and generic application

Named types are declared with `@type` and `@alias`, and either may take parameters, as in
`NAME<T, U>`:

- `type NAME = TYPE`, or `#: @type NAME {TYPE}`, declares a *nominal type* whose representation is
  `TYPE`.
- `alias NAME = TYPE`, or `#: @alias NAME {TYPE}`, declares a *structural alias* for `TYPE`.

The two forms share one namespace, so reusing a name under either form is an error, except for a
`#:` definition paired with the inline one directly below it
([inline and comment annotations together](#inline-and-comment-annotations-together)). A definition
is allowed only at the top level of a file. Definitions are project-global, so a reference need
not come after the declaration; [type names](#type-names) has the scoping rules.

The declared type parameters are in scope only within `TYPE`, where they shadow any project-global
type of the same name. A type parameter is not itself a generic, so applying type arguments to one,
as in `Wrap<integer>` where `Wrap` is a parameter, is an annotation error rather than a reference to
the shadowed global.

A named generic is applied with angle brackets, as in `Box<integer>`, and the application must match
the declaration's arity:

- Applying the wrong number of type arguments is an error at the applied name. For `Pair<T, U>`,
  `Pair<integer, character>` is valid, while `Pair<integer>` and `Pair<integer, character, double>`
  are errors.
- Applying type arguments to a declaration that is not generic, such as `Meters<integer>`, is an
  error.
- A bare reference to a generic, such as `Box` without arguments, is an error everywhere except after
  [`@new`](#nominal-introduction).
- A wrongly applied name then compares like `Unknown`, so the one arity error never cascades into
  mismatches between values.

#### Type aliases

An alias is purely structural: writing its name is the same as writing the type it stands for. It
creates no new identity, and may appear anywhere a type may, including inside a larger type. Using
an alias that expands in a cycle is an error, reported where it is used; a cycle no annotation uses
is not reported.

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
alias Box<T> = list{ value: T }

value: Box<integer> <- list(value = 1L)
```

</TabItem>
<TabItem label="Comments">

```r
#: @alias Box<T> {list{ value: T }}

#: Box<integer>
value <- list(value = 1L)
```

</TabItem>
</Tabs>

#### Nominal types

A nominal type creates a fresh type identity, even when another nominal type has exactly the same
representation. Its name may appear anywhere a type expression may.

- A nominal type is compatible with itself.
- Two different nominal types are not compatible with each other, even when their representations
  are identical.
- A structural value is not compatible with a nominal type unless [`@new`](#nominal-introduction)
  introduces it.
- A value of a nominal type *is* compatible with its representation type, so it can be passed to any
  function written for the representation, while `@new` stays the only place the type's invariant is
  established.
- When an operator, an indexing form, or a loop needs a structural shape, a nominal value projects to
  its representation type. The result of the projection is structural, not nominal.

In this example, `Person` and `Pet` are distinct and incompatible. The annotation on `shape` is valid
because a nominal value satisfies its representation, and the final call is an error because a
structural value does not satisfy the nominal type:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
type Person = list{ name: character, age: double }
type Pet = list{ name: character, age: double }

person <- @Person(list(name = "bob", age = 20))

shape: list{ name: character, age: double } <- person

get_name <- function(value: Person) -> character value$name

get_name(list(name = "bob", age = 20))
```

</TabItem>
<TabItem label="Comments">

```r
#: @type Person {list{ name: character, age: double }}
#: @type Pet {list{ name: character, age: double }}

#: @new Person
person <- list(name = "bob", age = 20)

#: list{ name: character, age: double }
shape <- person

#: fn(value: Person) -> character
get_name <- function(value) value$name

get_name(list(name = "bob", age = 20))
```

</TabItem>
</Tabs>

Projection is what makes field access and arithmetic work on a nominal value. In `get_name`,
`value$name` is `character` because `$` sees the representation. With `@type Meters {double}`,
`height + height` is `double`: arithmetic projects `Meters` to `double`, and the result does not keep
the nominal identity.

##### Opaque nominal types

An *opaque* nominal type has no representation to project. The standard-library stubs declare
`data.frame`, `factor`, `connection`, `Date`, and other types the grammar cannot describe
structurally as a bare `@type NAME` (see [stubs](/type-checking/stubs)). For these types:

- `$`, `[`, and `[[` are accepted and give `Unknown`, because the R objects behind these classes
  commonly support access that depends on values, such as `df$amount` and `df[rows, ]`.
- The access is not checked further: there is no field-existence, index-count, or index-type check.
- Every such access is an unsupported construct under [strict mode](#strict-mode).
- Arithmetic and every other structural requirement remain type errors, unless the class declares
  the matching [operator method](#operator-methods-on-a-class). The nominal identity itself checks
  like any other nominal type.

#### Type-argument variance

Two applications of the same generic nominal type, such as `Box<integer>` and `Box<integer | NULL>`,
are compared one type argument at a time. Each parameter's *variance* follows from where it occurs
in the representation:

- **Covariant** positions keep the checking direction. They are a function's return, a direct
  occurrence, and an element of a container or structural type (a `list` item, a `list{...}` field,
  a tuple item, a vector element, or a union member). So `Box<integer>` is accepted where
  `Box<integer | NULL>` is expected.
- A function **parameter** position is contravariant and flips the direction. Given
  `@type Handler<T> {fn(value: T) -> NULL}`, a `Handler<integer | NULL>` is accepted where a
  `Handler<integer>` is expected, but not the other way around, because then a `NULL` could reach a
  function that only accepts `integer`.
- A parameter that occurs in both kinds of position is **invariant**, and its arguments must match
  exactly. Given `@type Cell<T> {list{ get: T, set: fn(value: T) -> NULL }}`, `Cell<integer>` and
  `Cell<integer | NULL>` are incompatible in both directions.
- A parameter that does not occur at all constrains nothing, and accepts any argument.

A type parameter inside a nested generic application, such as the `T` of `Sink<T>` within
`@type Outer<T> {Sink<T>}`, is invariant: the inner type's own variance does not compose with the
outer direction. When a generic nominal has no visible definition, every argument is checked
invariantly, which errs toward rejecting rather than toward accepting an unsound widening.

R's lists and vectors are mutable, yet their element positions are treated as covariant. A sound
mutable container would have to be invariant, which would break structural coercions such as scalar
to vector and `T` into `T | NULL`.

### Union types

A union type `A | B | ...` describes a value that has one of the member types. It may have any number
of members, any type may be a member, and it can be written anywhere a type can. `T | NULL` is the
nullable form of `T`. A union records the shapes a value can take without merging or coercing its
members:

- `integer | character`
- `character[] | NULL`
- `fn(count: integer | NULL) -> character | logical | NULL`
- `(fn() -> integer) | NULL`, a function returning `integer`, or `NULL`

A type may be parenthesized for grouping, where `(TYPE)` means exactly `TYPE`. In
`fn() -> integer | NULL` the `->` extends over the whole union, so an optional callback has to be
written `(fn() -> integer) | NULL`, which is also how it renders.

#### Union normalization

Unions are kept in one normal form, so equivalent spellings mean the same type and render the same
way. Every union, written or inferred, is normalized:

- A member that is itself a union is flattened, so `(A | B) | C` becomes `A | B | C`.
- Repeated members collapse, keeping the first, so `integer | character | integer` becomes
  `integer | character`.
- Member order does not affect meaning. Rendering keeps first-occurrence order, except that `NULL`
  always renders last.
- A union whose members collapse to one type is that type, so `integer | integer` is `integer`.
- A union with an `Any` member is `Any`, because every value already satisfies `Any`.
- Otherwise, a union with an `Unknown` member is `Unknown`.

A call's result drops a union member that is a type parameter of the called function when the
callee's parameters mention it only as what a callback returns and the call left it unconstrained,
because the callback then never produces such a value. `Result.and_then` returns
`Result<B, E | F>`, where `F` is the error type of the step, so a step that never fails leaves `F`
unconstrained and the result keeps the error `E` alone:

```r
a <- Result.and_then(Str.to_integer("1"), function(n) :Ok(n))
# :Ok(integer) | :Err(:InvalidNumStr)
b <- Result.and_then(Str.to_integer("1"), function(n) if (n > 0L) :Ok(n) else :Err(:NotPositive))
# :Ok(integer) | :Err(:InvalidNumStr | :NotPositive)
```

A union made only of such parameters stays as it is. A type parameter that an argument fills
directly, or that appears only in the result (`<T> fn(name: character) -> T | NULL`), is kept,
because there an open `T` means any value. So is one that code outside the call still reaches,
such as an unannotated parameter passed as the callback:
`function(r, step) Result.and_then(r, step)` returns `:Ok(V) | :Err(U | W)`.

### Union compatibility

A value fits an expected union when it fits any one member, with the usual coercions applied per
member. So `integer` fits `integer | character | NULL`, and `NULL` fits any union that contains
`NULL`. Members are tried in order, and a failed attempt leaks no bindings into the next one.

A union *value* has to be acceptable in every shape it can take, so it fits an expected type only
when every one of its members does. A union therefore fits any wider union (`integer | NULL` fits
`integer | character | NULL`), but not a single member type: `integer | character` does not fit
`integer`, and `T | NULL` does not fit plain `T`.

An unannotated value checked against an expected union binds to the whole union at its first use.
Uses commit in program order, so a later use that needs a different type is reported at that later
site. When two union-typed contracts share only some members, such as `integer | character` at one
call and `logical | character` at the next, the checker does not compute their intersection; annotate
the value with the member type you intend.

## Records, tuples and tags

Records, tuples and tags are ry's own values, not R lists. The user guide is
[Records and tags](/type-checking/records-and-tags/); this section is their typing contract. They are
inline syntax, so with `[check] inline-annotations = false` each literal, tag or `match` is reported
as a `ry-syntax` warning. Literals are still typed then, but a `match` gets no coverage check. Their types may be written in `#:` comments
either way.

### Record and tuple types

| Literal | Type |
| --- | --- |
| `(x = 1, y = 2)` | `Record{x: double, y: double}` |
| `(1L, "a")` | `Tuple{integer, character}` |
| `(x = 1,)` | `Record{x: double}` |
| `(1L,)` | `Tuple{integer}` |
| `()` | `Tuple{}` |

A one-field record and a one-item tuple need the trailing comma, because `(x = 1)` and `(x)` keep
their R meaning. A literal is all fields or all items, and a repeated field name is an error.

- A record's fields are all required. Field order is part of neither its identity nor its type, so
  `Record{x: double, y: double}` and `Record{y: double, x: double}` are the same type.
- A record and a list are different types: `Record{x: double}` does not fit `list{x: double}`, and
  the reverse does not fit either.
- `point$x` and `point[["x"]]` type as the field's type, and a field the record lacks is a
  `type-mismatch`. `pair[[1L]]` with a literal index types as that item, and an index past the end
  is a `type-mismatch`. On a record, a position counts the fields in their sorted order. A computed
  index types as the union of the item or field types.
- `point$x <- value` and `point[["x"]] <- value` rebind `point` to a copy with that field replaced,
  and the record keeps its type. The value must be compatible with the field's type, and a field the
  record lacks is a `type-mismatch`, because a record's fields are fixed.

### Tag types

A tag's type is written the way its value is, with types in place of values: `:None` has type
`:None`, `:Some(5L)` has type `:Some(integer)`, and `:Rect(width = 2, height = 3)` has type
`:Rect(width: double, height: double)`. Tags are structural and need no declaration.

A *tag union* is an ordinary [union](#union-types), so the union rules apply unchanged: a tag value
fits a union that lists a tag of the same name with a compatible payload, and an `if` whose branches
build different tags types as their union. Normalization merges two members with the same tag name
and payload shape into one member whose payloads are joined position by position, so joining
`:Some(1L)` with `:Some("a")` gives `:Some(integer | character)`. Two members with the same name and
a different payload shape are a `type-mismatch` where they meet.

A union that lists `..` as a member is *open*: it also holds every tag it does not list.

- A tag value fits an open union when the union lists its name with a compatible payload, or does
  not list its name at all.
- A closed union fits an open one when each of its members does.
- An open union never fits a closed union. It fits another open union only when every tag the
  target lists is also listed by the source, with a compatible payload.

There are no row variables, so a function cannot pass the unlisted tags of an open union through
with their types. Generic tag unions come from aliases, such as
`#: @alias Option<T> {:Some(T) | :None}`. One is built in: the
[standard library](/reference/standard-library/) defines `Result<T, E>` as `{:Ok(T) | :Err(E)}`, and a
project's own `Result` alias shadows it.

### Nominal records, tuples and tags

A record, tuple or tag union may be the representation of a [nominal type](#nominal-types), as in
`type Shape = :Circle(radius: double) | :Square(side: double)`. The nominal rules apply unchanged, so
a structural value with the right shape, such as a bare `:Circle(radius = 1)`, does not fit `Shape`,
and only [`@Shape(...)`](#nominal-introduction) or `#: @new Shape` creates one. Wherever a rule of
this section needs the value's shape, the nominal value projects to its representation:

- `$`, `[[` and field writes follow the record and tuple rules above. A field write keeps the
  nominal type, its value must fit the field's type, and a field the representation lacks is a
  `type-mismatch`.
- A `match` checks its patterns and its [coverage](#exhaustiveness) against the representation, so a
  nominal tag union, including a recursive generic one such as
  `type Tree<T> = :Leaf | :Node(left: Tree<T>, value: T, right: Tree<T>)`, must be matched
  exhaustively.
- A binding pattern binds the value with its nominal type, and a payload binding has the payload's
  declared type, so `:Node(left = l, ..)` on a `Tree<integer>` binds `l` as a `Tree<integer>`.
- A nominal value whose representation is a record, tuple or tag is still a ry value when it
  [crosses into R](#crossing-into-r).

### `match`

`match (EXPR) { ARMS }` is a `match` expression only when the `{` is on the line of the closing `)`,
so every R use of `base::match` keeps its meaning. An arm is `PATTERN => EXPR` or
`PATTERN if (CONDITION) => EXPR`, separated by newlines, `;` or `,`.

| Pattern | Matches |
| --- | --- |
| `_` | anything, binding nothing |
| `name` | anything, binding it to `name` |
| `1L`, `"a"`, `TRUE`, `NA`, `NULL`, `-1` | a length-one value equal to the literal |
| `:Tag`, `:Tag(p1, p2)`, `:Tag(field = p)` | a tag with that name whose payload matches |
| `(p1, p2)`, `(p,)` | a tuple of that length whose items match |
| `(name = p, ..)`, `(name = p,)` | a record with those fields; without `..`, exactly those fields |
| `p1 \| p2` | either pattern; both sides must bind the same names |

The type of a `match` is the join of its arm types, as for `if`. A pattern that cannot match the
scrutinee's type, such as a tag a closed union does not list or a field the record lacks, is a
`type-mismatch` at the pattern. A scrutinee whose type is not yet known takes its shape from the
patterns: the arms' tags form a closed union. A catch-all arm accepts a value of any type, so with
one the scrutinee is not shaped by the patterns. Pattern
names are bound in the current environment, so after the `match` a name that only some arms bind
types like a variable assigned in only some branches of an `if`.

### Exhaustiveness

When the scrutinee's type is known, the arms must cover every value of it. Coverage is computed over
the cases the type has:

- a closed tag union has one case per tag, and an open union adds an "other tags" case that only a
  catch-all arm covers;
- a tuple or a record is one case, with its items or fields checked in turn;
- a scalar `logical` has three cases, `TRUE`, `FALSE` and `NA`. Coverage trusts the scalar claim,
  so a value typed scalar that holds several elements, such as `v[-1L]` (see
  [`[` on vectors](#-on-vectors-1)), matches no literal arm and stops with an error when the code
  runs;
- `NULL` is one case, and a union has the cases of each member;
- a nominal type has the cases of its representation;
- every other type has unboundedly many values, so only a binding or `_` covers it.

A guarded arm never counts toward coverage, because its guard can be false. A `match` that misses a
case is a `non-exhaustive-match` error naming up to three missing cases as patterns, and an arm that
the arms above it already cover is an `unreachable-pattern` warning.

### Crossing into R

R functions and C code do not know these values. `as.list()` converts a record, tuple or tag to a
list, and `as.record()`, `as.tuple()` and `as.tag()` convert back.

Passing one to an R function that is not the project's own is a `type-mismatch` at the argument. The
exceptions are the functions the runtime lets them through: those that understand them (`format`,
`print`, `identical`, `length`, `[[`, the conversions), those that only ask what a value is
(`is.null`, `class`, `inherits`), and those that store a value without looking inside it (`list`,
`lapply`, `do.call`). A value whose type only sometimes is a record, tuple or tag, such as
`Record{x: double} | NULL`, is not reported, because it may be R data when the code runs.

## Arrays

An Array is ry's strict typed vector. The user guide is [Arrays](/type-checking/arrays/); this
section is its typing contract. The `[...]` literal is inline syntax, so with
`[check] inline-annotations = false` each literal is a `ry-syntax` warning, and it is still typed.
The type `Array<T>` may be written in `#:` comments either way.

### Array literals

`[a, b, c]` types as `Array<T>`, where `T` is the type of the first item. Every other item must have
exactly that type: items are never converted into each other, so `[1L, 2.5]` is a `type-mismatch` at
`2.5`. The one exception is tags, whose types join into a tag union, so `[:Ok(1), :Err("no")]` is an
`Array<:Ok(double) | :Err(character)>`.

An item is a scalar-like `logical`, `integer`, `double` or `character`, or a ry value: a record,
tuple, tag, dictionary, set or another Array. Any other item type is a `type-mismatch`, and so is the
literal `NA`. A type does not say whether a value is missing, so an item computed by R code may still
be `NA`, and the constructor stops with an error on it when the code runs. It also checks that atomic
items share one type; that ry values share one type is checked only by the checker. In an annotation, `Array<T>` with any other `T`,
such as `Array<double[]>` or `Array<double | NULL>`, is an `annotation` error.

The empty literal `[]` takes its item type from an annotation, as in `#: Array<character>`, or else
is `Array<Unknown>` until a use such as `List.append(xs, 1L)` gives it one.

### Arrays and R vectors

- `Array<T>` fits `T[]` when `T` is atomic, and `list[T]` when `T` is a ry value, so an Array passes
  to any R function that takes a vector or a list.
- A plain R vector never fits `Array<T>`. `as.Array(x)` converts one: a `T[]` gives `Array<T>`, and a
  `list[T]` gives `Array<T>` when `T` is a ry value (the `item` constraint).
- At run time `as.Array()` stops with an error on an `NA` or a classed object, and drops names.
  Setting any attribute on an Array turns it into a plain R vector.

### Array operators

An elementwise operator takes two Arrays with the same item type, or an Array and a scalar-like value
of the item type. `integer` and `double` never mix, and an R vector operand is a `type-mismatch`
whose message suggests `as.Array()`.

| Operator | Items | Result |
| --- | --- | --- |
| `+ - * %% %/%`, unary `-` | `integer` or `double` | `Array<T>` |
| `/ ^` | `integer` or `double` | `Array<double>` |
| `== != < > <= >=` | atomic | `Array<logical>` |
| `& \| !` | `logical` | `Array<logical>` |

When the code runs, two Arrays of different lengths are an error rather than recycled, and a result
that holds `NA` or `NaN`, such as an integer overflow, is an error. An operator on Arrays of ry
values is an error.

### Array indexing

- `xs[[i]]` takes one `integer` or `double` position and types as `T`.
- `xs[i]` takes positions, a `logical` mask, or no index, and types as `Array<T>`.
- A `character` index, or more than one index, is a `type-mismatch`, because an Array has one
  dimension and no names.
- When the code runs, positions follow R where R gives no `NA`: a negative position leaves an item
  out and a zero selects nothing. A position past the end, an `NA` position, or a mask of a different
  length is an error, never `NA`.
- A replacement through `[<-` or `[[<-` must be an item of the item type, or for `[<-` an Array of
  them with one item per position, which is never recycled. When the code runs, a position past the
  end or an Array of the wrong length is an error. A replacement that is not an item of the item
  type, such as `NA` or an R vector, is a `type-mismatch` in checked code; when R code does it, as
  base `ifelse()` does with its `test` argument, the result is the plain R vector R would build.

`for (x in xs)` binds `x` as `T`. Every `List` function of the
[standard library](/reference/standard-library/) that takes a collection has an Array overload, so
`List.map` on an `Array<T>` returns an Array and `List.len` returns its length.

## Function types

A function can be annotated in one of two styles, but not both at once:

- the **expanded** style, with an optional `@forall`, then `@param` lines, then `@return` or
  `@returns`;
- the **compact** style, a single `fn(...)` type with an optional `-> RETURN_TYPE`.

Either way, consecutive `#:` lines form one annotation block for the function.

### Expanded function annotations

The expanded form puts one directive on each line: `@forall` to declare type parameters,
`@param name {TYPE}` for each parameter (or `@param [name] {TYPE}` for an optional one), and
`@return {TYPE}` or `@returns {TYPE}` for the result. A constrained binder is written
`@forall T: numeric`, with the same meaning as the compact `<T: numeric>`.

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
double_count <- function(count: integer, label: character | NULL = NULL) -> integer {
  count + count
}

then_some <- function<T>(condition: logical, value: T) -> T | NULL {
  if (condition) value
}
```

</TabItem>
<TabItem label="Comments">

```r
#: @param count {integer}
#: @param [label] {character | NULL}
#: @return {integer}
double_count <- function(count, label = NULL) { count + count }

#: @forall T
#: @param condition {logical}
#: @param value {T}
#: @return {T | NULL}
then_some <- function(condition, value) {
  if (condition) value
}
```

</TabItem>
</Tabs>

- Directives come in order: every `@forall` before any `@param`, and every `@param` before `@return`
  or `@returns`.
- Repeated `@forall` lines accumulate in source order, and a duplicate type parameter name is an
  error.
- At most one `@return` or `@returns` may appear. Without one, the return type is
  [elided](#elided-return-types).

### Compact function annotations

A compact annotation is a single function type, in one of these forms:

- `fn(name: TYPE) -> RETURN_TYPE`
- `fn(TYPE) -> RETURN_TYPE`
- `fn(name: TYPE, [optional_name]: TYPE) -> RETURN_TYPE`
- `<T> fn(name: TYPE) -> RETURN_TYPE`
- `<T, U, ...> fn(TYPE) -> RETURN_TYPE`

A leading `<...>` binder introduces [rank-1](#type-parameters-aliases-and-nominal-types) type
parameters for the whole function type. The binder always comes first: `fn<T>(...)` is not the
syntax. An optional parameter must be named, as in `[name]: TYPE`; a bare optional positional form
such as `fn(integer, [character])` is not supported. Omitting the return type
[elides](#elided-return-types) it.

A function may declare one rest parameter to accept a variable number of arguments. It is written
`...: TYPE`, and `fn(...)` is shorthand for `...: Any`. It has no name, because rest arguments are
matched by position, so `...items: TYPE` does not match the function's `...` and is reported, twice
at the same range: as a signature mismatch and as a parameter the function does not define. It can
come after the fixed parameters, as in `fn(prefix: TYPE, ...: TYPE) -> RETURN_TYPE`, or before named
ones, as in `fn(...: TYPE, [option]: TYPE) -> RETURN_TYPE`:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
join <- function(...: character) -> character paste0(...)

wrap <- function(x: character, ...: character) -> character {
  paste0(x, ": ", paste(...))
}
```

</TabItem>
<TabItem label="Comments">

```r
#: fn(...: character) -> character
join <- function(...) paste0(...)

#: fn(x: character, ...: character) -> character
wrap <- function(x, ...) paste0(x, ": ", paste(...))
```

</TabItem>
</Tabs>

The position of the rest parameter, counted as the number of parameters declared before it, is part
of the signature. It must match the position of `...` in the function's formals, and it decides which
parameters a positional argument can fill (see [function calls](#function-calls) and
[function type compatibility](#function-type-compatibility)).

### Annotations and the formal list

An annotation declares the *types* of a definition's parameters, not the parameter *list*. R matches
a call's arguments against the formals in the `function(...)` header, so those formals are the call
interface: their names, their order, their defaults, and where `...` sits. An annotation cannot add,
remove, or reorder them. A parameter the annotation does not mention keeps its inferred type, which
makes annotating just one of several parameters a supported partial form.

When the declared shape disagrees with the definition, the definition wins at every call site, and
the disagreement is reported once, at the definition, so a call is never blamed for a mistake in an
annotation. The possible disagreements are:

- a declared parameter name that is not one of the formals (an annotation may not rename a
  parameter, so `fn(count: integer) -> integer` over `function(n) n` is an error);
- more declared parameter types than there are formals left to receive them;
- a declared optional `[name]` over a formal that callers may not omit (one with no default that
  the body [may force](#lazy-arguments-and-required-formals)), because declaring a parameter
  optional tells callers they may omit it;
- a parameter declared as required over a formal that has a default, because R lets callers omit it,
  so the annotation must say `[name]`;
- a rest parameter at a different position in the annotation than in the formals, or present on only
  one side, so a fixed annotation on a variadic function and a variadic annotation on a fixed
  function are both rejected.

The first case and a required declaration over a defaulted formal name the parameter. The others are
reported as a mismatch of the whole signature. In every case, the body is still checked under the
parameter types the annotation does pin down, so hover and navigation keep their facts.

### Elided return types

Both styles allow the return type to be left out: an expanded block without `@return` or `@returns`,
or a compact `fn(...)` without `-> RETURN_TYPE`. An elided return is not the same as a written
`NULL`, and what it means depends on whether there is a function body to infer from:

- On a checked annotation of a `function(...)` literal, the return type is inferred from the body,
  exactly as if there were no annotation, so annotating only the parameters never pins the return.
  `@param u {integer}` on `add_one <- function(u) u + 1L` infers `fn(u: integer) -> integer`. Writing
  the return as `Unknown` has the same effect, because `Unknown` never overrides what the body shows.
- In a nested function type, such as a callback parameter written `@param cb {fn(integer)}`, the
  elided return means `NULL`, which matches R functions called for their side effects.
- In a [trusted coercion](#trusted-coercions), and in an annotation on a value that is not a function
  literal, such as `#: fn(integer)` on `g <- f`, the elided return is `Unknown`, so a call's result
  goes unchecked even when `f`'s return type is known. This is a known gap.

A function that really does return `NULL` can say so with `@returns {NULL}` or `-> NULL`. The
explicit form is enforced, so a body that returns anything else is then a type error.

### Inferred function types

An unannotated `function(...)` expression gets its type from the definition itself:

- Every parameter appears as a named parameter under its name in the definition, because R matches
  parameters both by name and by position.
- A parameter with a default is optional at call sites, and so is one the body never forces, as
  [lazy arguments](#lazy-arguments-and-required-formals) describes.
- A `...` formal becomes a rest parameter with element type `Any`, at the position it holds among the
  formals, so `function(x, ...) …` is `fn(x: T, ...: Any) -> …`. The values that reach `...` are not
  tracked into the body, so forwarding `...` to another call gives `Unknown`.
- Parameter and return types are inferred, and a parameter nothing constrains generalizes when the
  function is bound to a name, so `function(x) x` is `<T> fn(x: T) -> T`.
- A requirement inference could not discharge survives into the exported type: a parameter used as a
  number exports as `<T: numeric>`, so calls from other files keep being checked.

`function(count, label = NULL) count` may therefore be called as `f(1L)`, `f(count = 1L)`, or
`f(1L, "x")`.

#### Defaults

Defaults are type-checked, and they interact with the parameter's type in four ways:

- An error inside a default is reported, and the default of an annotated parameter must be
  compatible with the declared type.
- A `NULL` default is checked like any other. `function(title = NULL)` is R's usual way to write an
  optional argument, but when the caller omits it, `title` is `NULL` inside the body, so declaring it
  `character` is a promise the function does not keep. Declare `character | NULL` and narrow with
  `if (is.null(title))`. Marking the parameter `[title]` relaxes only the call.
- An unannotated parameter takes its type from its uses, not from its default, so
  `function(x = 1) x` is `<T> fn([x]: T) -> T`, and passing a character is not a finding.
- A call that omits the argument gets the default's type, because that is the value R puts in the
  frame: with `f <- function(x = 1) x`, `f()` is a `double` and `f("a")` is a `character`. A default
  is therefore checked against an *instantiation* of the declared type rather than against the
  binder, so `#: <T> fn([x]: T) -> T` over `function(x = 1) x` is accepted. A concrete declared type
  is unaffected: `fn(title: character)` still refuses a `NULL` default.
- An inferred parameter type always admits the default's type, because a call that passes the
  default's own value is always fine. When the body settles an unannotated parameter on a type the
  default does not have, the exported type is widened by the default's: with `up` declared
  `fn(x: character) -> character`, `function(s = NULL) up(s)` is
  `fn([s]: character | NULL) -> character`.

An `if` without `else` that writes a formal under a test reading that same formal *normalizes* the
input, as in `if (is.logical(type)) type <- if (type) "q" else "m"` or
`if (is.null(sep)) sep <- ","`. The write does not constrain the formal's own type, so callers may
still pass anything, and after the `if` the body sees the written type rather than a union with the
formal's type:

```r
to_double <- function(x = 1) {
  if (is.character(x)) x <- as.numeric(x)
  x
}
# to_double: <T> fn([x]: T) -> double
```

This is a deliberate approximation. A union with the open formal type would make every later use of
the value accept anything, while the normalized type is what the code after such a test assumes. A
`NULL` write is not a normalization and joins as an ordinary branch write.

### Function literals in call arguments

A function literal passed as a call argument takes its parameter types from the function type the
callee expects at that position. The other arguments are checked first, so the callee's type
parameters are already bound when the literal's body is inferred:

```r
xs <- [1, 2]
pairs <- List.map(xs, \(x) c(x, x))
# error: this function must return an Array item (...), but it returns `double[]`
```

`List.map` expects `fn(T) -> U` with `T` bound to `double` by `xs`, so `x` is `double` inside the
body, `c(x, x)` is `double[]`, and the `item` constraint on `U` refuses it. Without the expected
type, `x` would be an open variable and `c(x, x)` could not be typed. The rule has these limits:

- It applies only to a literal written directly as the argument, with no `#:` or inline annotation
  on any of its formals. An annotated formal keeps its annotation, which is then checked against the
  expected type.
- Every formal without a default must receive a type, or none does. In
  `Reduce(function(a, b) a + b, xs)` the accumulator's type is still open when the literal is
  checked, so both formals stay open and are inferred from the body, as for any unannotated
  function. A formal with a default is always left to inference.
- With an overloaded callee, a formal takes a type only when every candidate that accepts the other
  arguments expects the same one. The overload is then chosen as usual, with the literal's inferred
  type among the arguments.
- A literal with a formal after `...` takes no types, because R binds positional arguments to
  `...` before any later formal.
- A parameter type that is `Any`, `Unknown` or still contains an open type variable gives no
  context.

When the body uses a parameter that took its type this way as an operand its type does not allow,
the finding is reported on that use and names the parameter. Other misuses, such as passing the
parameter to a function that expects another type, keep their usual wording:

```r
words <- ["a", "b"]
bad <- List.map(words, \(w) w * 2)
# error: `w` is used as a numeric value (`integer` or `double`) here, but the call passes this
# function `character` for it
```

### Named and positional parameters

Parameter names in a function type are part of the call interface. A named parameter may be passed
as a named argument, while an unnamed parameter is positional only. So `fn(count: integer) -> integer`
allows a call with `count = 1L`, while `fn(integer) -> integer` makes a named argument a type error,
but only when no definition stands behind the type. When the annotation sits on a `function(count)`
definition, the formals supply the name, and `f(count = 1L)` stays legal. An optional parameter
follows the same rule, and must be named.

Parameter, field, and type names may contain `.`, matching R's convention for names such as
`na.rm` and `length.out`: `fn(x: double, na.rm: logical) -> double`, `list{na.rm: logical}`, and
`@type My.Type {integer}` are all valid.

### Function type compatibility

A function value is compatible with an expected function type when its parameters accept every call
the expected type may make, and its return type satisfies the expected return type.

Parameters pair by name where the expected type names them, because R matches arguments against the
definition's formal names. So `fn(a: integer, b: character)` accepts a function defined as
`function(b, a)`. An unnamed parameter type pairs with the remaining parameters from left to right,
so `fn(count: integer) -> NULL` and `fn(integer) -> NULL` are compatible with each other.

Arity is a range, not a fixed count. The function may declare more parameters than the interface
passes, as long as the extra ones have defaults. It may not require more than the interface supplies,
and it may not refuse an argument the interface may send. An optional parameter in the expected type
promises callers they can omit it, so the function's formal must have a default.

Parameters are contravariant and the return type is covariant: each expected parameter type must be
compatible with the function's parameter type, and the function's return type must be compatible
with the expected one.

- `fn(integer | NULL) -> integer` is accepted where `fn(integer) -> integer` is expected.
- `fn(integer) -> integer` is rejected where `fn(integer | NULL) -> integer` is expected, because the
  interface may pass `NULL`.
- `fn(a: integer, [b]: integer) -> integer` is accepted where `fn(integer) -> integer` is expected,
  because `b` has a default. This is what lets a standard-library function serve as a callback:
  `lapply(list(mean, sd), function(g) g(1:3))` is `list[double]`, even though `mean` and `sd` declare
  optional formals the callback never passes.
- `fn(a: integer, b: integer) -> integer` is rejected there, because the interface never supplies `b`,
  and `fn() -> integer` is rejected because it cannot receive the argument the interface sends.
- `fn(count: integer, [label]: character) -> integer` does not accept `function(count, label) count`
  in a checked annotation, because `label` has no default. At an argument position this is not yet
  checked, which is a known gap.

A variadic function serves a fixed-arity interface, because its rest parameter requires no
arguments: `mean`, declared as `fn(x: Any, ...: Any)`, is accepted where `fn(integer[]) -> double`
is expected. The other direction is rejected, because a variadic interface may send any number of
arguments and a fixed-arity function cannot receive them. Between two variadic types, the rest
element types are contravariant like any parameter, and both sides must declare the same number of
parameters before `...`. This rejects some safe pairings, but never admits an unsound one.

The base functions that take a function argument and resolve it with `match.fun` (`lapply`,
`sapply`, `vapply`, `mapply`, `Map`, `Filter`, `Find`, `Position`, `Reduce`, `do.call`, `outer`,
`apply`, `tapply`, `sweep`, `rapply`, `eapply`, `Vectorize`, `Negate`, `aggregate`, and `match.fun`
itself) also accept the function's name as a string. A string literal that names a known function
checks as that function, so `vapply(words, "toupper", numeric(1))` is an error because `toupper`
returns `character`. Any other string, such as `"[["` or a computed name, is `Unknown` and
unchecked. A string reaches a function-typed parameter only at these callees: a project function
that calls its `callback` parameter does not accept `"toupper"`.

When a function value is rejected at a parameter, the finding names the one position that failed
rather than printing both whole signatures: either the parameter to which the interface passes a
value the function will not take, or the function's return, which the interface will not take. An
arity mismatch still shows both signatures.

#### Callback forwarding at variadic call sites

R's apply family calls its callback as `FUN(element, ...)`, forwarding the caller's extra arguments,
so a callback with more formals than the interface declares is still correct when the call forwards
the difference. At a call to a variadic function, a function-typed argument that fails the plain
interface check is therefore checked again, as that forwarded call:

- Forwarded named arguments fill the callback's formals of the same name first, each checked against
  its formal's type.
- The interface's own parameter types then fill the remaining formals in order, followed by the
  forwarded positional arguments.
- Any formal left unfilled must have a default.
- The callback's return type must satisfy the interface's return type.
- If the second check fails, it binds nothing, and the reported error is the plain interface
  mismatch.

`lapply(words, gsub, pattern = "a", replacement = "o")` is therefore checked as
`gsub(word, pattern = "a", replacement = "o")` and is `list[character]`, and `lapply(words, nchar)`
accepts `nchar`'s optional formals. A forwarded argument of the wrong type fails the check, and the
call is an error.

Inside a wrapper, a call that forwards its own `...` to a function parameter, as in
`function(func, x, ...) func(unique(x), ...)`, demands only the parameters its other arguments fill,
because the forwarded `...` may be empty. So `dedup(basename, paths)` is accepted even though
`basename` takes a single argument. A call that passes nothing but the forwarded `...`, as in
`function(callback) function(...) callback(...)`, gives the parameter the type `fn(...: Any) -> T`,
which any function satisfies, including one with required parameters such as
`function(path) paste0(path, "/cache")`. An annotation `fn(...: Any) -> T` means the same.

### Higher-order function types

A function type may appear inside another function type, as in
`fn(transform: fn(integer) -> character) -> character`, and as an expanded `@param` type such as
`@param render_count {fn(integer) -> character}`. A nested function type cannot carry its own
binder, because binders are rank-1.

## Type annotations and assertions

### Checked annotations

`#: TYPE` is a checked annotation: the annotated value must be *compatible* with `TYPE`, so the check
allows widening wherever the rules on this page define it. When the check succeeds, the value is
accepted (through a coercion if one is needed), and the annotated binding or expression has the type
`TYPE` from then on.

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
value: list[integer] <- list(1L, 2L, 3L)
```

</TabItem>
<TabItem label="Comments">

```r
#: list[integer]
value <- list(1L, 2L, 3L)
```

</TabItem>
</Tabs>

This is valid, because `list{integer, integer, integer}` is compatible with `list[integer]`.

A checked annotation with a nominal type asserts that the value *already* has that type; it does not
create one. `#: Person` on a structural value is a type error, even when the value matches the
representation. Use [`@new`](#nominal-introduction) instead.

### Unknown-only coercions

`#: @if-unknown TYPE` fills a gap in inference. It is allowed only when the inferred type is
`Unknown`, and it then gives the annotated binding or expression the type `TYPE`. When the checker
already knows the type, `@if-unknown` is an error, even if the requested type matches the known one,
so it can never override information the checker has.

Inline, the directive goes between the binding's `:` and its type:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
frame <- data.frame(a = 1)

gap: @if-unknown integer <- frame$a   # valid: `frame$a` is `Unknown`

value: @if-unknown integer <- 1L      # an error: the type is already known
```

</TabItem>
<TabItem label="Comments">

```r
frame <- data.frame(a = 1)

#: @if-unknown integer
gap <- frame$a   # valid: `frame$a` is `Unknown`

#: @if-unknown integer
value <- 1L      # an error: the type is already known
```

</TabItem>
</Tabs>

### Trusted coercions

`#: @trust TYPE` is the unchecked override: it treats the annotated value as `TYPE` without requiring
the usual compatibility at that site. It has the same effect as coercing the value to `Any` and then
to `TYPE`, and exists as a shorter way to write that.

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
callback <- function(x) x

render_count: @trust fn(count: integer) -> character <- callback
```

</TabItem>
<TabItem label="Comments">

```r
callback <- function(x) x

#: @trust fn(count: integer) -> character
render_count <- callback
```

</TabItem>
</Tabs>

A trusted coercion silences a real error as readily as a false one, so use it only when you know
more than the checker does.

### Nominal introduction

`#: @new NOMINAL_TYPE` is the one way to create a value of a nominal type. The annotated value must
be compatible with the nominal type's representation, and when it is, the annotated binding or
expression has the nominal type from then on.

- `NOMINAL_TYPE` must refer to a nominal type declared with `@type`, either by its bare name, such as
  `Person`, or as a generic application, such as `Person<integer>`. An alias, a structural type, a
  union, a function type, or any other type form is not allowed after `@new`.
- A generic nominal may be written unapplied. `@new Person` on a `Person<T>` infers the type
  arguments from the representation check, so a value `list(value = 1L)` becomes a
  `Person<integer>`.
- When the value already has the nominal type, `@new` is allowed and does nothing further.
- The parentheses of `@Name(...)` are the value's own, so they follow the record and tuple literal
  rules: `@Point(x = 1, y = 2)` is a record, `@Pair(1L, "a")` a tuple, and `@UserId(id = 1L,)` a
  one-field record. `@UserId(id = 1L)` is an R assignment wrapped in the constructor, and when the
  representation is a one-field record with that field, the `type-mismatch` suggests the trailing
  comma.
- `@new` is an annotation form, not a type expression, so it cannot appear inside a compact type or
  an expanded function annotation.

Inline, `@Person(value)` introduces the nominal type on any expression, and `x: @new Person <- value`
on a binding:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
type Person<T> = list{ value: T }

value <- @Person<integer>(list(value = 1L))
```

</TabItem>
<TabItem label="Comments">

```r
#: @type Person<T> {list{ value: T }}

#: @new Person<integer>
value <- list(value = 1L)
```

</TabItem>
</Tabs>

## Operators

### Operators over union operands

Control-flow joins and mixed containers produce union-typed operands, so every operator below accepts
a union member by member. A union operand is accepted when every member is accepted; one unacceptable
member rejects the whole operand, and the diagnostic shows the full union. The result is the join of
the per-member results, which for a binary operator means the join over every pair of left and right
members.

- `(integer | double) + integer` is `integer | double`.
- `(integer | double) > 0L` is `logical`.
- `(integer | character) + 1L` is a type error, because the `character` member is not numeric.
- `(integer | NULL) + 1L` is `integer`. R's arithmetic and comparison give an empty vector for a
  `NULL` operand rather than failing, so a `NULL` member is accepted and contributes nothing to the
  result, and `(character | NULL) == "a"` is `logical`. An operand that is only `NULL`, as in
  `NULL + 1L` or `NULL == 1L`, gives `Unknown`.
- `rec$a` on `list{a: integer} | list{a: character}` is `integer | character`. A member that lacks
  the field changes the result, as [indexing](#indexing) describes.
- A `for` loop over `integer[] | character[]` binds its variable as `integer | character`.

#### Conditions

`if`, `while`, and the operands of `&&` and `||` all take a *scalar condition*, and R decides what a
scalar condition admits:

- `logical` is the ordinary case.
- `integer` and `double` are accepted, and coerce as R coerces them: zero is false, and anything else
  is true. That makes `if (length(x))`, `if (nrow(df))`, and `while (n)` ordinary R.
- `character`, `complex`, and `raw` are type errors. R refuses `complex` and `raw` outright, and
  accepts a `character` condition only when it spells `TRUE` or `FALSE` (such as `"T"` or `"true"`),
  so `if ("yes")` is reported.
- A vector is accepted, because a vector type carries no length, and the vector a test produces,
  such as `x >= 1` on a `double[]`, has length one at run time far more often than not. Only a
  `c()` call with two or more arguments is known to be longer than one, so `if (c(TRUE, FALSE))` is
  a type error, as it is in R.
- A condition whose type is still undetermined becomes `logical`, so `function(flag) if (flag) 1L`
  infers `flag: logical`. A value already required to be numeric keeps that requirement, so
  `function(n) if (n %% 2L) "odd" else "even"` is `<T: numeric> fn(n: T) -> character`. An
  unannotated formal with a default is the exception: an option flag such
  as `function(x, which = FALSE) if (which) ...` is called with `1` as often as with `TRUE`, so the
  condition leaves its type to its other uses. The same holds for `!` on such a formal.
- A union is accepted when every member other than `NULL` is. The `NULL` member is the "not
  supplied" path of an optional value, which code tests only once it holds one, so
  `if (config_flag(pkg))` on a `logical | NULL` is not reported. An undetermined member, such as a
  parameter rebound on one path (`T | logical`), becomes `logical` as a lone one would. A bare `NULL`
  condition is still a type error, as `if (NULL)` is in R.

### Indexing

`[[` extracts a single element, and `[` is R's general subsetting operator. `[` with an out-of-range
position or a missing name gives `NA` at run time, which is a property of the value, not of its type.
`[[` with a missing name gives `NULL` on a list, which the rules below record as `| NULL`; they
record the same for a named vector, where R instead fails at run time.

`$name` behaves like `[["name"]]` on lists, on records, and on opaque nominals, and a backtick-quoted
name follows the same rule. `$` does not work on atomic vectors, because R rejects it on every atomic
vector, named ones included: `c(foo = 1L)$foo` is a type error, while `c(foo = 1L)[["foo"]]` is
`integer | NULL`.

Every element of `NULL` is `NULL` in R, so `NULL$name`, `NULL[["name"]]`, and `NULL[1]` are `NULL`.
A list that may be absent is therefore read directly: on `list{retries: integer} | NULL`,
`config$retries` is `integer | NULL`.

On a union, a field may be missing from some of the members. When the members that lack it are
empty lists, the read is that field's type unioned with `NULL`, which is what R answers for the
empty list. Code that builds a list field by field therefore checks:

```r
args <- list()
if (escape) args$escape <- TRUE
args$escape        # logical | NULL
```

When a non-empty member lacks the field, the read is `Unknown`, for the reason a single record-like
list reads a missing name as `Unknown`. A field that *no* member has is still an error when it is a
near miss of a field some member has, and the "did you mean" suggestion draws on every member's
fields.

#### `[[` on vectors

- A scalar-like `T` returns `T`.
- An array-like `T[]` returns `T`.
- A map-like `T[named]` returns `T | NULL` for a name index.

#### `[[` on lists

- A list-like `list[T]` returns `T`. `$name` on it returns `T | NULL`, because such a list may still
  carry names at run time, and R answers `NULL` for a name it lacks.
- A dict-like `list[named: T]` returns `T | NULL` for a name index, and `T` for a positional or
  computed one.
- A tuple-like list returns the element at a literal position. A position that does not exist is an
  error, and a computed position returns the union of the item types.
- A record-like list returns the field at a literal name or literal position, and a computed index
  returns the union of the field types, which is how a call to a function looked up in a list gets
  its type. A position that does not exist is an error.
- A literal name a record-like list lacks reads as `Unknown`, because R lists are open: a list
  literal is often only the start of a value other code adds fields to. A name that is a near miss
  of a field, such as `opts$verbsoe` for `verbose`, is still an error with a "did you mean"
  suggestion. `$` also matches a unique prefix of a field name, as R does, so `opts$verb` reads
  `verbose`.

#### `[` on vectors

The result of `[` on a vector depends on the shape of the index:

- A scalar-like `integer`, `double`, or `character` index gives the scalar element type. That is not
  always exact, since `x[-1]` drops one element and returns the rest, but a scalar coerces into every
  vector position, so the claim can never cause a false error later.
- An array-like or map-like numeric or character index, such as `x[c(1L, 3L)]`, keeps the subject's
  shape.
- A `logical` index of any shape is a mask, as in `x[x > 0]`, and keeps the subject's shape.
- `NULL` selects nothing and gives the array-like vector of the element type.
- An index whose shape is undetermined, such as an unannotated parameter or an `Unknown`, counts as
  scalar-like and is left unconstrained.
- A `complex` or `raw` index is a type error, as is a list, a function, or any other index that is not
  a vector.

Keeping the subject's shape means `E[]` on a scalar-like `E` or an array-like `E[]`, and `E[named]` on
`E[named]`, because `[` keeps names. A character index is allowed on every vector shape, not only a
map-like one, because R returns `NA` rather than failing when the subject has no names, and most
operations erase names.

- `c(1L, 2L, 3L)[2L]` is `integer`.
- `c(1L, 2L, 3L)[c(1L, 3L)]` is `integer[]`.
- `c(a = 1L, b = 2L)[c("a", "b")]` is `integer[named]`.
- `x[list(1)]` is a type error.

#### `[` on lists

`[` slices a list, so a fixed shape does not survive into the result:

- A list-like `list[T]` returns `list[T]`.
- A dict-like `list[named: T]` returns `list[named: T]`.
- A tuple-like list returns `list[T]`, where `T` is the union of the item types, so
  `list(1L, "foo")[1L]` is `list[integer | character]`.
- A record-like list returns `list[named: T]`, where `T` is the union of the field types.
- Slicing the empty list gives `list[NULL]`.

#### Indexing a value whose shape is unknown

`$`, `[[`, and `[` on a value whose shape the checker has not determined, such as an unannotated
parameter, give `Unknown` and leave the value unconstrained. So `function(node) node$value`,
`function(x) x[[1L]]`, and `function(x) x[1L]` report nothing, and neither does indexing with several
indices, as in `function(m, i, j) m[i, j]`. Ordinary R reads fields and slices off values whose shape
nobody wrote down, so refusing here would report correct code. Like access on an opaque nominal, such
an access is an unsupported construct under [strict mode](#strict-mode).

Indexing with several indices, which is matrix and data frame selection, or with a named argument
such as `drop = FALSE`, is not modelled on any subject. It gives `Unknown` without a report, so
`c(1L, 2L)[1L, 2L]` passes, and strict mode reports it as an undetermined type. An empty index is
the subject itself, so `x[]` on `list{integer, integer}` is `list{integer, integer}`.

### Arithmetic operators

The arithmetic operators are defined for numeric operands:

- `integer` and `double`;
- `logical`, which R promotes to `integer` before arithmetic, so `TRUE + TRUE` is `2L`;
- `complex`, which makes the result `complex`, so `1i + 2` and `1i / 2L` are `complex`;
- an unannotated value, which is then required to be numeric (see below);
- a class that declares an [operator method](#operator-methods-on-a-class).

The result is scalar-like when both operands are scalar-like, and array-like otherwise, so a map-like
operand gives an array-like result. Unary `-` keeps a scalar-like or array-like operand's shape. The
result's atomic type depends on the operator:

- `+`, `-`, `*`, `%%`, and `%/%` give `integer` when both operands are `integer` (or `logical`), and
  `double` otherwise.
- `/`, `^`, and `**` (R's parser alias for `^`) always give `double`.
- Unary `-` keeps its operand's atomic type. A class with arithmetic methods negates to itself,
  because R dispatches unary `-` through the same methods, so `-(m %*% m)` is a `matrix`.

For example, `double * integer[]` is `double[]`, `integer[named] + integer` is `integer[]`,
`2L ^ 3L` is `double`, and `-c(foo = 1L, bar = 2L)` is `integer[]`. Every `%op%` operator other than
`%%` and `%/%` is covered under [operator methods on a class](#operator-methods-on-a-class).

#### Unannotated values in arithmetic

An unannotated value used as an arithmetic operand is *required to be numeric* rather than rejected:
it must end up as `integer` or `double`, in any vector shape, or as a class that declares an
arithmetic operator method.

- `function(x) x + 1L` is `<T: numeric> fn(x: T) -> T`, and calling it with `"oops"` is a type error.
- `function(x) x / 2` is `<T: numeric> fn(x: T) -> double`.
- `function(a, b) a + b` is `<T: numeric> fn(a: T, b: T) -> T`.

When the other operand is a vector, the unannotated operand stays open and the result is a `double`
vector, so `f <- function(x) x + c(1L, 2L)` is `<T: numeric> fn(x: T) -> double[]` and accepts
`f(TRUE)` and `f(c(1, 2))` alike. When the other operand is a union, the unannotated operand is pinned
to a scalar `double`, which matches how R treats bare numbers. An operand whose shape is still unknown
counts as scalar-like here and in comparisons, by the same claim that
[`[` on vectors](#-on-vectors-1) makes. A generic vector written `T[]` is the exception, and its
operator results really are vectors.

A `logical` argument satisfies the numeric requirement, because R promotes it, so
`cost <- function(price, rate) price * rate` accepts `cost(TRUE, 0.5)` and `cost(1L, 0.5)`. Mixed
arguments widen in R's order, `logical` to `integer` to `double`, so both calls are `double`.

### Operator methods on a class

When an operand of an operator is a nominal type, the operator first dispatches to the class's
declared operator method, before any numeric rule applies, just as R dispatches `d + 30L` on a `Date`
through `+.Date`.

The lookup follows R's order: first the operator-specific method, such as `+.Date`; then the
operator's S3 group generic, `Arith.Date` for arithmetic and `Compare.Date` for comparison; and
finally `Ops.Date`. Either operand's class may supply the method, the left one first, so `30L + d`
behaves like `d + 30L`. The method name's suffix is the nominal type's name, not R's full class
vector, so a class declared as `@type ggplot` takes `+.ggplot`, even though R registers the method
as `+.gg`.

A method is declared under the name R gives it, in a stub or an annotation, so the result stays
precise for each pairing of operands: subtracting two `Date` values gives a `difftime`, and offsetting
one by a count gives a `Date`. A class that declares an operator but has no candidate that accepts
the operands at hand is a `type-mismatch` error rather than a fall-through to the numeric rules, just
as in R. A class that declares nothing does fall through to the numeric rules, so arithmetic on an
opaque nominal is still a type error. An unannotated operand beside a class operand does not take
the class from the first candidate, because R accepts a plain vector there too. It is only required
to be numeric, so in `function(omega, v) omega + v %*% t(v)`, `omega` is a `T: numeric`, and a call
with two plain vectors is accepted.

Your own classes count. A method declared anywhere the global scope reaches, which includes a
package's `R/` sources and a script's own top level, makes its class support that operator exactly as
a shipped stub does. That is also how the class satisfies the numeric requirement: passing a `Money`
to `function(x) x + 1L` is accepted when the project defines `+.Money`, and refused when it defines
no arithmetic method.

R also dispatches on a class that `class(x) <- "string"` sets on a plain list, and no type tracks
that attribute. So when the project defines an arithmetic or `Ops` method for a class that no type
declares, arithmetic with a list operand is left to that method: `result + "text"` on such a list,
and the rest of a chain `result + a + b`, give `Unknown` and report nothing. Without such a method,
`list(a = 1) + 1` is a type error, as it is in R.

`c()` dispatches the same way. A class that declares a `c.Class` method keeps its class through
concatenation, so `c(d1, d2)` on two `Date` values is a `Date`. A nominal with no such method loses
its class but keeps its data, as R's default `c()` does, so two values of `@type Money {double}`
combine to `double[]`. An opaque nominal has no representation, so combining it gives `Unknown`.

`a %op% b` is the call `` `%op%`(a, b) ``. A `%…%` operator that the standard-library stubs declare
is checked and typed as that call, so `"a" %in% valid` is `logical` and `m %*% m` is a `matrix`.
Every other `%…%` operator, including a project's own, gives `Unknown`, because a user operator may
quote its right operand instead of evaluating it, as magrittr's `%>%` does. Using any `%…%` operator
still counts as a read of its name, so a project's own operator is never reported as unused.

### Comparison operators

`<`, `<=`, `>`, `>=`, `==`, and `!=` compare two `logical`, `integer`, `double`, or `character`
operands, mixed freely. R coerces both operands to a common type before comparing, so
`Sys.getenv("RSTUDIO") == 1` and `1L < "a"` are legal R and are not reported. `complex` and `raw`
operands are not supported, so `1i < 2` is a type error. A map-like vector takes part through its
compatibility with an array-like vector. A `NULL` operand, or a `NULL` member of a union, is
accepted, because R answers an empty `logical` vector instead of failing, as
[union operands](#operators-over-union-operands) describe. A list compared with an atomic value
is accepted, because R compares it element by element when each element is a length-one atomic,
so `parts[parts != "null"]` on a parsed list and `lapply(xs, anyDuplicated) > 0` are not reported.
Two lists never compare, so `list(1L) == list(1L)` is a type error, as it is in R.

An unannotated operand is left unconstrained, whatever the other operand is, so
`function(x) x > 0` is `<T> fn(x: T) -> logical` and `function(a, b) a < b` is
`<T, U> fn(a: T, b: U) -> logical`. A comparison against a number is often how R code tests a
string or a flag, so it is not evidence that the operand is numeric. The cost is that a caller's
mistake can pass unreported: with `f <- function(x) x > 0`, `f(function() 1)` is accepted, although
R fails the comparison. Comparing a value whose type is known, as in `1 > function() 1`, is still a
type error.

The result is always `logical`: scalar-like when both operands are scalar-like, and array-like
otherwise. So `1L == 1.5` and `1L < "a"` are `logical`, and `c(TRUE, FALSE) > 0` is `logical[]`.

### Unary `!`

Logical negation coerces its operand exactly as a [scalar condition](#conditions) does, so `!0` is
`TRUE` and `!5` is `FALSE`. Its result is always logical:

- `!logical`, `!integer`, and `!double` are `logical`.
- `!logical[]`, `!integer[]`, and `!double[]` are `logical[]`.
- A map-like operand gives `logical[]`, because negation does not preserve map-likeness.
- `!NULL` is `logical[]`, the empty vector R returns, so a value that may be `NULL` negates without
  error: `!x` on `logical | NULL` is `logical[]`.
- An `Any` or `Unknown` operand gives `Unknown`.
- An operand whose type is still undetermined is constrained to `logical`, and the result is
  `logical`, except for an unannotated formal with a default, which stays open as it does in a
  [condition](#conditions).
- Any other operand is a type error.

### Range operator `:`

`from:to` builds a numeric sequence. Each endpoint may be an `integer`, a `double`, or a `logical`,
which R takes as a number, or a union of those. A vector endpoint is accepted too, because R uses its
first element and a vector type carries no length; only a `c()` call with two or more arguments is
known to be too long, so `1:c(1L, 2L)` is a type error, and so is a non-numeric endpoint. The
result is `integer[]` when both endpoints are `integer` or `logical`, and `double[]` when either
may be `double`, so `1:TRUE` is `integer[]` and `1:n` on `n` of type `integer | double` is
`double[]`. A whole-number `double` literal such as `1` or `10`
counts as `integer` here, matching what R does at run time, so `1:10` is `integer[]` and `1.5:3L` is
`double[]`.

An unannotated operand, as in `1:n`, is required to be a scalar `integer` or `double`. Passing a
numeric vector through the enclosing function is therefore a type error at the call, because R's
warning about truncating the endpoint marks a bug. The result is `double[]`, because the endpoint may
turn out to be a `double`.

### Combine `c(...)`

`c(...)` builds a vector from arguments of any shape:

- With no arguments, `c()` is `NULL`, as in R.
- `NULL` arguments are dropped, as in R, so `c(x, NULL)` is `c(x)` and `c(NULL)` is `NULL`.
- A union-typed argument takes part member by member. Its `NULL` members are dropped first, and every
  remaining member joins the coercion like a separate argument. So with `acc` of type
  `double[] | NULL`, `c(acc, 1.0)` is `double[]`, and `c(if (a) list(1), if (a) list(2))` is
  `list[double]`.
- When any argument is a list, `c` concatenates into a list-like `list[T]` whose element type is the
  join of every argument's elements, with an atomic argument contributing its own type:
  `c(list(1L), "a")` is `list[integer | character]`. The atomic rules below apply only when no
  argument is a list.
- An argument whose element type is not known statically, such as `Any`, `Unknown`, an unannotated
  parameter, or a union or vector that holds one (`T | NULL`, `T[]`), is tolerated, and the whole
  result is `Unknown`, because a concrete element type could
  be widened by a later argument. So `function(x) c(x, 1L)` is `<T> fn(x: T) -> Unknown`. Under
  strict mode, an unannotated parameter makes the `c()` call the origin, an `Unknown` argument was
  already reported where it arose, and an `Any` argument is not reported.
- Mixed atomic arguments coerce to the widest type in R's order,
  `logical < integer < double < complex < character`.
- `c()` never reports an argument, because R's `c()` accepts every value. An argument the order
  does not cover, such as a function or a `raw` beside another atomic type, makes the result
  `Unknown`, so `c(as.raw(1L), 2L)` and `c(function() 1, 2)` are `Unknown`.
- When every argument is named, the result is a map-like `T[named]`; otherwise it is an array-like
  `T[]`.

For example, `c(TRUE, 1L)` and `c(1L, NA)` are `integer[]`, `c(1L, "a")` is `character[]`, and
`c(foo = 1L, bar = 2L)` is `integer[named]`.

### Assignment operator `<-`

`name <- expr` writes the type of `expr` into the variable slot for `name` in the current scope,
creating the slot on the first write (see [value names](#value-names) for the slot model). The
assignment expression itself has the type of `expr`, so `y <- (x <- 1L)` gives both `x` and `y` the
type `integer`. When the assignment carries an annotation, `expr` is checked by the annotation rules.

- A string in place of the name binds that name: `"x" <- 1` is `x <- 1`, and so is `` `x` <- 1 ``.
  For a string target, the range of any finding is the literal, quotes included.
- A target that is not a name, such as a computed value or a number, is reported as a
  `syntax-error`, because R refuses it at run time. A target headed by `!` is exempt, because `!`
  binds tighter than `<-`, so rlang's `expr(!!name <- value)` builds an assignment instead of
  performing one.
- A later assignment in the same scope writes the same variable. On a straight-line path the new
  write replaces the old type, and writes that arrive from different paths are joined (see
  [control-flow joins](#control-flow-joins)). So after `x <- 1L; x <- "foo"`, `x` is `character`, and
  after `x <- 1L; if (flag) x <- "foo"`, it is `integer | character`.

#### Recursion

A function can call itself, because its own name is visible inside its body.
`fact <- function(k) if (k <= 1L) 1L else k * fact(k - 1L)` is `fn(k: integer) -> integer`, and a
call that violates the recursively inferred signature is an error. The recursive uses share one
instantiation, so there is no polymorphic recursion.

Two local functions that call each other are beyond this, because names are bound one at a time. The
forward reference still resolves, since a closure sees later writes to its frame, but it stays
`Unknown`.

At a package's top level, a self-recursive definition and a group of mutually recursive definitions
are both re-derived until their types stop changing, starting from `Unknown`. Simple recursion
converges to its precise type: a top-level `fact` exports `fn(n: integer) -> integer`, and the pair
`is_even` and `is_odd` exports `<T: numeric> fn(n: T) -> logical`.

A self-reference whose type would grow without bound cannot converge without recursive types. A tree
fold is one: its parameter would need `T = double | list[T]`, so such a group settles at `Unknown`. A
cycle can also converge with an `Unknown` inside it, and a pure self-call such as
`f <- function() f()` settles at `fn() -> Unknown`. Either way, strict mode reports it, and an
explicit annotation on the binding closes the cycle exactly.

### Boolean operators `&&` and `||`

Both operands are [scalar conditions](#conditions), and the result is a scalar `logical`. As in a
condition, a vector operand is accepted unless it is a `c()` call with two or more arguments, so
`v && TRUE` on a `logical[]` passes, while `c(TRUE, FALSE) && TRUE` and `TRUE || c(FALSE, TRUE)` are
type errors.

### Elementwise operators `&` and `|`

Each operand is a `logical`, `integer`, or `double` scalar or vector, and the result is `logical`.
It is a scalar when both operands are scalars, and `logical[]` otherwise, so `a > 0 & b > 0` on two
`double[]` parameters is `logical[]`. An operand whose type is `Any` makes the result `Any`, and
one whose type is `Unknown` makes it `Unknown`, which strict mode reports where the operand's type
was lost. An operand with no type yet, such as an unannotated parameter, could be a scalar or a
vector, so the operator gives `Unknown` and strict mode reports it; annotate the parameter.

## Calls

### Function calls

A call evaluates to its callee's return type. When the callee expression or its return type is
`Unknown`, the call is `Unknown`. When the callee is a union whose members are all function types,
the call must be valid against every member, since the value could be any of them, and it evaluates
to the union of the members' return types. No member's argument bindings leak into another's.
Calling a function looked up in a list, as in `handlers[[name]](...)`, has this shape.

A call is a type error when a required argument is missing, when it passes too many arguments to a
callee without a rest parameter, or when an argument is incompatible with its parameter's type. The
[named and positional parameter rules](#named-and-positional-parameters) apply throughout. A missing
named argument is reported by name, as in "this call leaves out `y`, which the function requires",
and too many arguments are counted as the positional arguments against the
positional slots that named arguments left open.

#### Matching arguments to parameters

Arguments are matched in R's order, and names compare case-sensitively:

1. Every argument given by name claims the parameter of exactly that name, before any positional
   argument is placed.
2. A remaining named argument claims a parameter declared before the rest parameter whose name it
   is a prefix of, when exactly one unclaimed parameter has that prefix. So
   `list.files(".", full = TRUE)` sets `full.names`. Parameters after the rest parameter match only
   exactly, as in R.
3. The positional arguments then fill what is left: first the fixed positional parameters, then the
   unclaimed named parameters declared before the rest parameter, in declaration order. When the
   function is not variadic, they fill all the unclaimed named parameters.
4. The rest parameter absorbs whatever remains, positional or named.

So in `vapply(xs, character(1), FUN = f)`, the named `FUN` is claimed first, and `character(1)`
reaches `FUN.VALUE`, exactly as R matches it. In `lapply(1:2, fmt, x = data)` the lowercase `x`
does not match `lapply`'s `X`, so it goes to the rest parameter and is forwarded to `fmt`.

A rest parameter follows R's rules for the formals around the dots:

- It adds no required arguments, so `paste()` is legal.
- Positional arguments fill the parameters declared before it first, so `wrap("a", "b")` on
  `fn(x: character, ...: character)` gives `x = "a"` and sends `"b"` to the rest.
- It then absorbs any number of remaining positional arguments, each checked against its element
  type.
- A parameter declared after it can only be matched by name, so `sum(1, 2, na.rm = TRUE)` on
  `fn(...: integer[] | logical[], [na.rm]: logical)` sends `1` and `2` to the rest and `na.rm` by
  name.
- It also absorbs a named argument that matches no declared parameter, as in
  `read.csv(file, colClasses = "character")`.
- A named argument that duplicates a parameter already given is still an error, because R rejects a
  formal matched twice.

When an argument is the enclosing function's bare `...`, as in a wrapper
`function(x, ...) helper(x, ...)`, it forwards an unknown number of arguments, possibly none. Such a
call skips both arity checks, and the `...` argument itself matches no parameter. The call's other
arguments are still checked as usual.

#### Argument compatibility

Arguments are checked for compatibility, not exact equality:

- The ordinary coercions apply at parameter positions, including a scalar-like `T` into an
  array-like `T[]`, and `T` or `NULL` into `T | NULL`.
- The promotion order from [vector coercions](#vector-coercions) applies, so `mean(1L)`,
  `sd(c(1L, 2L))`, and `sum(x > threshold)` are not errors.
- A whole-number `double` literal counts as `integer` at a parameter, as it does at the endpoints of
  `:`, so for `fn(n: integer)`, `f(10)` is as valid as `f(10L)`. A fractional literal such as `2.5`
  is still rejected, and so is a `double` variable that happens to hold a whole number. `-3` is unary
  minus applied to a literal, not a literal, so `f(-3)` is rejected too.
- An argument whose type is `Unknown` is accepted at any parameter, because whatever made the value
  `Unknown` was already diagnosed where it happened.
- A `character` argument is accepted at a parameter of function type, because R's functional
  helpers resolve a function's name with `match.fun`, which makes `lapply(calls, "[[", "call")` and
  `apply(m, 1, "mean")` idiomatic. At the base helpers that call `match.fun`, such as `lapply`,
  `sapply`, `vapply`, `Map`, `Filter`, `Reduce`, `do.call`, and `apply`, a string literal that names a
  known function is checked as that function, so `lapply(list(1, 2), "sqrt")` is `list[double]`.
  Any other string is accepted unchecked.
- At a parameter of type `T | NULL` with `T` still open, which is what a callee that tests
  `is.null(x)` infers, `T` binds to the argument's non-`NULL` part. Passing a value there says that
  the callee tolerates `NULL`, not that the caller's value may be `NULL`, so with
  `check <- function(x, allow_null = FALSE) if (allow_null && is.null(x)) ...`, a caller that runs
  `check(thing)` and then reads `thing$field` keeps `thing` open.

#### The native pipe

R's parser rewrites `x |> f(y)` into `f(x, y)` before anything runs, so the pipe types exactly like
that call. The piped value becomes the first positional argument, and every call rule applies to it:
arity, argument compatibility, and overload selection. A chain composes from left to right, and a
type error in the piped value is reported on the left-hand expression.

The `_` placeholder follows R's rule: it is legal only as the entire value of exactly one named
argument, which then receives the piped value instead of the first positional slot. So
`x |> lm(y ~ z, data = _)` is `lm(y ~ z, data = x)`, and `2 |> f(tag = _)` supplies only `tag`.

A pipe that R itself would reject is not guessed at. That covers a right-hand side that is not a
call, a positional or repeated `_`, and a `_` nested inside a subexpression. Such a pipe types as a
silent `Unknown`, and its reads are not reported.

### Overload sets

A standard-library stub may declare several signatures for one name, forming an ordered overload
set ([authoring stubs](/contributing/authoring-stubs#overloads-and-generics) describes how). A call
to such a name is resolved separately at each call site:

- Candidates are tried in declaration order, and the call commits to the first one whose parameters
  accept the arguments. That candidate's return type is the call's type, so `sum(1L, 2L)` is
  `integer` and `sum(1.5, 2.5)` is `double`. Nothing a failed candidate bound leaks into the next
  candidate or into the result.
- A candidate that leaves the caller's undetermined types as they were beats one that constrains
  them, whatever the declaration order. A wrapper like `function(x) cumsum(x)` therefore keeps its
  parameter open, because `cumsum`'s `Any` fallback accepts it without constraining anything. Strict
  mode reports a call that resolves to such a fallback. When only one candidate fits, it is selected
  and whatever it determines stands.
- When several candidates fit only by narrowing the caller's undetermined types, the call keeps that
  narrowing only if they all narrow the same way. Otherwise the type becomes `Unknown`, and so does
  the call: `function(xs) Filter(f, xs)` infers `fn(xs: Unknown) -> Unknown` and accepts both a vector
  and a list. A function literal among the arguments does not belong to the caller, so narrowing its
  parameters is no guess: that is how `lapply(xs, function(v) v + 1L)` gives `v` a type.
- An argument whose type is not known statically fits every candidate, so the call does not guess
  among candidates whose results differ, and it is `Unknown`. So
  `function(w) sort(unique(unlist(w)))` is `<T> fn(w: T) -> Unknown` rather than taking `sort`'s
  `factor` candidate.
- The [whole-number literal rule](#argument-compatibility) does not influence which candidate is
  selected. Candidates are first tried against the arguments' true types, so `sum(1, 2)` selects the
  `double` candidate, matching what R computes. Only if no candidate accepts them is the set tried
  again with literals allowed as integers.
- When no candidate accepts the arguments, the call is a type error. Normally the error names the
  overloaded callee and how many signatures were tried, and gives the first candidate's failure as a
  hint. One candidate's own finding is reported instead, at its own argument range, when every
  candidate rejects the call for the same reason, or when one candidate got strictly further into the
  argument list than all the others.
- Passing an overloaded name as a value, or hovering over it, sees the *last* declaration, which by
  convention is the most general. Go-to-definition jumps to the *first* declaration.
- The exception is an overloaded name passed by name to `lapply`, `sapply`, `vapply` or `Reduce`.
  There the set is resolved once per element type, as R calls it once per element, so
  `lapply(list(units = c(1L, 2L)), sum)` is `list[named: integer]` and `sapply(list(a = 1L), sum)`
  is `integer[named]`. Each field of a record or frame is its own element type, and an element no
  candidate accepts is an error. A class whose first argument declares a `sum.<class>` or
  `Summary.<class>` method is dispatched to that method instead of the set, as R dispatches it.

Only a declaration file can overload a name, because a name with several signatures has no single
most general type and must be resolved by search rather than inferred. A `#:` annotation on your own
function declares exactly one signature; to make one name accept several shapes, give the parameter
a [union type](#union-types), or split the shapes into separate functions.

A local or package binding that shadows a stub name switches its overload set off, and the binding is
used everywhere, calls included. A project override stub may declare overload sets, because a
`.Rtypes` file is a declaration file wherever it lives.

## Control flow

### `if` expressions

#### `if` without `else`

An `if` without `else` takes a [scalar condition](#conditions). If the branch has type `T`, the whole
expression is `T | NULL`, because the missing branch contributes `NULL`. Union normalization applies,
so a `NULL` body stays `NULL`, a nullable body stays a single `T | NULL`, and an `Unknown` body stays
`Unknown`.

#### `if ... else`

An `if ... else` takes a [scalar condition](#conditions) and joins the types of its two branches. The
join does not merge or coerce branch types beyond unification; it records the alternatives:

- Branches that unify share that type. `if (flag) 1L else 2L` is `integer`, and `if (cond) a else b`
  over two unconstrained values keeps them unified as one polymorphic type.
- A `NULL` branch joins by union without constraining the other branch, so `if (flag) NULL else 2L`
  is `integer | NULL`.
- Branches with genuinely different types give their union: `if (flag) 1L else "foo"` is
  `integer | character`, not a type error.
- A branch whose type is still undetermined is never pinned by the other branch.
  `function(flag, x) if (flag) x else "s"` is `<T> fn(flag: logical, [x]: T) -> T | character`, not
  `fn(flag: logical, x: character)`, because unifying would make a caller wrong because of a line
  that is not wrong.
- A branch whose variable the body has already constrained may unify with the other branch, because
  that adds nothing the program did not already require. That is how the recursive `fact` above
  converges to `fn(n: integer) -> integer`.
- Two branches that are both still open are tied to each other.
  `function(value, fallback) if (is.null(value)) fallback else value` is
  `<T> fn(value: T | NULL, [fallback]: T) -> T`.
- An `Unknown` branch makes the whole conditional `Unknown`.
- An `if` whose value is discarded, such as a statement in the middle of a block, does not join its
  branches at all, so a branch that only has a side effect never ties its types to the other
  branch's.

#### Diverging branches

A branch *diverges* when it never falls through to the code after the `if`: `return(...)`,
`stop(...)`, `break`, or `next`, a block ending in one of those, or an `if ... else` whose branches
both diverge. A diverging branch contributes neither its value nor the state of its variables, so
`x <- if (c) return(NULL) else 5` gives `x` the type `double`, and a variable written inside a
diverging branch does not join into the state after the `if`.

A call that never returns has no bottom type of its own. A `stop(...)` call types as `Any`, which
fits every context and which strict mode does not report, so `function() stop("no")` is
`fn() -> Any`. `stop(...)` is recognized by its bare name, as `local` and `return` are, so
rebinding `stop` is not modelled.

### Guard narrowing

A condition that applies a type-guard predicate to a plain local variable refines that variable's
type along each edge of the `if`. Inside each branch, the variable keeps the refined type until a
write replaces it, and the refinements merge back at the join exactly as branch writes do. With `x`
a local variable or parameter, the recognized guards are:

- `is.null(x)` makes `x` a `NULL` in the true branch, and removes `NULL` from its union in the false
  branch.
- `is.character(x)`, `is.logical(x)`, `is.integer(x)`, `is.double(x)`, `is.function(x)`, and
  `is.list(x)` keep only the members of that family in the true branch, and remove them in the false
  branch. `is.numeric(x)` does the same for the `integer` and `double` family.
- `!cond` swaps the two branches.

Combined with a [diverging branch](#diverging-branches), the surviving edge's refinement persists
after the `if`, which is the idiomatic early-exit guard:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
f <- function(x: integer | NULL) -> integer {
  if (is.null(x)) {
    return(0L)
  }
  x + 1L   # x : integer here
}
```

</TabItem>
<TabItem label="Comments">

```r
#: fn(x: integer | NULL) -> integer
f <- function(x) {
  if (is.null(x)) {
    return(0L)
  }
  x + 1L   # x : integer here
}
```

</TabItem>
</Tabs>

The details:

- A family test covers both the scalar and the vector of that atomic type, so `is.character` is true
  for `character` and `character[]`. `is.list` covers every list shape, and `is.function` covers
  function types.
- Narrowing filters union members. A member whose family cannot be decided statically, such as an
  unannotated value or an opaque nominal, is kept on both edges.
- An unannotated parameter whose runtime type the body inspects is `Unknown`, because code that
  inspects a type uses the value as a different type on each branch, so no one type describes it.
  The inspections are `typeof()`, `class()`, `mode()`, `storage.mode()`, `inherits()`,
  `is.object()`, `oldClass()`, and the `is.*` family tests, such as `is.character()`. So
  `function(x) if (is.character(x)) x else "other"` is `fn(x: Unknown) -> Unknown`. `is.null()`,
  `is.na()`, and `is.finite()` test a value rather than its type, so they keep the parameter typed,
  and an annotated parameter still narrows.
- `is.null(x)` on an `Any` or `Unknown` variable refines the true edge to `NULL`, because the runtime
  guarantees it. A family guard does not refine `Any` or `Unknown`, because inventing a concrete shape
  there would cause reports on standard-library functions that declare a scalar result for a value of
  any length.
- `is.null(x)` on a value with no constraints yet, such as an unused unannotated parameter, *shapes*
  it: the test asserts that `NULL` is possible, so the variable becomes `T | NULL` for a fresh `T`, and
  the edges narrow as for an ordinary union. That is how the `value`/`fallback` function under
  [`if ... else`](#if--else) types without annotation. Testing a parameter for `NULL` and then
  passing it unguarded to a parameter that excludes `NULL` is therefore a genuine finding, although
  arithmetic and comparison on it are accepted, as [union operands](#operators-over-union-operands)
  describe. The shaping never fires on a variable that already
  carries a constraint, or on a declared rigid type parameter.
- When a guard cannot fire, such as `is.null(x)` on a union with no `NULL` member, nothing is refined.
  Dead branches get no special typing.
- Only a read of a variable narrows: a parameter, a function local, or a top-level variable assigned
  by an earlier statement. `is.null(f(x))` and `is.null(x$field)` do not narrow.
- A refinement does not outlive the top-level statement it was made in. Inside a function body, or
  one braced top-level block, `if (is.null(x)) stop(...)` narrows `x` for the rest of the body,
  because the guard and the later reads are one statement. Written as bare top-level statements, the
  guard and the read after it are two statements, and the read is not narrowed.
- A read from inside a closure narrows when the guard is in the same statement, just as a local
  does. The guard's own subject must not itself be a deferred read: that body runs later, so the test
  proves nothing about the value it will see then.
- Guards compose across `&&` and `||`. The right operand of `&&` runs only on the left's true edge,
  so it is checked under that refinement, and the whole condition refines its true edge by both
  tests: `!is.null(x) && length(x) > 0L` reads a non-`NULL` `x`. `||` does the same on the false
  edge. The other edge of a compound condition is not refined. A family test on an untyped local
  makes the value unchecked on the true edge rather than constraining it, so after `y <- a`,
  `is.numeric(y) && y + 1 > 0` leaves `a` open, where `y + 1 > 0` alone would require it to be
  numeric.
- `is.na(x)` is not a type guard, because being `NA` is a property of a value, not of a type.

#### Lazy arguments and required formals

R evaluates an argument only when the body forces it, and omitting an argument is an error only at
that moment. A formal without a default is therefore required at call sites only when every path
through the body forces it, so `function(x, unused) x` may be called as `f(1)`, and
`function(x, y) if (is.null(x)) y else x` may be called as `f(1)`, because the branch that reads `y`
is not taken. This relaxes only an inferred
signature. An annotation is honored as written, so under `#: fn(a: integer, b: character) -> integer`,
`function(a, b) a` still requires `b`, and to let callers omit it the annotation says `[b]`. A read forces the formal, with these
exceptions and additions:

- A read on only some paths does not force the formal. The branches of `if`, `switch()`, and `match`
  force only what all of them force, and an `if` without `else` or a `switch()` without an unnamed
  default forces nothing. The right operand of `&&` or `||` and the body of a loop may not run, so
  they force nothing either.
- Passing the formal on under its own name to a project function, as in `inner(x, finally = finally)`,
  does not force it, because the callee decides whether it is needed. A call to a library function
  still forces it.
- A body that dispatches with `UseMethod()` forces none of its formals, because it hands them to a
  method unevaluated, and the method decides what it needs. So
  `describe <- function(x, ...) UseMethod("describe")` may be called as `describe()`.
- A read guarded by `missing(name)` does not make the formal required; see below.
- An argument of `substitute()` or `quote()` is not evaluated, so a formal named only there is not
  forced.
- A formal assigned before any read, as in `function(x) { x <- 1; x }`, is never forced. The order
  is evaluation order, so `n <- n / 2` forces `n`, and a `for` variable is assigned by the loop.
- The write must happen on every path to the read. `if (flag) x <- 1 else x <- 2` assigns `x`, and
  so does a branch beside one that returns or stops, but `if (flag) x <- 1` alone does not, and
  neither does a write inside a `while` or `for` body, the right operand of `&&` or `||`, `local()`,
  or only some arms of a `switch()` (or all of them when it has no unnamed default). So `function(x, flag) { if (flag) x <- 1; x }` requires `x`.
- `x <<- 1` writes an enclosing frame, so it never assigns the formal `x`.
- A read inside a nested function forces the formal, because the closure may run, unless the
  nested function has its own parameter or assignment of that name.
- When a forced formal has a default, the formals its default reads are forced too, so in
  `function(x, y = x) y`, `x` is required.

#### `missing()` on a defaultless formal

A formal that the body tests with `missing(name)` is optional at call sites, which is how R writes an
optional argument without a default: `function(name, punct) if (missing(punct)) … else …punct…` may
be called without `punct`. The test also narrows whether the formal was supplied, like a type guard:

- On the true edge, reading `name` is an error, because R fails that read with "argument is missing,
  with no default". Writing it is legal and supplies it, as in `if (missing(punct)) punct <- "!"`.
- On the false edge the formal is supplied, and reads are ordinary.
- A diverging true edge, such as `if (missing(x)) stop(...)`, leaves the rest of the body on the
  supplied edge, and `!missing(name)` swaps the edges.
- After the branches rejoin, the formal counts as unsupplied only when it is unsupplied on both
  edges, so only definite failures are reported.
- A formal with a default is never narrowed, because reading it while unsupplied evaluates the
  default.
- As in R, `missing()` applies only to the immediate function's own formals.

### Blocks

A block evaluates to the type of its last expression, so an empty block is `NULL`. A trailing `;`
adds no expression in R's grammar, so `{ 1L; }` is `integer`.

### `return`

`return(x)` exits the enclosing function with `x`, and `return()` exits with `NULL`. It is a
control-flow construct recognized by its bare name, as `local` is, rather than a call.

- A function's return type is the union of every `return` value in its body with the body's trailing
  value, so `function() { if (c) return("foo"); 5 }` is `fn() -> character | double`.
- A body that always exits, because it ends in a `return`, or in a `repeat` that no `break` leaves,
  contributes no trailing value, so `function() return(TRUE)` is `fn() -> logical`, not
  `fn() -> logical | NULL`. A body that ends in `stop()` contributes none either, so
  `function(x) { if (x) return(1L); stop("no") }` is `fn(x: logical) -> integer`.
- The `return` expression itself yields no value where it stands, so it types as `NULL` locally and is
  not a strict-mode origin, just like `break` and `next`.
- The returned expression is checked like any other expression.
- A `return` inside a loop exits the whole function, so it abandons the loop the way `break` does.
- A `return` at the top level is an R runtime error. Its value is still checked, and joins no
  function's return type.

### `switch`

`switch(subject, a = ..., b = ..., default)` selects one branch by the subject's value at run time.
That selection cannot be modelled statically, but the call is still checked in full:

- The subject and every branch are type-checked.
- The call's type is the union of the branch value types. `NULL` joins the union unless there is a
  default branch, because an unmatched `switch` returns an invisible `NULL`. A default branch is any
  branch without a name, including the first.
- A named branch with no value falls through to the next branch, as in R, and contributes no type of
  its own.
- A branch label may be `NULL`, as R's grammar allows: `switch(typeof(x), NULL = 1, 2)` labels the
  case for the string `"NULL"`.
- With a subject `typeof(x)` on a local variable, each named branch runs only for values whose type
  its labels (together with the empty labels falling through to it) name, so `x` is narrowed inside
  the branch. A union keeps the members a label can match. An unannotated parameter tested this way
  is `Unknown`, as [guard narrowing](#guard-narrowing) describes, so `logical = if (x) ...` does not
  pin the type the other branches and callers see:
  `function(x) switch(typeof(x), logical = if (x) "T" else "F", "other")` is
  `fn(x: Unknown) -> character`.
- Exactly one branch runs, so assignments inside them fork and join exactly like the arms of an
  [`if`](#if-expressions), and a branch that cannot fall through contributes no state. A name
  introduced only inside the branches is not defined on the path where nothing matches, which R
  reports as `object 'r' not found`.
- `switch` is recognized by its bare name, so a local binding named `switch` makes the call an
  ordinary one again.

### `for`

`for (name in value) body` needs an iterable source, and binds `name` to its element type:

- A vector of any shape iterates with its scalar element type.
- A list-like `list[T]` and a dict-like `list[named: T]` iterate with `T`.
- A tuple-like or record-like list iterates with the union of its item types, so
  `for (item in list(a = 1L, b = "two")) ...` binds `item` as `integer | character`. The empty list
  iterates with `NULL`, the union of zero item types.
- A union of iterables iterates member by member.
- `NULL` is iterable and runs zero times, which is legal R. It binds the variable as `NULL`.
- `Any` iterates with `Any` items, and `Unknown` with `Unknown` items.
- An opaque nominal iterates with `Any` items, because its element shape is not visible.
- Iterating does not constrain a value whose shape is undetermined, such as an unannotated
  parameter, because R iterates both vectors and lists. The loop variable becomes `Unknown`.
- Any other source, such as a function, is an error, reported on the source expression.

The source is evaluated once, before the first iteration, and the loop does not change its type. The
loop variable is re-initialized from the source on every iteration, so an assignment to it in the
body does not carry over into the next iteration. After the loop, R keeps the variable's last value.
A read of it there is `Unknown` and is not reported, inside a function or at the top level of a
file, and not even in strict mode. Typing it as the element type is a known gap.

### `while`

A `while` loop takes a [scalar condition](#conditions), which is re-evaluated before every iteration,
so reads in the condition see the loop's joined state. The loop evaluates to `NULL`.

### `repeat`

A `repeat` loop has no condition and runs its body at least once, so a variable written in the body is
definitely assigned after the loop. It evaluates to `NULL`. A `repeat` that no `break` leaves never
completes, so code after it is unreachable and a function body ending in it contributes no trailing
value.

## Naming and scoping

### Project file order

Project files are ordered the way R collates a package: by the `Collate` field of `DESCRIPTION` if it
has one, and otherwise by the `C`-locale collation of the source file names. An earlier or later file
on this page means earlier or later in this order.

### Value names

A top-level value name in a package is global across its files:

- Any file may refer to a top-level binding in another.
- When several files define the same name, the later file wins, and both definitions are reported.
- Every top-level assignment binds a package global, wherever it sits in the statement: in a bare
  `{ }` block, in an `if`, `for`, or `while` body, in a block passed to a call such as
  `suppressWarnings({ x <- f() })`, or in the value of another assignment.

A reference from another file sees the binding's generalized exported type. Type information does not
flow back into the exporting file, so a call in one file never changes the inferred type of a
function defined in another. Within one file, a top-level name also resolves to its final exported
type, so a use placed before the definition still sees it.

A conditionally executed top-level assignment behaves like a variable slot within its own document:
a later top-level read resolves to it, and reports the maybe-undefined warning when a path without the
assignment also reaches it. A read from another item, or from another file, sees the join of every
conditional writer's type, so `for (i in 1:3) total <- i` followed by
`report <- function() total` types `report` as `fn() -> integer`. Past eight conditional writers, the
slot is `Unknown`.

Inside executable code, naming is lexical, over *mutable variable slots*, matching R's environments:
a scope holds one variable per name, and assignment mutates it.

- A function body, a `local(expr)` call, and a script's top level each form one scope, called a
  *frame*.
- A parameter introduces a slot in the function's frame, and assigning to the parameter's name writes
  that slot.
- The first `<-` or `=` assignment to a name in a frame creates its slot. Every later assignment
  writes the same slot rather than creating a new, shadowing binding.
- An assignment inside a branch or a loop body writes the enclosing frame's slot, because braces and
  control flow do not create scopes.
- A slot shadows an outer or package-global binding of the same name. But a slot that no write reaches
  at a given read does not shadow, and the read resolves outward, just as R's lookup would.
- `for` introduces a loop-local slot, re-initialized from the source on every iteration.
- `local(expr)` evaluates `expr` in a fresh child scope and takes its type. Assignments inside are
  local, while references still see the enclosing names.

Two families of calls evaluate an argument non-standardly. Each is recognized by its bare name, and
rebinding the name to a user function does not change that:

- `library(pkg)`, `require(pkg)`, and `help(topic)` read a bare first argument as a package or topic
  name, so `library(stats)` means `library("stats")`. The name is never resolved as a variable and
  never warned about. A string argument, a named first argument, or a qualified callee makes it an
  ordinary call.
- `quote(expr)`, `substitute(expr)`, `bquote(expr)`, and `expression(expr)` build an expression
  instead of running it, so an assignment written inside one binds nothing: `quote(x <- 1)` leaves `x`
  undefined. Nothing inside is checked for arity or argument types, and a name it mentions need not
  exist. Those names still count as reads, because `eval` may run the expression later.

### Name references

A name reference evaluates to the type currently bound to the name. When the name is not bound, the
checker reports it as unresolved, and treats the reference as `Unknown` from then on, so checking
continues without a cascade of follow-on errors.

### Called names

R looks up the name in a call `f(...)` as a function: a binding whose value is not a function is
skipped, and the lookup continues outward. A string call head is the same lookup, so
`"toupper"(x)` calls `toupper` exactly as `toupper(x)` does. A called name therefore resolves to the nearest binding
whose type can be a function, so this is clean:

```r
upper_names <- function(x) {
  names <- toupper(names(x))
  names(x)
}
```

- A binding whose type is definitely not a function (`NULL`, an atomic vector, a list, a record, a
  tuple, a tag, a frame, or an opaque nominal such as `matrix` or `Date`) is skipped. The lookup tries the enclosing frames' slots of the same name,
  then the package's top-level binding, then the library. A top-level `l10n_info <- NULL` therefore
  leaves `l10n_info()` calling base's function. In a package file the top level is the namespace
  itself, so past it only the library remains. A test file's top level encloses in the helpers'
  bindings and then the package namespace, and a script's in the namespace, so
  `path <- path("a")` in a test still leaves `path("b")` calling the package's `path`.
- A binding typed as a function, `Unknown`, `Any` or a nominal type is used.
- A binding with no type information yet, such as an unannotated parameter nothing has constrained
  or a parameter annotated with a type parameter `T`, may hold anything. When the body only ever
  calls it, it is a callback, and the call checks against it as usual: both
  `function(x, callback) callback(x)` and `function(format) format(1L)` infer the parameter as a
  function, even though base has a `format`. When the body also reads it as a value and an outer
  binding of the same name is a function, the call could reach either one, so it types as `Unknown`
  and constrains neither. So `function(x, names) x[names(x) %in% names]` does not make `names` a
  function parameter, and `dir <- path; dir(dir)` calls base's `dir` unchecked. A function that a
  default-attached package exports counts as such an outer binding even when no stub types it, so in
  `function(range, pretty = TRUE) if (pretty) pretty(range) else range` the call reaches base's
  `pretty` and is `Unknown`. A package import that ry has no export list for counts too, so under
  `import(fs)`, `path <- path(path, "DESCRIPTION")` calls fs's `path` and is `Unknown`.
- When no binding of the name is a function, R reports the call, and so does the checker: the error
  names the nearest binding's type. A `NULL` binding is the exception, because it is usually a
  placeholder that a package fills in later, from `.onLoad` or with `<<-`. A call on a callee whose
  type is `NULL`, such as `reject(1)` after a top-level `reject <- NULL`, or `registry$invoke()` on
  a `NULL` `registry`, is unchecked and types as `Unknown`. A callee that only may be `NULL`, such as
  `(fn(x: T) -> T) | NULL`, is still reported.
- Hover and go-to-definition on the called name follow the binding the call reaches.

`pkg::name` is never looked up this way: it names one namespace, as described next.

### Namespace access

`pkg::name` and `pkg:::name` read one name directly from a package's namespace, bypassing lexical
scoping.

- A namespace is *known* when stubs declare it. The shipped standard-library packages are known, and
  so is any namespace a project stub file declares: `stubs/dplyr.Rtypes` declares the namespace
  `dplyr` (see [stubs](/type-checking/stubs)).
- The project's own package is always known. Qualifying a name with the package you are editing, as
  `withr::defer()` does inside the package `withr`, reads the definition the checker already holds,
  and wins over a stub namespace of the same name. It reads the namespace only, so in a test file or
  a script `pathpkg::path` skips that file's own `path` binding. The name itself is not validated,
  because a package exports names its sources never bind: re-exports, S4 generics from
  `setGeneric`, datasets under `data/`, and bindings installed by `.onLoad`.
- When the stubs declare `name` in `pkg`, the qualified read has the stub's type. A project binding
  of the same name does not change it: `base::date()` calls base's `date` even when the package
  defines its own `date`. A name that only the namespace's [export manifest](#standard-library-exports) lists
  validates the same way, and types as `Unknown`.
- An unknown namespace warns, and so does a known namespace that neither declares nor lists the name
  ("not exported"). An unknown namespace stays quiet when it belongs to the package's
  [declared universe](#package-imports-namespace-and-description).
- A [conditional namespace](#conditional-stub-namespaces-datatable-dplyr-ggplot2-and-testthat), and
  any shipped export manifest outside R's own packages, stays inactive until the project uses the
  package, and a `pkg::name` read does not count as use. The read is still accepted, because
  `pkg::name` loads a package without attaching it, so a script may use a package that way alone.
  Until the package is used, the name is not validated and types as `Unknown`, so in a script with
  no `library(dplyr)` and no `DESCRIPTION`, both `dplyr::mutate` and a misspelled `dplyr::mutat`
  pass.
- A project stub that overrides a shipped name's type does not remove the name from its shipped
  namespace, so `stats::sd` stays valid under an `sd` override.
- A qualified read that could not be validated types as `Unknown`, and is a strict-mode origin.
- `:::` reads an internal name, so a name the namespace does not export is not reported there.

### Package imports (`NAMESPACE` and `DESCRIPTION`)

The package's `NAMESPACE` and `DESCRIPTION` files at the package root extend name resolution across
the whole package. Without them, analysis behaves as though both were empty.

- `importFrom(pkg, name)` makes `name` a known bare read that is never reported as unresolved. The
  read has the stubs' type for the name when there is one, and `Unknown` otherwise. An `importFrom`
  naming something a stub-described namespace does not export is an error at the import, rather than
  the warning a qualified read gets, because R refuses to load such a package.
- `import(pkg)` of a namespace the stubs describe makes exactly `pkg`'s exports known bare reads.
  When no stubs describe `pkg`, its export set cannot be known, so every otherwise-unresolved bare
  read in the package is tolerated instead of guessed at.
- A `library(pkg)` or `require(pkg)` call anywhere in the project is the script-world equivalent of
  `import(pkg)`, and follows the same rule. Because R's search path is project-wide, so is the
  tolerance. An [export manifest](/contributing/authoring-stubs#export-manifests) is enough to lift
  it; types are not required. The tidyverse, `knitr`, `rlang`, `glue`, `jsonlite`, `R6`, and the rest
  of the shipped manifests therefore keep unresolved-name detection on. A package nothing describes
  switches it off, and a two-line `stubs/<pkg>.Rtypes` of your own switches it back on.
- Attaching a meta-package activates the packages it attaches, not the names it exports.
  `library(tidyverse)` makes `mutate`, `read_csv`, and `str_to_upper` reachable because it attaches
  `dplyr`, `readr`, and `stringr`, types included where they have them.
- Attaching or importing the project's *own* package, the one named in the `Package` field of
  `DESCRIPTION`, does not switch the tolerance on, because its exports are the project's own
  definitions. Otherwise the `library(yourpkg)` that `usethis` writes into `tests/testthat.R` would
  turn off unresolved-name detection for the whole package.
- A `pkg::name` read of a namespace the stubs do not know does not warn when `pkg` belongs to the
  package's *declared universe*: a `DESCRIPTION` dependency field (`Depends`, `Imports`, `Suggests`,
  or `Enhances`), or the source namespace of any `NAMESPACE` import. Such a read types as `Unknown`.
- `useDynLib(lib, ...)` binds native symbols, which read as `Unknown`. Each listed symbol binds its
  name with the `.fixes` prefix in front, so `useDynLib(lib, hash, .fixes = "c_")` binds `c_hash`.
  With `.registration = TRUE`, R binds every routine the compiled code registers, and those names
  are known only to the compiled code, so two reads resolve: any name that starts with a non-empty
  `.fixes` prefix, such as `C_endpoints` under `.fixes = "C_"`, and any bare name that is the routine
  argument (the first positional one, or `.NAME`) of `.Call`, `.External`, `.External2`, `.C`, or
  `.Fortran`.

### Standard-library exports

The shipped stubs pair each namespace with a vendored *export manifest*: the complete list of names
the namespace really exports, generated from a live R session (see
[authoring stubs](/contributing/authoring-stubs#export-manifests)). Every manifest name is a known
global:

- A bare or qualified read of a manifest name always resolves, with no unresolved or not-exported
  warning. It has the stub's type when one exists, and `Unknown` otherwise.
- Typo suggestions for names that really are unresolved draw on manifest names as well as on typed
  declarations.

Manifests follow the way R exposes each namespace:

- The default-attached packages, `base`, `stats`, `utils`, `graphics`, `grDevices`, `methods`, and
  `datasets`, resolve bare and qualified, unconditionally.
- The packages R ships but does not attach, `tools`, `parallel`, `compiler`, `grid`, `splines`,
  `stats4`, and `tcltk`, always validate a qualified read. A bare read resolves only once the project
  attaches the package with a `library()`-family call or declares it as a dependency, exactly as in
  R.
- A conditional namespace's manifest activates together with its stubs (see
  [conditional stub namespaces](#conditional-stub-namespaces-datatable-dplyr-ggplot2-and-testthat)).
  While the namespace is inactive, its names stay unknown, bare and qualified alike.
- A read satisfied only by an import still counts as a use for the unused check. A bare read of such
  a name is not a strict-mode origin, which is a known gap; a qualified `pkg::name` read with no
  known type is.

### Replacement-form assignment

A replacement-form assignment (`x$field <- v`, `x[["name"]] <- v`, `x[[key]] <- v`, or
`x@slot <- v`) reads the base variable, applies the write, and writes the result back to the base's
slot, so the slot's type reflects the update:

- A write to a known field, `x$field <- v` or `x[["literal"]] <- v`, on a record-like `x` sets that
  field's type to the type of `v`, adding the field if it is absent. The same write on an empty
  `list()` starts a record `list{field: V}`.
- The same write on a *nominal* `x` is checked rather than applied, because a nominal type's
  representation is its invariant: `v` is checked against the field's declared type, a field the
  representation does not declare is an error, and `x` keeps its nominal type either way.
- A write with a computed key, `x[[key]] <- v` where `key` is not a literal, refines the container's
  element type instead:
  - an empty `list()` becomes a dict-like `list[named: V]`;
  - a dict-like `list[named: T]` becomes `list[named: T | V]`;
  - a list-like `list[T]` becomes `list[T | V]`, and stays list-like;
  - a record-like or tuple-like container is left unchanged, because widening a shape whose fields
    are individually known would throw away precision the code has not given up.
- A write through a chain of accessors, such as `x[[1]]$private <- v` or `x$a$b <- v`, rewrites
  each container on the way back to the root: the innermost one takes `v` by the rules above, and
  each enclosing one takes the rewritten child at its own step. A step whose position is known
  (`$name`, `[["name"]]`, or `[[1]]`) updates that field or position, and a computed `[[i]]` step
  follows the computed-key rules above. A write through a `[` or `@` step is not tracked. So after
  `old <- list(list(private = NULL)); old[[1]]$private <- list(deep_clone = 1)`, reading
  `old[[1]]$private$deep_clone` is a `double`. Writing a field of a `NULL` grows it into a one-field
  record, as R does, so `x <- NULL; x$a <- 1` makes `x` a `list{a: double}`.
- The accessor chain and the index or key expressions are ordinary reads, so their own errors surface.
  A replacement whose accessor chain has no variable at its root, such as `f(x)$a <- v`, is an
  unsupported construct: it types as `Unknown` and is a strict-mode origin.

Building a map with computed-key writes and then reading a key back gives `V | NULL`, because a
dict-like read may miss (see [`[[` on lists](#-on-lists)), so guard the read with `is.null` before a
use that needs a `V`.

### Control-flow joins

A read of a variable sees every write that can reach it, so wherever control flow merges, the
variable's possible states are joined:

- After an `if` without `else`, a variable written in the branch joins its type from before the `if`
  with the type the branch wrote.
- After an `if ... else`, a variable joins the outcomes of the two branches, and a branch that does
  not write it contributes the state from before the `if`.
- A loop body may run zero or more times, so reads inside the body and after the loop join the state
  from before the loop with the state flowing around the back edge.
- `repeat` runs at least once, so after the loop the variable has the state the body left it in.
- Joining equal types keeps the type, and joining different types gives their union. Joining with
  `Unknown` keeps the other side, so that a recursive definition, which starts from `Unknown`, can
  still reach a precise type.

So `f <- function(flag) { x <- 1L; if (flag) x <- "two"; x + 1L }` is a type error, because `x`
reads as `integer | character`, and `+` rejects the `character` member.

A variable that still holds an untyped value, usually an unannotated parameter, joins differently
when one path rebinds it. A union would let a later use of the rebound value constrain the
parameter that the other path still holds, so the joined variable is `Unknown` instead, and the
parameter stays open: `function(x, flag) { if (flag) x <- 1L; x + 1L }` is
`<T> fn(x: T, flag: logical) -> Unknown`. The default idiom `if (is.null(x)) x <- 0L` joins the
same way, so `x` reads as `Unknown` after the `if`. A parameter that only carries a bound such as
`numeric` still counts as untyped, so `if (flag) omega <- omega + m %*% m` leaves `omega` a
`T: numeric` that a caller may fill with a plain vector, and a loop's `x <- n` does not make two
parameters one type.

A variable with exactly one reaching write keeps that write's generalized type, so
`f <- function(x) x` inside a body stays `<T> fn(x: T) -> T`, and so does an alias of it: after
`g <- f`, both `g(1L)` and `g("a")` check. When writes merge at a join, the variable holds a single
type instead, so two conditionally assigned functions read as a union of both signatures. A call on
that union returns the union of their return types. An argument whose type is still open, and which a
member accepts only by narrowing it, becomes `Unknown`.

Definite assignment follows four rules:

- A read that some path reaches with no prior write reports
  [`maybe-undefined`](/reference/diagnostic-codes), because R raises `object 'x' not found` on that
  path. Inside a function, a binding of the same name outside the function would be read instead,
  which this check does not yet consider. The finding is off by default; turn it on with
  `[check] maybe-undefined = true`. Two conditions that always agree at run time are still two
  branches to the checker, so `if (ok) v <- …` followed by `if (ok) use(v)` is reported, although it
  is safe.
- A `repeat` is left through its `break` points, so one that always assigns before breaking reports
  nothing, and nothing after a `repeat` without a `break` is reachable. A branch that cannot fall
  through contributes no path.
- A read that no write can reach does not resolve to the variable at all (see the shadowing rule
  under [value names](#value-names)).
- A top-level variable is different, because a path without a write reaches the enclosing
  environment. The read then sees the name's binding elsewhere in the script or package, and that type
  joins into the slot like any other reaching write. After `p <- "word"`, the body of
  `while (cond) p <- p - 1L` is a type error, because the first iteration reads a `character`. A name
  with no such binding stays `Unknown`.

An item whose check reports an error exports `Unknown`, so one mistake does not cascade across a file.
An item with a `#:` annotation is the exception: even when its body violates the annotation, every
call site is still checked against the declared signature.

#### Unused assignments

With the `unused` check enabled, an assignment whose value no read can observe on any path reports
`unused` on the assigned name. Top-level assignments visible to the package, parameters, `for`
variables, and names starting with `.` or `_` are never reported.

A read inside a nested function is a *capture*. The closure runs after its frame has finished, so
every write to the captured name stays observable, and none of them is a dead store. That holds only
for the frame the read resolves to: a same-named binding in an enclosing frame is shadowed, not read,
and still warns.

- `f <- function() { x <- 1L; x <- 2L; y <- x; y }` warns that the first write to `x` is unused.
- `f <- function() { x <- 1L; g <- function() x; x <- 2L; g }` is clean, because both writes stay
  alive through the capture.
- `f <- function() { x <- "outer"; g <- function() { x <- TRUE; function() x } }` warns, because the
  innermost function reads the `x` of `g`.

`on.exit(expr)` reads the same way: R runs the expression when the function returns, so it observes
the last value of every name it mentions. The standard rollback guard is therefore clean:

```r
with_transaction <- function(con, body) {
  committed <- FALSE
  on.exit(if (!committed) dbRollback(con))
  body(con)
  committed <- TRUE          # read by the exit handler, not a dead store
  invisible(TRUE)
}
```

#### Names bound at run time

In a file that calls `R6Class`, the names `self`, `private`, and `super` resolve and type as
`Unknown`, because R6 creates those bindings when an object is constructed. The recognition is
syntactic, so a local binding that shadows `R6Class` is not honored, and it is scoped to the file, so
a file that defines no R6 class still warns about `self`.

Inside any function body, the S3 dispatch variables `.Generic`, `.Method`, `.Class`, `.Group`,
`.GenericCallEnv`, and `.GenericDefEnv` resolve and type as `Unknown`, because `UseMethod`,
`NextMethod`, and group-generic dispatch bind them in the method's frame and any function can be
called as a method. At the top level they are unresolved names.

A top-level `globalVariables(c("a", "b"))` or `utils::globalVariables(...)` call with literal string
arguments declares those names as bound dynamically for the whole package, which suppresses the
unresolved-name warning for them everywhere.

### Type names

`@type` and `@alias` declarations share one project-global namespace:

- A type reference may resolve to a declaration in the same file or another, and forward references
  are allowed.
- A duplicate type name is an error whatever the declaration kind: `@type` twice, `@alias` twice, and
  one of each all conflict, and every declaration involved is marked as erroneous.
- A duplicate is judged within the namespace the declaration lives in. Package files share the
  project-global namespace, so two package files that declare one name conflict. A script's
  declarations belong to that script alone, so two scripts may each declare `Thing`, while declaring
  `Thing` twice within one script is a duplicate.
- Type parameters are local binders, and shadow project-global type names.
- A type reference that resolves to nothing is an error at the referencing token, with a hint when a
  close match exists. A reference can resolve to a built-in type, a binder in scope, a project `@type`
  or `@alias` declaration, or a class declared in a stub. An undeclared name then compares like
  `Unknown` everywhere, so the typo is reported exactly once.

### Non-package documents

A file that is not a package source file, such as a script under `scripts/`, contributes neither to
the package's global value namespace nor to the project-global type namespace. A script runs top to
bottom, so its top level is one sequential lexical scope, like a function body:

- A top-level binding is visible only after its assignment, and rebinding a name changes the uses
  after it.
- A use before any script-local or package-global definition is an unresolved name. That includes a
  read inside the very statement that first binds the name, such as `x <- x + 1L` with no earlier `x`.
- A read from inside a nested function resolves against the whole document, because the closure runs
  after the frame has settled, and the last top-level binding of the name wins. That includes the
  enclosing statement's own binding, so self-recursion resolves.
- A conditional top-level write creates the document's variable slot exactly as in package files.
- A masked read, from `with` or from data.table indexing, and a read inside an opaque operator, which
  is a user `%op%` or a pipe R would reject, are never reported as unresolved. Each still counts
  as a use for the unused check, and navigation connects it.

Scripts are type-checked like package files, against the package-global values and project-global
types, plus their own local bindings and type declarations:

- A script may resolve package-global value names and project-global `@type` and `@alias` names.
- A script's top-level value bindings and type declarations are visible neither to package files nor
  to other scripts.
- A package file and a script may reuse the same top-level value or type name without conflict.
- Duplicate top-level value names inside a script do not produce the package-global duplicate-binding
  warning; they behave like ordinary rebinding.

Files directly under `tests/testthat/` are test files, except that a file whose name starts with
`helper` or `setup` is a helper file. testthat sources the helper files into one environment whose
parent is the package namespace, and runs each test file in its own child of that environment. A
test or helper file therefore reads the package's names but never adds to them:

- A test or helper file resolves a name first in its own sequential scope, exactly like a script,
  then in the helpers' namespace, then in the package-global namespace.
- The helpers' namespace holds the top-level bindings of every helper file, the last one in project
  order winning. A test file's own bindings are invisible to every other test file, so a name one
  test file defines and another reads is an unresolved name.
- Inside a closure, a test file's name resolves to the binding written by the same top-level
  statement when there is one, and otherwise to the file's last binding. Each `test_that()` block
  is one statement, so `f <- function() g()` calls the `g` its own block defines even when a later
  block defines another `g`.
- A test file's bindings are invisible to package files, so `names <- letters[1:4]` in a test does
  not change what `names` means under `R/`, and a package file reading a name that only a test
  defines is an unresolved name.
- A test binding and a package binding of the same name are not duplicates, and neither are two test
  bindings. Test files' `@type` and `@alias` declarations are file-local, like a script's.

## Data frames and non-standard evaluation

R evaluates some arguments inside a data frame's own environment, where a bare name is a column
reference that no lexical scope can see. In these *masked* positions, a read that resolves to no
binding is treated as a column reference: a silent `Unknown`, with no unresolved-name warning and no
strict-mode origin. The recognized masks are:

- A single `[` bracket whose subject types as the `data.table` nominal masks all of its index
  arguments, so `DT[speed > 20]` and `DT[, x]` are column references.
- A `[` call carrying an unambiguous data.table signature masks all of that bracket's index arguments,
  even when the subject's type is unknown. The signatures are a `by =` or `keyby =` argument, a `:=`
  column assignment, a `.()` list call, and the specials `.SD`, `.N`, `.I`, `.BY`, `.GRP`, and
  `.EACHI`.
- The base masking family, `with()`, `within()`, `subset()`, and `transform()`, masks every argument
  except the data. Which argument is the data follows R's own matching: a named argument claims its
  formal first (`data` for the `with` pair, `x` for `subset`, `_data` for `transform`), and the
  remaining positional arguments fill what is left, so `with(speed > 20, data = frame)` masks the
  condition. The `base::` spelling masks exactly like the bare one, while another package's export of
  the same name masks nothing.
- A call to a [`@masked`](#conditional-stub-namespaces-datatable-dplyr-ggplot2-and-testthat) stub
  declaration.

A name inside a mask that does resolve, such as a local variable or a function like `sum`, keeps its
ordinary resolution and typing, because data.table itself falls back to the lexical scope for names
that are not columns. Inside any single `[`, a `..name` read is data.table's way to name the
variable `name` from the enclosing scope, so it resolves to `name`. Base indexing such as `m[i, j]`
carries no data.table marker, so it keeps full lexical checking. A function written inside a masked argument is masked too, because it is created
inside the data's frame.

### data.table result classes

A bracket with a data.table signature but an unknown subject types as `Unknown`. When the subject
*is* the `data.table` nominal, the class of the result follows from the bracket's syntax, even though
the columns are unknown. Here `j` is the second positional slot or a `j =` argument:

```r
DT[i]                        # data.table: a row filter or a join returns a table
DT[, x := 1]                 # data.table, returned invisibly
DT[, .(m = mean(x))]         # data.table: `.()` and `list()` build a table
DT[, sum(x), by = g]         # data.table: a grouped result is always a table
DT[, x]                      # Unknown: the shape would need column knowledge
```

Anything not covered above, such as an ungrouped computed `j` or a `with =` form, is `Unknown` and a
strict-mode origin.

The class is a real type. It flows through chains, so `DT[a > 1][, .(m = mean(b)), by = g]` stays a
`data.table` from end to end, and it satisfies or violates annotations and parameter types like any
other. Column-level knowledge is out of scope for the `data.table` nominal: element types, membership
checks, and the evolution of columns through `:=` are not tracked. A `data.table` whose columns are
known, such as the result of `fread`, and the built-in DataFrame below track all three.

### DataFrames

A `DataFrame` is ry's built-in table. Its type lists its column vectors, written like a `list{...}`
record with `DataFrame` in front:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
price_of <- function(prices: DataFrame{id: integer[], price: double[]}) -> double[] prices$price
```

</TabItem>
<TabItem label="Comments">

```r
#: fn(prices: DataFrame{id: integer[], price: double[]}) -> double[]
price_of <- function(prices) prices$price
```

</TabItem>
</Tabs>

A column is always a vector, so a scalar column type broadens: `DataFrame{id: integer}` is
`DataFrame{id: integer[]}`. A bare `DataFrame` is one whose columns are unknown, and every column
reference on it is a silent `Unknown`. Three more types share this shape: `LazyFrame{...}` is a
query plan, `GroupBy{k: K; a: A}` is a grouped DataFrame whose key columns come before the
semicolon, and `LazyGroupBy{...}` is a grouped plan. A `data.table` with known columns is written
`data.table{...}` in the same way.

A DataFrame is no `data.frame`: its run-time class is `"DataFrame"` alone, so passing one to a
`data.frame` parameter is a type error. `as.data.frame()` converts it and loses the column types,
because a base data frame's columns are not typed, while `as.data.table()` and `as.DataFrame()`
keep every column. A DataFrame satisfies a `list` parameter, because `lapply()`, `Map()` and
`Filter()` call `as.list()`, which turns it into the list of its columns. This is unsound for a
function that indexes its `list` argument with `[`, which on a DataFrame selects rows; overloads
that take a DataFrame directly would close the gap.

`DataFrame()` builds one. Each named argument becomes a column of its vector type, and an unnamed
variable keeps its name:

```r
sales <- DataFrame(team = c("a", "b"), amount = c(1, 2))   # DataFrame{team: character[], amount: double[]}
```

An unnamed computed argument, a repeated name, or `...` leaves the columns unknown, and so does a
project's own function named `DataFrame`, which shadows the builtin.

#### Verbs

Each verb of the [DataFrame API](/guides/dataframes) types as a new column list, computed from the
syntax of its arguments. A string argument names a column, and any other argument is an
expression built from `col("x")`:

| Call | Result |
| --- | --- |
| `DataFrame.select(df, ...)` | one column per argument |
| `DataFrame.with_columns(df, ...)` | `df`'s columns, each argument replacing the column of its name or added after them |
| `DataFrame.filter(df, ...)`, `DataFrame.sort(df, ...)`, `DataFrame.head(df)`, `DataFrame.tail(df)` | the columns of `df` |
| `DataFrame.group_by(df, ...)` | `GroupBy{keys; rest}`: the key columns, then `df`'s other columns |
| `GroupBy.agg(groups, ...)` | `DataFrame{keys, aggregates}` |
| `DataFrame.join(df, other, on, how)` | `df`'s columns, then `other`'s non-key columns, with `suffix` added to a name `df` already has; `"semi"` and `"anti"` keep `df`'s columns only |
| `DataFrame.join_asof(df, other, on, by)` | as a left join on the `by` columns and then `on` |
| `DataFrame.lazy(df)`, `LazyFrame.collect(plan)` | the same columns, as a `LazyFrame` or a `DataFrame` |
| `DataFrame.read_csv(path)`, `LazyFrame.scan_csv(path)` | the columns of the file, sniffed as for `fread` (see [Reading files](#reading-files-and-datatables-functions)) |

Every `LazyFrame.` verb types like its `DataFrame.` namesake and returns a `LazyFrame`.

An expression's column is named by `Expr.alias` or by the argument's name, and otherwise by the
first column it reads, as Polars names it. Its type follows R's rules for the operation:

| Expression | Column type |
| --- | --- |
| `col("x")` | the type of `x` |
| `a + b`, `a - b`, `a * b`, `-a` | `integer` when both sides are `integer` or `logical`, otherwise `double` |
| `a / b`, `a ^ b`, `Expr.mean`, `Expr.median`, `Expr.std`, `Expr.var`, `Expr.cor` | `double` |
| comparisons, `&`, `\|`, `!`, `Expr.is_null` | `logical` |
| `Expr.sum` | `integer` for an `integer` or `logical` column, otherwise `double` |
| `Expr.min`, `Expr.max`, `Expr.first`, `Expr.last`, `Expr.head` | the type of the column |
| `Expr.len()`, `Expr.count` | `integer` |
| `Expr.if_else(test, yes, no)` | the type `yes` and `no` share |
| `lit(value)`, a plain R value | the value's type |

A string or `col("x")` naming a column the subject does not have is a type error on that string,
and so is a join key missing on either side. Inside `GroupBy.agg`, an expression that reads a
column must aggregate it, since `agg` needs one value per group. The exception is an item that is
exactly `Expr.head(n)`, whose up to `n` values per group become rows; `Expr.head` inside a larger
expression is the same error:

```text
type-mismatch

  x `units` gives one value per row, but `agg` needs one value per group. Aggregate it, for example with `Expr.sum` or `Expr.first`
    --[a.R:10:62]
 10 | bad2 <- sales |> DataFrame.group_by("region") |> GroupBy.agg(col("units"))
    |                                                              ^^^^^^^^^^^^
```

An argument whose expression the checker cannot read, such as a variable holding an `Expr`, leaves
the result's columns unknown.

#### data.table queries

DataFrames also accept data.table's bracket syntax for compatibility, and the checker types it on
a DataFrame and on a `data.table` whose columns it knows, such as the result of `fread`. The rest
of this section describes that syntax.

`f[i, j, by]` evaluates `i`, `j`, and `by` with the frame's columns in scope, as data.table does. A
bare name that is a column types as that column's vector, ahead of any lexical binding of the same
name. A name that is no column keeps its lexical type, and a name that is neither is reported:

```text
unresolved

  ! the frame `sales` has no column `amuont`, and nothing else defines that name. Did you mean `amount`?
   --[a.R:6:13]
 6 | print(sales[amuont > 1])
   |             ^^^^^^
```

This is an `unresolved` warning rather than a type error, because R looks a non-column up in the
enclosing scope, so only a name nothing defines is certainly wrong. `.N`, `.GRP`, and `.NGRP` are
`integer`, `.I` is `integer[]`, and `.SD` is the source frame without its group columns, or the
columns `.SDcols` selects (see [Every column at once](#every-column-at-once)). A called
name, such as `sum` in `sum(amount)`, is looked up as a function and never reads a column. A
`..name` read is the variable `name` from the enclosing scope, never a column, and a bare `..name`
as `j` selects the columns it names, which makes the result a `DataFrame` with unknown columns.

The result of the query follows from its arguments:

| Query | Result |
| --- | --- |
| `f[i]`, `f[order(x)]` | the frame type of `f` |
| `f[, x]`, with `x` a column | the column vector |
| `f[, sum(x)]` | the value of `j`, for an atomic or `NULL` value; otherwise `Unknown` |
| `f[, .(a = e1, b = e2)]` or `list(...)` | `DataFrame{a: T1[], b: T2[]}` |
| any `j` with `by` | the group columns first, then the `j` columns |
| `f[, y := v]` | `f` with `y` added, or with its type replaced |

In a `.()` or `list()` `j`, an unnamed bare column keeps its name, `.N` becomes the column `N`, and
any other unnamed item is named by its position, as data.table names it: `f[, .(id, price * 2)]` is
`DataFrame{id: integer[], V2: double[]}`. Under `by`, a bare `.N` as `j` is the column `N`, and any other
unnamed computed `j` becomes the column `V1`. The groups can be written `by = g`,
`by = .(g, h)`, `by = c("g", "h")`, or `by = "g"`, and `keyby` works the same way. A group named
in a string must be a column, so a misspelled one is a type error:

```text
type-mismatch

  x the frame `sales` has no column `taem`. Did you mean `team`?
   --[a.R:8:44]
 8 | print(sales[, .(total = sum(amount)), by = "taem"])
   |                                            ^^^^^^
```

A query's row index `i` must be logical or numeric when its type is known. A frame as `i` is reported
with a hint to add `on =`, because without it data.table joins on a key that ry cannot see. Queries
chain, and each step sees the columns the step before it produced:

```r
sales[amount > 0][, .(total = sum(amount)), by = team][order(-total)]
# DataFrame{team: character[], total: double[]}
```

#### Every column at once

`f[, lapply(.SD, g)]` applies `g` to each column of `.SD`, so its result has one column per column
of `.SD`, each typed as `g` applied to that column alone. Under `by`, the group columns come first:

```r
sales <- DataFrame(team = c("a", "b"), units = c(1L, 2L), price = c(1.5, 2.5))
sales[, lapply(.SD, sum), by = team]
# DataFrame{team: character[], units: integer[], price: double[]}
sales[, lapply(.SD, round, digits = 1), .SDcols = "price"]
# DataFrame{price: double[]}
```

Because each column is checked on its own, a function that does not fit one column is reported
with that column's name, not against the union of all column types:

```text
type-mismatch

  x this function is passed `character[]`, but its parameter `v` is used as a numeric value (`integer` or `double`), for the column `team` of `.SD`
   --[main.R:2:27]
 1 | sales <- DataFrame(team = c("a", "b"), units = c(1L, 2L), price = c(1.5, 2.5))
 2 | print(sales[, lapply(.SD, function(v) v * 2)])
   |                           ^^^^^^^^^^^^^^^^^
```

A finding that every column causes is about `g` itself, so it is reported once and without a
column name.

`.SDcols` selects `.SD`'s columns, in the frame's order, in any of these forms:

| `.SDcols` | Columns of `.SD` |
| --- | --- |
| `"a"`, `c("a", "b")` | the named columns |
| `a:b` | the columns from `a` to `b` |
| `is.numeric`, `is.integer`, `is.double`, `is.character`, `is.logical` | the columns of that type |
| any of the above after `!` or `-` | the other columns |

A named column must exist, so a misspelled name in a string or a range is a type error on that
name. `.SDcols` names `.SD`'s columns exactly, so a group column it names stays in `.SD`, and the
result then repeats that column's name, as data.table repeats it. A frame type cannot hold two
columns of one name, so such a result has unknown columns, as does any other `.SDcols` form, such
as `patterns()` or column positions.

`c("a", "b") := lapply(.SD, g)` assigns the applied columns to the named ones in order, and
`(c("a", "b")) := ...` does the same. Column names can also come from a variable, in `.SDcols = cols`
and `(cols) := ...`, when the variable is assigned once, in the same function, to a string or a
`c()` of strings:

```r
relabel <- function(sales) {
  cols <- c("units", "price")
  sales[, (cols) := lapply(.SD, as.character), .SDcols = cols]
}
```

A misspelled name is then reported on its string in the assignment. A variable written more than
once, changed in place (`cols[2] <- "team"`), or assigned in another top-level statement names
columns ry cannot see, so the result has unknown columns.

#### Column updates

`f[, y := v]` is copy-on-write: the statement rebinds `f` with `y` added, or with `y`'s type replaced.
An alias taken earlier keeps the old type, and `y := NULL` removes the column:

```r
sales <- DataFrame(team = c("a", "b"), amount = c(1, 2))
before <- sales
sales[, tax := amount * 0.2]    # sales: DataFrame{team: character[], amount: double[], tax: double[]}
before$tax                      # error: the frame `before` has no column `tax`. Its columns are `team`, `amount`
```

The left side may also be a string, `c("a", "b")` paired with a `list()` of values, or the functional
form `` `:=`(a = v, b = w) ``. Any other left side, such as `(columns) := v`, makes the columns
unknown, silently. `f$y <- v` and `f[["y"]] <- v` update a column in the same way.

data.table coerces a value written into an existing column to that column's type, so the column
keeps its type whenever the value does not replace it whole. That is the case with a row index, as in
`f[id > 1, price := 0L]`, with `by`, and with a literal value, as in `f[, price := 0L]`. A value that
replaces the whole column, as in `f[, price := 1:3]`, replaces its type, and a column the statement
creates takes the value's type. Only a literal counts as a single value: a call such as `sum(x)` also
returns one value at runtime, but the checker types `f[, price := sum(id)]` as a replacement.

A value the column keeps its type for must fit it. Strings written into a logical or numeric column
are parsed, so a string that is no number becomes `NA`, and a literal with a fraction written into an
integer column is truncated. data.table only warns about either, but each is a type error here:

```text
type-mismatch

  x column `amount` holds `integer[]`, so this `character` value is parsed as a number, and a string that is not one becomes `NA`
   --[a.R:7:27]
 7 | events[id > 1L, amount := "none"]
   |                           ^^^^^^
```

A number written into a string column is converted without loss, so it is accepted, and a value that
replaces the whole column, such as `f[, amount := as.character(id)]`, replaces its type instead.

The rebinding applies only to a name the current scope already binds: any top-level name, or a
function's own local or parameter. A `:=` on any other name, such as a global updated inside a
function, creates no local binding, so the name keeps resolving to its original definition for
goto-definition, references, and rename. That is what data.table code, which updates a shared table
by reference, needs. When that name is a global frame, later reads in the same function still see
the updated columns, while other top-level code keeps the frame's declared type:

```r
sales <- DataFrame(team = c("a", "b"), amount = c(1, 2))
with_tax <- function() {
  sales[, tax := amount * 0.2]
  sales$tax                       # double[]
}
unchanged <- sales                # DataFrame{team: character[], amount: double[]}
```

#### Joins

`x[i, on = conditions]` joins two frames. Each condition pairs a column of `x` with a column of `i`
through `==` or one of the orderings `<`, `<=`, `>`, `>=`, and every form data.table documents is
typed:

| Form | Conditions |
| --- | --- |
| `"id"`, `.(id)`, `c("id")` | `id == id` |
| `"a==b"`, `.(a = b)`, `c(a = "b")` | `a == b` |
| `"id,t>=lo"`, `c("id", "t>=lo")` | `id == id` and `t >= lo` |
| `.(id, t >= lo, t < hi)` | `id == id`, `t >= lo`, and `t < hi` |

Each column a condition names must exist on its side. A missing column is a type error, and in a
condition string the error points at the name inside the string:

```text
type-mismatch

  x the frame `windows` has no column `low`. Its columns are `id`, `lo`, `hi`
   --[a.R:5:38]
 5 | print(events[windows, on = "id, t >= low"])
   |                                      ^^^
```

The two columns of a condition must hold values the join can compare, as data.table requires: numbers
with numbers (an integer column joins a double one), strings with strings, and logicals with
logicals. Any other pair is a type error, and so is an ordering on a column of strings, because only
`==` joins strings:

```text
type-mismatch

  x the join condition `t > label` compares numbers, but `label` is `character[]`. Only `==` joins strings.
   --[a.R:6:32]
 6 | print(events[names, on = .(t > label)])
   |                                ^^^^^
```

A factor column is typed `Any`, so it is not checked. `roll =` keeps the type of the join, and
combining it with an ordering condition is a type error, since a rolling join needs every condition
to be `==`.

The result follows data.table's layout. First come `x`'s columns, where a column a condition compares
takes the values, and so the type, of `i`'s column in its first condition. A further condition on the
same column `t` adds a column `t.1`, then `t.2`, carrying that condition's values of `i`. Last come the
columns of `i` that no condition uses, renamed `i.name` when `x` has the same name. A name that still
repeats takes the first free numeric suffix, as R's `make.unique` gives it:

```r
events <- DataFrame(id = 1:3, t = c(1, 2, 3), v = c("a", "b", "c"))
windows <- DataFrame(id = 1:2, lo = c(0, 1), hi = c(2L, 5L))
events[windows, on = .(id, t >= lo)]           # DataFrame{id: integer[], t: double[], v: character[], hi: integer[]}
events[windows, on = .(t >= lo, t < hi)]       # DataFrame{id: integer[], t: double[], v: character[], t.1: integer[], i.id: integer[]}
```

Inside the join, `j` can also read either side by prefix: `x.t` is `x`'s own `t`, which the join
replaced with `i`'s values, and `i.lo` is the joined frame's `lo`. This works for a compared column
and for a column whose name does not clash. A prefixed name the side does not have is reported like
any other missing column, and a prefixed name in a query that is no join ry can see is a silent
`Unknown`. A join whose `i` is not a frame, or whose `on` is some other form, such as a variable
holding the conditions, is `Unknown`.

`by = .EACHI` runs `j` once per row of `i`. The result's group columns are the compared columns, in
the order of their conditions and named as in the join's layout, followed by `j`'s columns. Within
`j`, a column carrying `i`'s values is that row's single value, while a column of `x` is the vector of
the rows the row matched, and `.N` counts those rows:

```r
counts <- DataFrame(t = c(1, 2, 3), v = c(10L, 20L, 30L))
counts[windows, on = .(t >= lo), .(n = .N, total = sum(v), wide = if (hi > 2L) "yes" else "no"), by = .EACHI]
# DataFrame{t: double[], n: integer[], total: integer[], wide: character[]}
```

The `if` on `hi` is accepted because `hi` is one value per row of `i`; the same `if` on `v` is a type
error, since `v` is a vector.

#### Columns

`f$x`, `f[["x"]]`, and `f[[1L]]` type as the column. A missing column is a type error that names the
frame and suggests the closest column, like a missing record field:

```text
type-mismatch

  x the frame `sales` has no column `amuont`. Did you mean `amount`?
   --[a.R:7:13]
 7 | print(sales$amuont)
   |             ^^^^^^
```

#### Reading files and data.table's functions

`fread`, `rbindlist`, `melt` and `dcast` return a `data.table`, and the checker sharpens its
columns from the arguments it can see, so the result is a `data.table{...}`. A DataFrame satisfies a
`data.table` parameter, so data.table's functions accept one.

`fread("data/prices.csv")` types with the columns the file has. ry sniffs the head of every `.csv` and
`.tsv` file in the project (gitignored ones included) with the same rules as the runtime's reader,
which follow `fread`: the header, the separator, and each column's type out of `logical`, `integer`,
`double` and `character`. The path is relative to the project root. `fread(text = "...")`, and an input
holding a line break, sniff the literal itself.

```r
prices <- fread("data/prices.csv")   # data.table{id: integer[], ticker: character[], price: double[]}
cheap <- prices[prce < 10]           # warning: the frame `prices` has no column `prce`, ... Did you mean `price`?
```

`select`, `col.names` and `stringsAsFactors = TRUE` are applied to the sniffed columns. A computed
path, a file the project does not have, and any other argument that changes the columns (such as
`colClasses` or `skip`) give a `data.table` with unknown columns. `DataFrame.read_csv` and
`LazyFrame.scan_csv` sniff their file the same way.

The other functions follow data.table's rules:

| Call | Type |
| --- | --- |
| `setnames(f, old, new)`, `setnames(f, new)` | renames the columns of `f` from here on; `old` must name columns of `f` unless `skip_absent = TRUE`, and `new` alone must name every column |
| `setcolorder(f, c("b", "a"))` | moves the named columns of `f` to the front from here on |
| `setkey(f, a, b)`, `setorder(f, a, -b)`, `setkeyv(f, cols)`, `setorderv(f, cols)` | `f` unchanged; each named column must exist |
| `rbindlist(list(f, g))` | binds by position; each column takes the widest type of its pieces (`logical` < `integer` < `double` < `character`, and a factor with strings stays a factor) |
| `rbindlist(..., use.names = TRUE)`, `rbindlist(..., fill = TRUE)` | binds by name; `fill` adds the columns only some pieces have |
| `rbindlist(..., idcol = "source")` | adds a first column of each piece's name (`character[]`), or its position (`integer[]`) when the list is unnamed |
| `melt(f, id.vars, measure.vars)` | the id columns, `variable: factor` (`character[]` with `variable.factor = FALSE`), and `value` of the measures' widest type; either list defaults to every other column |
| `dcast(...)` | `data.table` |
| `fifelse(test, yes, no, na)` | a vector of the type `yes`, `no` and `na` share; integers and doubles widen to doubles, a bare `NA` fits any type, and any other mix is a type error |
| `shift(x)`, `nafill(x)`, `fcoalesce(x, ...)` | the type of `x` |
| `rleid(...)`, `x %chin% table`, `between(x, lower, upper)`, `uniqueN(x)` | `integer[]`, `logical[]`, `logical[]`, `integer` |
| `tstrsplit(x, split)` | `list[character[]]` |

`setnames` and `setcolorder` change their subject by reference, so ry treats them like `:=`: the name
holds the new columns after the call.

### Conditional stub namespaces: data.table, dplyr, ggplot2 and testthat

Four packages have shipped stubs that do not join name resolution by default:

- `data.table`, with the `data.table` nominal, `fread`, and the `set*()` family;
- `dplyr`, with the `@masked` verbs, the joins, the tidy-select helpers, and the rest of its
  vocabulary;
- `ggplot2`, with the `ggplot` and `gg` nominals, `+.ggplot`, the geoms and scales, and the `@masked`
  `aes`;
- `testthat`, with the expectations and `test_that`.

R does not attach these packages by default either, and their names must not suppress typo warnings
in projects that never use them. So a conditional namespace activates only when:

- the project declares the package, through a `DESCRIPTION` dependency field or a `NAMESPACE`
  `import` or `importFrom` that names it;
- any project file attaches it, with a `library()`, `require()`, `requireNamespace()`, or
  `loadNamespace()` call whose package argument is a literal name or string; or
- the project ships its own `stubs/<pkg>.Rtypes` override for the namespace.

While a namespace is inactive, it behaves exactly like any package the stubs do not describe.

The shipped dplyr verbs preserve their data argument's class, as `<T> fn(.data: T, ...) -> T`, so a
native-pipe chain keeps its class from end to end: `fread(path) |> mutate(r = a / b)` stays a
`data.table`, and every column reference inside those verbs' `...` stays masked.

A project stub can declare its own masking function with the `@masked` attribute:

```
filter : @masked fn(.data: Any, ...: Any) -> Any
mutate : @masked fn(.data: Any, ...: Any) -> Any
```

A call to a `@masked` name, bare or as `pkg::name`, evaluates the arguments absorbed by its `...`
rest parameter inside the data's frame. An argument that matches a formal declared before the `...`,
such as `.data` above, resolves normally. A declaration whose only parameter is `...`, such as
`join_by : @masked fn(...: Any) -> Any`, masks every argument. A locally defined function of the same
name masks nothing. `@masked` on a declaration that is not variadic is a stub error.

## Object systems (S3, S4, R6)

The checker covers the parts of R's object systems that are written down as declarations, and stays
out of the parts decided at run time from a value's class attribute:

- An operator on a nominal type dispatches statically; see
  [operator methods on a class](#operator-methods-on-a-class).
- A directly called S3 method, such as `speak.dog(x)`, is an ordinary call, checked against that
  function's own signature.
- `UseMethod("speak")`, and any call to an S3 generic, gives `Any`, with no strict-mode finding.
- `structure(list(...), class = "dog")` keeps the argument's type, because a `class` attribute is
  data, not a type, so the record's fields stay checkable. A `dim` attribute is the exception: it
  makes the value an array, whose shape is not tracked, so such a value is `Unknown`.
- `setClass`, `setGeneric`, `setMethod`, and `new` are not modeled, so `new(...)` is `Unknown`.
- `x@slot` reads an S4 slot and types as `Unknown`, and is a strict-mode origin. The subject
  expression is still inferred and counts as a read for naming, the unused check, references, and
  rename. A slot write `x@slot <- v` is an ordinary
  [replacement-form assignment](#replacement-form-assignment) of its base variable.
- `R6Class(...)`, `$new(...)`, and R6 fields and methods are not modeled and are `Unknown`; `self`,
  `private`, and `super` are covered under [names bound at run time](#names-bound-at-run-time).
  Strict mode does not report R6 values yet, because `R6Class` is known only from an export list.

### Declaring a checked type for your own classes

A class is a [nominal type](#nominal-types) with a representation. Wrapping the constructor is
enough to get slot types, constructor arity, and field access checked on an S4 or R6 class:

```r
type Point = list{x: double, y: double}

setClass("Point", representation(x = "numeric", y = "numeric"))

make_point <- function(x: double, y: double) -> Point {
  @Point(new("Point", x = x, y = y))
}

norm2 <- function(p: Point) -> double sqrt(p$x^2 + p$y^2)

norm2("nope")   # type-mismatch: the argument is not a `Point`
make_point(1)   # type-mismatch: a required argument is missing
```

</TabItem>
<TabItem label="Comments">

```r
#: @type Point {list{x: double, y: double}}

  #: @new Point

}

#: fn(p: Point) -> double
norm2 <- function(p) sqrt(p$x^2 + p$y^2)

```

The `setClass` call stays opaque, and the annotation is what the checker reads. Operators on the
class work the same way: declare `Arith.Point`, and `p1 + p2` is checked. Method dispatch, on the
other hand, needs the argument's class at the call site, and inside an unannotated
`function(x) speak(x)` that class is not known.

## Strict mode

Strict mode is an opt-in check, switched on with `[check] strict` and off by default. It changes
nothing about inference and adds no typing rules. It reports the places where the checker could not
determine a type, together with the [parameters nothing constrains](#untyped-parameters), and it
escalates unresolved references to errors.

A value typed `Any` by an annotation or a single declaration is an intentional opt-out and never
produces a strict finding. A call that falls back to an overload set's `Any` candidate is the
exception, because the fallback marks a call the declarations could not describe.

Strict mode also reports each read that the
[attached-package tolerance](#package-imports-namespace-and-description) silenced, and points at the
[stub](/type-checking/stubs) that would make it checkable. Without that, a clean run after
`library(unknownpkg)` would look the same as a run that checked nothing.

### Unresolved references escalate to errors

An unresolved reference carries the `unresolved` code, and comes in three kinds:

- a bare name the resolver cannot find in the package, its imports, or the builtins;
- an unknown package namespace in `pkg::name`;
- a name that a known namespace does not export, read as `pkg::name`.

Outside strict mode these are warnings; under strict mode they are errors, whether strict mode comes
from the configuration or from the per-file directive. Turning strict mode on can therefore raise the
severity of findings without changing their count, which matters when a `--min-severity error` gate
reads them.

Two `unresolved` findings are errors in every mode, because they stop the package from loading: a
`NAMESPACE` `importFrom` naming something the namespace does not export, and an `export()` naming
something that is not in the package's namespace. That namespace holds every top-level binding of a
package file, including each target of a chained assignment such as `memoise <- memoize <-
function(f) f`, and every imported name, so a package may re-export what it imports: a name from an
`importFrom`, such as `importFrom(magrittr, "%>%")` with `export("%>%")`, or from an `import(pkg)`
whose namespace exports it. An `import(pkg)` of a namespace without stubs may supply any name, so it
silences the check.

### Per-file directive

A plain top-level comment sets one file's typing mode, overriding the configured `[check]` switches
in both directions:

```r
# typing: strict
```

- `off` silences the file's type errors and strict diagnostics, even when the configuration checks
  types. `on` opts a single file into type checking, with strict mode off. `strict` also switches on
  strict mode for the file.
- The comment must hold nothing but the directive: `# typing: off  # reason` is reported as an
  unknown directive.
- A directive must be a comment between top-level expressions. Inside any expression, such as a
  function body or an `if` block, it is ignored.
- The older `#: @strict` form is still supported: `#: @strict` means `# typing: strict`, and
  `#: @strict off` means `# typing: on`.
- If a file has several directives, the last one wins. A `typing:` comment with any other value is
  reported as an error.
- The directive changes only which diagnostics are published for the file. Inference and every other
  check are untouched, so hover and the other editor features keep working under `off`.

### A package file's top level

Under strict mode, the top level of a library file may hold only definitions, so that loading the
package binds names and registers classes and does nothing else. A library file is a file in the
package's `R/` directory. Every other file is an entry: a script that `ry run` starts, a test file
or helper under `tests/`, and each console command. Entries may run anything at their top level.

A top-level statement of a library file is a definition when it is one of these:

- `name <- value` or `name = value` whose value is a function, a class definition form, or a
  constant (below), including a chain such as `a <- b <- function(x) x`. zeallot's
  `c(a, b) %<-% value` counts the same way.
- A call to a class definition form: `setClass`, `setClassUnion`, `setGeneric`, `setMethod`,
  `setReplaceMethod`, `setValidity`, `setOldClass`, `setAs`, `setRefClass`, or `R6Class`, bare or
  namespace-qualified. Their arguments are not inspected.
- A call that imports a package (`library`, `require`, `requireNamespace`, `loadNamespace`,
  `attachNamespace`) or only declares something (`globalVariables`, `suppressForeignCheck`,
  `delayedAssign`, `makeActiveBinding`, `.S3method`, `registerS3method`).
- A `type` or `alias` definition, or an expression with no effect, such as `NULL`.
- An `if` whose condition has no effect, or is an import call such as
  `requireNamespace("x", quietly = TRUE)` (negated or not), and whose branches are definitions, or a
  `{` block of definitions.

A constant's initializer must have no effect. Literals, names, `pkg::name`, function literals,
formulas, and the built-in operators have none. A call has none when its function is declared pure
and its arguments have none; the arguments of `quote`, `expression`, `alist` and `substitute` are not
evaluated, so they are not inspected. Inside `local()`, assignments and loops touch only the local
environment and are allowed, but a call to a function bound inside that `local()` is an effect,
because nothing declares it pure.

Anything else is an effect, which is a `strict` error reported on the expression that causes it.
Only the first effect of a statement is reported. The effects are:

- a call to a function that is not declared pure, including a `%op%` operator;
- a call whose function is computed, such as `handlers[[1]]()`;
- a `for`, `while` or `repeat` loop outside `local()`;
- `<<-`, which assigns outside the package namespace;
- a replacement such as `names(x) <- value` or `x$field <- value`, which changes a value after its
  definition;
- an assignment nested inside an expression, such as `f(x <- 1)`;
- `?`, which looks up help.

#### Purity

A function is pure when calling it has no effect beyond returning a value, whatever its arguments.
Purity is declared and never inferred, and the declaration is trusted: ry does not check the body.
A project function is declared pure with a `#: @pure` comment line above its definition or an inline
`@pure` before `function` (or `\(x)`), and a stub declares one with `name : @pure fn(...)`. With
inline annotations turned off, an inline `@pure` declares nothing and carries the `inline-annotation`
warning. The
standard library's stubs mark base R's pure functions, such as `paste0`, `seq_len` and `sum`, and
`c`, `list`, `switch`, `expression` and `alist` are pure without a stub.

A project definition of a name shadows the stub's declaration, so a package's own `paste0` is pure
only if it is marked. A function defined inside a condition, such as `if (cond) f <- function() 1`,
is never pure, because which definition exists depends on the condition.

Purity belongs to each definition alone. Adding `cat()` to the body of a function marked `@pure`
re-checks only that function, and removing the marker re-checks only the statements that call it.

#### Lazy constants

`ry load` binds a library file's functions lazily, and under strict mode its constants too: a constant
whose name has exactly one top-level writer becomes a promise that evaluates its initializer on first
use. Every package name the initializer mentions must also be written exactly once, by a statement
earlier in collation order, and otherwise the constant runs eagerly in order. Because the initializer
has no effect and what it reads cannot change after it, evaluating it later gives the value a load
would have computed. A reload binds the constant again whenever anything its initializer reaches changed, such
as the body of a pure function it calls.

### Untyped parameters

A parameter without an annotation is reported when nothing constrains it, because it then accepts
any value unchecked. That is the case when its inferred type is `Unknown`, or is still a fresh type
variable of its own function that neither another parameter nor the return type mentions:

```r
describe <- function(x) cat("a value\n")
```

```text ry check typing strict
x strict mode: parameter `x` has no type. How the function uses it does not determine one, so any
  value is accepted unchecked. Annotate it, as in `x: TYPE`
```

A type variable that the signature mentions twice is genuine polymorphism, so `function(x) x`
(`<T> fn(x: T) -> T`) and `function(flag, a, b) if (flag) a else b` are not reported. Neither is a
constrained variable such as `<T: numeric>`, a variable tied to an enclosing function, such as the
inner `x` in `function(f) function(x) f(x)`. A lambda passed as an argument is not judged at all,
because the call gives its parameters their types only after the lambda is inferred. A `...` formal is
never reported, and a default does not count as a type, because an unannotated parameter takes its
type from its uses. Annotate a parameter that really accepts anything as `Any`, which strict mode
treats as a deliberate choice.

The parameter finding is about the declaration, so it can stand beside an origin in the body that it
feeds, as in `function(node) node$value`, where annotating `node` would fix both.

Returns and bindings are not reported separately. An undetermined return or binding always traces
back to one of the origins below, a type error, or a reference to a project binding whose own
definition is reported, so reporting the declaration too would repeat that finding.

### Where an undetermined type is reported

An undetermined value is reported once, where it first became undetermined, not at every later
expression that carries it. There are three such origins: a construct the type system does not
describe, a reference to a binding whose type is not known, and a recursive definition that could not
be typed. A declaration whose return type is `Unknown` produces no finding at its call sites, and an
`Unknown` nested inside a larger type is not reported either.

A reference to a binding defined in this project is not an origin; the binding's own definition is
reported instead, so one undetermined value does not produce a finding in every file that reads it.
An unresolved bare name is not an origin either, because naming already reports it. An unresolved
`pkg::name` is currently reported both ways. A value under any `#:` annotation (checked, `@trust`,
`@if-unknown`, or `@new`) is not an origin, because the annotation gives it a type.

### Diagnostics

Strict diagnostics carry the code `strict`, so they can be filtered separately from type errors. Each
origin is reported once, at the exact range of the originating expression. A binding and a bare
expression are worded differently, because a binding can be annotated and a bare expression cannot.

## Syntax errors

A file with syntax errors is still analyzed, under one rule: a broken region reports its syntax error
and, strict mode aside, nothing else, because the checker draws no conclusions from source it could
not read.

- Every well-formed statement in the file is analyzed normally. Definitions keep their exports,
  references resolve, and a genuine type error outside the broken region still surfaces.
- A broken statement contributes nothing: no names, no reads, and no diagnostics beyond the syntax
  error covering it. Strict mode is the exception, and can still report an undetermined type there.
- An unterminated argument or parameter list ends at the next statement, so the mistake stays on the
  line that made it. A list that runs onto the next line is ordinary R, and a fragment there such as
  `beta)` really is a forgotten separator and is reported as one. But a line that assigns is the next
  statement, because adopting it would report a "missing separator" on that line and every line after
  it, and cost each adopted line its own definitions.
- A broken assignment whose name side is intact keeps its definition. The value becomes a hole that
  types as `Unknown`, so its dependents neither lose resolution nor see a wrong type while the value
  is being edited. The hole is not a strict-mode origin, because the syntax error already marks it.
- A checked annotation on such a broken definition binds its declared type without checking it, so
  the definition keeps its contract for callers until the value parses again, and is then checked
  against the annotation as usual.
