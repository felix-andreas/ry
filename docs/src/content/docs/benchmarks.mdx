## Untyped R on call-heavy real-world workloads

`just bench-real` times the workloads below. They are shaped like production R: S3 classes and
dispatch, S4 and R6 objects, `tryCatch` and condition handlers, validation helpers, `lapply`
pipelines, list records, tables, xts and zoo time series, and scalar simulation. Each workload runs
in a fresh process per engine, in five or more rounds, and the table reports the median seconds
([how it was measured](#timing-the-real-world-workloads)).

<RealWorkloads />

A ratio above 1 means ry is faster. Most hot code in these workloads sits in closures called too
few times to reach the JIT, so call setup, S3 lookup and complex assignment decide the result, and
ry trails GNU R there. The `functional` and `strings` workloads are missing from the table because
they fail on the GNU R of the measuring machine. A single run on the measuring machine varies by up
to 25%, so read a ratio together with its spread, not alone. The workloads will be recalibrated against
[profile summaries](/reference/cli#profile-summary) from real code bases.

`just bench-real --write` regenerates `tools/bench/real/results.json`, which this page reads.

## Synthetic kernels

Each program runs as plain R on GNU R, as the same plain R on ry, and typed in
[strict mode](/tutorial/fully-typed#strict-mode) on ry. All three compute the same result.

<BenchmarkTable />

Recursion and loops gain the most, while vectorized builtins already run in C on GNU R. Types add
a second gain: a typed function in strict mode compiles to native code before its first call and
works on native numbers, strings and lists, so `closures`, `report` and `expr_tree` run between 60
and 120 times faster typed than on GNU R. Whole-vector arithmetic (`vector_arith`) gains little,
because each operation still writes a new vector, and the typed functions over `Result` and
dictionaries (`validate`) run about twice as fast as untyped code.

## How it was measured

Each program times its own work with the harness above, so startup and the static check are left
out. The harness runs once to warm up, then three times, and keeps the fastest run.

### Timing the real-world workloads

`just bench-real` (`tools/bench/real/run.py`) times every engine in rounds. A round runs each
engine once, in a fresh process and in an order shuffled per round, and the ratio of two engines is
taken within each round. The table reports the median of those per-round ratios with the lowest and
highest round beside it, so `1.62x (1.47 to 1.78)` means the second engine was faster in every one
of the rounds and by 1.62x in the middle one. Each suite's geometric mean comes with a 95% bootstrap
interval over rounds.

The method follows from where the noise comes from. The measuring machines are shared cloud VMs
whose effective CPU speed drifts with the load of other tenants, and that drift does not show up as
steal time or load average. A fixed loop of integer arithmetic in C took between 0.30 and 0.39 s
across processes on a quiet VM, and pinning the process to one core or turning address-space
randomization off did not narrow that. A slow drift moves both engines of one round together, which
is why each ratio is formed inside a round:

| Choice | Why |
| --- | --- |
| At least 5 rounds (`--repeat`, default 5) | With 25% swings per process, 3 samples cannot tell a 10% change from noise. |
| Engines shuffled within each round (`--seed`) | A fixed order lets a drift favour whichever engine runs second. |
| Two ry builds in the same rounds (`--baseline PATH`) | Each build is compared with the same GNU R samples. Comparing two runs that each timed GNU R separately once turned one program's 1.53x into 1.12x, because GNU R's own time moved by 31% between the two runs while ry's moved by 4%. |
| Rows under 0.1 s on any engine are marked too short and left out of the geometric mean | A run that short mostly measures start-up and the timer. |

A workload in the representative mix reports the median of `RY_BENCH_REPEAT` warm runs inside its
process (`harness.R`), after one cold run. A program from the public suites (`--public`) runs once
per process, so its time includes GNU R's byte compilation and ry's tier-up, as a script run from
the command line would. Neither number includes process start-up, which is 0.18 s for GNU R and
0.05 s for ry on the measuring machine.

One sitting of 5 rounds on a 4-core cloud VM, timing GNU R, ry and an older ry build together,
gave these 95% intervals. The last column compares two ry builds with nearly the same runtime, so
it shows the smallest change between builds that one sitting can resolve:

| Suite | Rows in the mean | GNU R / ry, JIT on | Older build / ry, JIT on |
| --- | ---: | --- | --- |
| Representative mix | 10 | 1.59x (1.52 to 1.63) | 1.02x (0.97 to 1.04) |
| awfy | 5 | 1.87x (1.78 to 1.98) | 0.99x (0.92 to 1.07) |
| rcp | 14 (empty-while and scalar-while too short) | 2.36x (2.22 to 2.44) | 1.01x (0.95 to 1.06) |
| shootout | 31 (spectralnorm and spectralnorm_naive too short) | 1.94x (1.89 to 1.97) | 1.00x (0.98 to 1.03) |

A difference between two builds smaller than about 5% on a suite, or 10% on a single program,
needs more rounds or an instruction count (`valgrind --tool=callgrind`) to show.

### Comparing two builds of ry on testthat

The testthat workload (`tools/bench/real/testthat.R`) gives two different wall times, and they
answer different questions:

| Number | What it covers | Command |
| --- | --- | --- |
| Test phase | One warm run of the tests, the median of `RY_BENCH_REPEAT` runs | field 3 of the output of `RY_JIT=on RY_BENCH_REPEAT=5 ry run --runtime ry testthat_full.R` |
| Process wall | Start-up, loading testthat, one cold run and five warm runs | `time` around the same command |
| Load | Start-up and loading testthat only | `time ry run --runtime ry load.R`, where `load.R` holds only `suppressPackageStartupMessages(library(testthat))` |

`testthat_full.R` is `harness.R` followed by `testthat.R`, and its checksum is `27:22821`. Both
builds use the same `R_LIBS`, a library that ry itself installed testthat into, and each number is
the median of five fresh processes. On the Linux release build with the JIT on, the test phase
measured 0.219 s and the process wall 1.44 s, which is how one workload can be quoted as both. The
comment at the top of `tools/bench/real/harness.R` gives the full environment of each command.

`just bench-why --write` runs every program twice per engine, alternating engines, and stores the
fastest time and the largest memory peak in `tools/bench/why/results.json`, which every table on
this site reads.
