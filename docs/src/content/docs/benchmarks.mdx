Four suites compare ry's runtime with GNU R. Two run code that others wrote: the programs that
R compiler research measures itself on, and the test suites of CRAN packages. The other two run
code we wrote: small numeric kernels, each also written in typed ry, and programs in the shape of
package and business code. Each suite's geometric mean of ry's speed-ups over GNU R:

Every number on this page is rendered from the results files in `tools/bench/`, and each chart names
the date, the version of the engine ry is compared with, the machine and the ry commit of its
measurement.

## Public R JIT benchmarks

These are the programs that the [Ř](https://github.com/reactorlabs/rir) (rir) and rcp R compilers
are measured on. They come from the benchmark directory of the
[r-compile-server](https://github.com/PRL-PRG/r-compile-server/tree/b2b13a3150bddcc2d6dae8c37ecbbf1007170940/client/rsh/inst/benchmarks)
repository, the suite of Kocourek, Křikava and Vitek,
"[Copy-and-Patch Just-in-Time Compiler for R](https://ch-rigid.github.io/publications/kocourek_copyandpatch_2025.pdf)"
(VMIL 2025): all 57 but three that cannot be sized to a few seconds. The suite combines ports of
[Are We Fast Yet](https://github.com/smarr/are-we-fast-yet), ports of the
[Benchmarks Game](https://benchmarksgame-team.pages.debian.net/benchmarksgame/) and the rcp
micro-benchmarks. They are vendored unchanged with their MIT licence, and
each file ends with a driver that runs the program once at a fixed size and prints a checksum and
its time. The sizes make GNU R 4.6 take about half a second to two seconds per program. Every run
is a fresh process, so the time includes GNU R's byte compilation and ry's JIT tier-up, though not
start-up.

<SpeedChart suite="public" />

Scalar loops gain the most, because the JIT compiles them to machine code while GNU R interprets
bytecode. Programs that spend their time allocating gain the least.

Each distinct algorithm also exists in typed ry, as a `<name>.typed.R` beside its main program, and
runs in [strict mode](/guide#strict-mode) as the ry typed column; the variants of one algorithm have
no typed version of their own. A port is written as typed ry is written, so where the R program
relies on something typed ry does not have, such as `...`, `<<-`, matrices or complex numbers, it
uses the typed equivalent, and `suite.toml` notes which. Its printed output and result match GNU
R's, so it has the same checksum. awfy storage and regexdna have no typed version, because typed
ry cannot yet express them as written.

## Package test suites

This suite times the test suites of packages from ry's benchmark dependency set. Each package and
every dependency it installs is pinned by version and by the SHA-256 of its source tarball
(`tools/bench/packages/lock.tsv`), so two machines measure the same code. GNU R installs them into
one library that both engines load, because ry's `libR` is ABI-compatible with GNU R's. The tests
run the way `R CMD check` runs them, offline. Each time is the wall time of a whole process, or
for a package whose `tests/` holds plain scripts, the sum over one process per script, so it
includes start-up and loading the package and its imports, as real use does.

The suite also counts the tests that pass, fail and raise errors on each engine. A package whose
counts differ between the engines is flagged, and a package whose tests do not run to the end on an
engine is marked as failing there and has no speed-up.

## Numeric kernels (ours)

These are small programs we wrote whose time goes into arithmetic on numbers and numeric vectors:
recursion, scalar loops, element loops over vectors, whole-vector arithmetic and a few kernels from
the finance and biostatistics code bases. A process runs each program once cold and then five
times warm, and the median warm run is its time, so the time leaves out start-up, GNU R's byte
compilation and ry's first tier-up. Most programs also exist in typed ry, as a `<name>.typed.R`
beside the plain R, which runs in [strict mode](/guide#strict-mode) as the ry typed column. Every
engine must print the same checksum as GNU R, or the runner refuses to store the results.

<SpeedChart suite="kernels" />

Recursion and scalar loops gain the most from the JIT. Kernels whose time goes into vector and
statistical routines gain the least, because those routines run in C on GNU R too. Typed scalar
loops and recursion gain more again, because a typed function in strict mode compiles to native
code before its first call.

## Application workloads (ours)

These are programs we wrote in the shape of the code that packages and analyses run: validation at
API boundaries, condition handling, S3, S4 and R6 objects, records as named lists, string building,
data frames and data.table, time series and a testthat suite. Their time goes into R's object and
data machinery rather than into arithmetic. They are measured like the kernels, and six of them
also exist in typed ry.

<SpeedChart suite="applications" />

These programs gain less than the kernels, because call setup, method dispatch, condition handling
and complex assignment decide their time, not loops the JIT compiles. Typing gains the most where
the typed core compiles the whole program. Where it refuses part of a program, that part runs in
the interpreter, and the flag under the bar names what was refused.

<BenchmarkSection suite="typed">

This suite asks how close typed ry comes to Rust. It takes the typed version of every numeric
kernel and application workload above and times it against the same program written in Rust: the
same algorithm on the same sizes, in the data model a Rust programmer would pick, such as a
`Vec<f64>` for a `List<F64>`, a struct for a record and an enum for a tagged union. Rust is the
baseline here, so a ratio is typed ry's time over Rust's: 1x is Rust's speed, and lower is faster.

<SpeedChart suite="typed" />

Each Rust program is one file compiled with `rustc -O`. That is optimization level 3, the level of
cargo's release profile, and no flag names a target CPU, so the program is built the way a released
Rust program is. The two engines are timed alike: a process runs the program once cold and five
times warm and reports the median warm run, through a harness in each language that takes the same
samples (`tools/bench/harness.typed.R` and `tools/bench/typed/harness.rs`). A Rust program passes
its inputs through `black_box`, which keeps the compiler from computing the result ahead of the
run. Both must print the same checksum.

Start-up is outside these times, so the suite can time much shorter runs than the suites above. A
program counts as too short only when Rust finishes it in under 0.1 ms. The suite has no memory
table, because the runner cannot read a peak below its own memory use, and a Rust program needs
less than that; the two suites above give the memory of the typed programs. Reproducing the suite
needs `rustc` and no GNU R.

Compile time is outside every timed run too, and the suite reports it in a table of its own,
because typed ry compiles a function the first time it is called and has to stay fast at it. The
Rust column is one `rustc` process per program. The typed column is the time the typed core spent
compiling the program's functions, summed from the `compiled for ... in N us` and
`refused ... after N us` lines that `RY_TYPED_LOG=1` prints.

## How it was measured

The published numbers measure the build you download: the official Linux x86_64 archive of a
tagged release, which is profile-guided and laid out by BOLT (`tools/layout/optimize.sh`). The
runner unpacks the archive into a private directory where its `ry` extracts the runtime and base R
it embeds, and the line under each chart names the release and the first digits of the archive's
sha256. A suite whose line names a commit instead was measured on a plain release build of that
commit (`cargo build --release`), without the release layout.

A run measures several rounds. Each round runs every program on every engine once, with the
programs in an order shuffled per round and the engines in an order shuffled per program, from a
recorded seed. Each ratio is formed inside one round, GNU R's time over the engine's, and the
reported speed-up is the median of those per-round ratios. Pairing matters because the measuring
machines are shared cloud VMs whose effective CPU speed drifts with other tenants' load: a slow
drift moves both engines of one round together, so it cancels in the ratio. Each speed-up and each
geometric mean carries a 95% bootstrap interval over the rounds.

What one timed run covers differs by suite:

| Suite | One process runs | The time includes |
| --- | --- | --- |
| Public R JIT benchmarks | the program once | byte compilation and JIT tier-up, not start-up |
| Package test suites | the package's tests | start-up and loading the package and its imports |
| Numeric kernels, application workloads | the program once cold, then five times warm | the median warm run only |

The runner, not this page, judges the data:

- **Checksums.** Every engine must print the same checksum as GNU R for a program, or the run fails
  and nothing is written. A numeric checksum may differ by a relative 1e-10, because a typed program
  may sum in a different order. A program that fails on any engine also fails the run.
- **Package tests.** The packages suite is the exception, because there the program is the
  package's own test suite. Test counts that differ between the engines are flagged as tests
  differ, and the package stays in the geometric mean. A test script that ends in an R error, as
  `R CMD check` reads a failing script, counts as one failed test. A test suite that crashes or
  does not run to the end on an engine is recorded as failing there, which leaves the package out
  of the geometric mean.
- **Too short.** A program GNU R finishes in under 0.1 s does too little work for a stable ratio, so
  it is flagged too short and left out of every geometric mean. A ry time under 0.1 s is flagged
  too, but it counts, because that speed is what the suite measures.
- **Wide intervals.** A ratio whose interval reaches more than 10% from its median gets extra
  rounds, and it is flagged wide interval if they do not narrow it.
- **Refused typed programs.** Where the typed core refuses part of a typed program, that part runs
  in the interpreter, and its flag gives the refusal.

<BenchmarkMethod />

To reproduce a suite, run its command from the table on a machine with GNU R; the packages suite
first needs `just bench-packages install`. Without `--release`, a run measures the local release
build in `target/release`, which is how to compare two builds of your own (`--baseline`), and
`--ry PATH` measures the release build at another path. With
`--write`, the runner stores `tools/bench/<suite>/results.json` with the release tag, the archive's
file name and sha256, and the commit the tag names, and `just readme` rewrites the README summary
from it. `--write` refuses a nightly archive, a local build, and a working tree with a change to a
tracked file or an untracked file under `crates/` or `tools/bench/`, so the stored programs
reproduce the measurement. The README summary warns when the suites were measured on different machines (CPU
model or kernel) or against a GNU R on a different BLAS, because their ratios are then not
comparable.
