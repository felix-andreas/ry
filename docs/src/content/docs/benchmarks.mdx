## Public R JIT benchmarks

These are the 54 programs that the Ř (rir) and rcp R compilers are measured on, from the suite of
Kocourek, Křikava and Vitek, "Copy-and-Patch Just-in-Time Compiler for R" (VMIL 2025), minus three
programs that cannot be sized to a few seconds. They are vendored unchanged with their licences, and
each file gets a driver block that calls the program once at a fixed size and prints a checksum.
The sizes make GNU R 4.3 take about 0.5 to 2.5 seconds per program. A run starts a fresh process
per program and engine, so the time includes GNU R's byte compilation and ry's tier-up.

## Package test suites

This suite times the test suites of the packages in ry's benchmark dependency set, with their
dependencies: 58 packages, each pinned by version and the SHA-256 of its source tarball, so two
machines measure the same code. Both engines load the same builds, installed by GNU R, because ry's
`libR` is ABI-compatible with GNU R's. The tests run the way `R CMD check` runs them, offline, and
each time is the wall time of a whole process, so it includes start-up and loading the package and
its imports, as real use does. The suite also counts the tests that pass and fail on each engine.

## Numeric kernels (ours)

These are small programs we wrote: recursion, scalar loops, element loops over vectors, closures,
records and strings, and a few kernels from the finance and biostatistics code bases. Each exists
twice, as plain R and typed in [strict mode](/guide#strict-mode), so the suite compares three
engines: GNU R, ry on the plain R, and ry on the typed program. All three must print the same
checksum, or the runner refuses to store the results.

<SpeedChart suite="kernels" />

Recursion and loops gain the most from the JIT, while vectorized builtins run in C on GNU R too, so
whole-vector arithmetic gains little. Types add a second gain: a typed function in strict mode
compiles to native code before its first call and works on native numbers and lists, so typed
scalar loops and recursion gain the most. Programs built on records, tags and text run mostly in
the interpreter, because the native compiler does not handle those types, so typing gains them
little or loses.

## Application workloads (ours)

These are programs we wrote in the style of production R, each exercising one kind of code:
condition handling, object systems, records, tables, time series and argument validation. Most of
their time goes to calls, method dispatch and assignment rather than to arithmetic. The code is
untyped R, run unchanged on GNU R, on ry with its JIT on and on ry with its JIT off.

<SpeedChart suite="applications" />

Most hot code here sits in closures that are called too few times to reach the JIT, so call setup,
S3 lookup and complex assignment decide the result, and ry trails GNU R on most workloads. Vector
arithmetic in loops, as in `simulation`, is where ry gains.

## How it was measured

Every suite runs the same way. A run measures several rounds, and each round runs every engine on
every program once, in an order shuffled from a recorded seed. Each ratio is formed inside one
round, GNU R's time over the engine's, and the reported speed-up is the median of those per-round
ratios. Pairing matters because the measuring machines are shared cloud VMs whose effective CPU
speed drifts with other tenants' load: a slow drift moves both engines of one round together, so it
cancels in the ratio. Each speed-up and each geometric mean carries a 95% bootstrap interval over
the rounds.

The runner, not this page, judges the data:

- **Checksums.** Every engine must print the same checksum for a program, or the run fails and
  nothing is written. A failing program also fails the run, so a committed file holds no failures.
- **Too short.** A program that an engine finishes in under 0.1 s does too little work for a stable
  ratio, so it is flagged too short for that engine and left out of that engine's geometric mean.
- **Refused typed programs.** A typed program the compiler refuses in strict mode has no typed time,
  and its flag gives the compiler's reason.

No suite includes ry's static check. Each suite's own section says whether process start-up counts.
