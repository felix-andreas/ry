---
title: Nominal types
description: Named types that keep values with the same shape apart, and make one constructor the only way to create a value
---

import { Tabs, TabItem } from '@astrojs/starlight/components';

Records and tag unions are *structural*: a value fits a type when it has the right shape, whatever
the type is called. `alias` only gives a shape a name, so these two types are the same type, and
passing a Fahrenheit temperature where Celsius is expected goes unnoticed:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
alias Celsius = Record{degrees: double}
alias Fahrenheit = Record{degrees: double}

boils <- function(water: Celsius) -> logical water$degrees >= 100

oven: Fahrenheit <- (degrees = 350,)
boils(oven)   # no error: both are a record with one `degrees` field
```

</TabItem>
<TabItem label="Comments">

```r
#: @alias Celsius {Record{degrees: double}}

#: @alias Fahrenheit {Record{degrees: double}}

#: fn(water: Celsius) -> logical
boils <- function(water) water$degrees >= 100

#: Fahrenheit
oven <- (degrees = 350,)
boils(oven)   # no error: both are a record with one `degrees` field
```

</TabItem>
</Tabs>

`type` declares a *nominal* type instead: a named type that is distinct from every other type, even
one with exactly the same shape. A value gets the type only from its constructor, `@Fahrenheit(...)`,
so the mix-up is an error. The comment spellings are `#: @type` and `#: @new`:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
type Celsius = Record{degrees: double}
type Fahrenheit = Record{degrees: double}

boils <- function(water: Celsius) -> logical water$degrees >= 100

oven <- @Fahrenheit(degrees = 350,)
boils(oven)
```

</TabItem>
<TabItem label="Comments">

```r
#: @type Celsius {Record{degrees: double}}

#: @type Fahrenheit {Record{degrees: double}}

#: fn(water: Celsius) -> logical
boils <- function(water) water$degrees >= 100

#: @new Fahrenheit
oven <- (degrees = 350,)
boils(oven)
```

</TabItem>
</Tabs>

```text ry check typing
type-mismatch

  x expected `Celsius`, found `Fahrenheit`
```

Choose `type` when values share a shape but must not mix, such as two units, or a user ID and an
order ID. Choose `alias` when any value of the shape will do. Everything else works as it does for
the structural form: `$` reads a field, `match` checks every case, and at run time `@Fahrenheit(x)`
is just `x`. The parentheses of `@Name(...)` belong to the value inside, so `@Fahrenheit(degrees =
350,)` is a one-field record, `@Pair(1L, "a")` a tuple, and `@Shape(:Circle(radius = 1))` a tag.

## One constructor

Only `@Name(...)` creates a value of a nominal type, so when it appears in one function, that
function is the only way to make one. Here `@Email(...)` appears only in `check_email()`, so every
`:Verified` address in the program has passed the check. A tag written anywhere else does not fit,
although its shape does:

<Tabs syncKey="annotation-style">
<TabItem label="Inline">

```r
type Email =
  | :Verified(address: character)
  | :Unverified(address: character)

check_email <- function(address: character) -> Email {
  if (grepl("@", address)) {
    @Email(:Verified(address = address))
  } else {
    @Email(:Unverified(address = address))
  }
}

email: Email <- :Verified(address = "nobody")
```

</TabItem>
<TabItem label="Comments">

```r
#: @type Email {
#:   | :Verified(address: character)
#:   | :Unverified(address: character)
#: }

#: fn(address: character) -> Email
check_email <- function(address) {
  if (grepl("@", address)) {
    #: @new Email
    :Verified(address = address)
  } else {
    #: @new Email
    :Unverified(address = address)
  }
}

#: Email
email <- :Verified(address = "nobody")
```

</TabItem>
</Tabs>

```text ry check typing
type-mismatch

  x expected `Email`, found `:Verified(address: character)`. The value has the right shape, but `Email` is a nominal type, so only `@Email(...)` or `#: @new Email` creates one
```

## Over R values

`type` works over any type, not only ry's records and tags. With `type UserId = character` and
`type OrderId = character`, passing an `OrderId` where a `UserId` is expected is an error, although
both are strings at run time. Over an R list, the `#:` spelling keeps the file plain R that GNU R
runs:

<Tabs syncKey="annotation-style">
<TabItem label="Comments">

```r
#: @type Money {list{amount: double, currency: character}}

#: fn(amount: double, currency: character) -> Money
money <- function(amount, currency) {
  if (amount < 0) stop("negative amount")
  #: @new Money
  structure(list(amount = amount, currency = currency), class = "Money")
}
```

</TabItem>
<TabItem label="Inline">

```r
type Money = list{amount: double, currency: character}

money <- function(amount: double, currency: character) -> Money {
  if (amount < 0) stop("negative amount")
  @Money(structure(list(amount = amount, currency = currency), class = "Money"))
}
```

</TabItem>
</Tabs>

The constructor checks the shape when ry analyzes the code, and `stop()` checks the values when it
runs, so every `Money` in the program has passed both.

## Operators

A nominal value is still accepted where its representation is, so `nchar()` works on a `UserId`.
Arithmetic gives the plain representation back: with `type Celsius = double`, the sum of two
`Celsius` values is a `double`, because ry cannot assume that adding two temperatures gives a
temperature. `Money` is a list, so `+` on it is an error until you declare the operator:

<Tabs syncKey="annotation-style">
<TabItem label="Comments">

```r
#: fn(a: Money, b: Money) -> Money
`+.Money` <- function(a, b) money(a$amount + b$amount, a$currency)
```

</TabItem>
<TabItem label="Inline">

```r
`+.Money` <- function(a: Money, b: Money) -> Money {
  money(a$amount + b$amount, a$currency)
}
```

</TabItem>
</Tabs>

Now `money(1, "EUR") + money(2, "EUR")` is a `Money`. R finds `+.Money` through the class attribute,
which is why the constructor sets one; ry itself needs no class to check the type.

## Parameters and aliases

A type can take parameters: with `type Page<T> = list{items: list[T], total: integer}`, reading
`items` from a `Page<integer>` gives a `list[integer]`.

`alias` names a type without making it nominal, so `alias Row = list{id: integer}` is a shorter
way to write the shape.

Definitions belong at the top level of a file. In the comment spelling, a `@type` or `@alias` line
needs its own `#:` block, separated from other annotations by a blank line. If you keep both
spellings, put the `#:` block directly above the inline definition: ry reads the pair as one
definition and warns when the two disagree.

## R6 and S4 objects

Existing R6 and S4 classes keep working, but their objects are [`Unknown`](/type-checking/unknown), and ry warns on each
class definition (`object-system`) because [records and tags](/type-checking/records-and-tags)
model data with every field checked. To check who receives one, give it a nominal type over [`Any`](/type-checking/unknown#any) and wrap its
constructor:

<Tabs syncKey="annotation-style">
<TabItem label="Comments">

```r
#: @type Account {Any}

#: fn() -> Account
new_account <- function() {
  #: @new Account
  AccountClass$new()
}
```

</TabItem>
<TabItem label="Inline">

```r
type Account = Any

new_account <- function() -> Account @Account(AccountClass$new())
```

</TabItem>
</Tabs>
